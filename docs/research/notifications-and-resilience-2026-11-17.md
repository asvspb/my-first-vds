## 1. Сценарий: две фазы попадания «в поле зрения»

Когда сервер попадает под внимание РКН/ТСПУ, сценарий обычно состоит из двух фаз.

### Фаза A — разведка (Active Probing)

ТСПУ или сканеры ФГУП «ГРЧЦ» начинают прощупывать IP/порт сервера: шлют нестандартные
TLS ClientHello, HTTP-запросы, проверяют ответы UDP — пытаются классифицировать узел
(«обычный сайт» или VPN).

### Фаза B — воздействие (блокировка по IP / порту / протоколу)

ТСПУ начинает дропать пакеты от российских клиентов к серверу или слать поддельные
TCP RST.

**Парадокс зарубежного сервера:** сам зарубежный узел (asv2) при этом не видит ошибок —
для него в его сегменте интернета всё работает идеально, просто от конкретного клиента
внезапно перестают приходить пакеты (тишина). Блокировка видна **не серверу**, а клиенту.

**Кто видит блокировку мгновенно:** клиентская сторона — `vpn guard` на ноутбуке
(см. §3.4), правила уровня `G-01` (blackhole), `G-04` (`awg_tx_no_rx`: пакеты в AWG
уходят, ответов ноль), `G-09` (серия TCP RST до рукопожатия).

## 2. Что сервер делает при сканировании **сейчас** (подтверждено кодом)

### 2.1 `vds gateway probe-watch` — монитор Active Probing

Модуль `src/gateway/probing.py`. Ранний сигнал перед TSPU-блокировкой: измеряет
зондирование боевых TCP-портов **{443, 8443, 2053}** без изменения конфигов xray/hysteria2.

Механика (по докстрингу модуля):

| Элемент | Что делает |
|---|---|
| nft-таблица `inet vds_probe` | счётчики `syn_bare` (все SYN на 443) и `syn_valid` (SYN с пакетом длиннее минимальных 40 б — клиентский SYN всегда несёт TCP-опции; голый SYN-сканер masscan/zmap — ровно 40 б); аддитивные `syn_valid_extra` / `syn_bare_extra` (суммарно 8443+2053) |
| set `probers4` | src-IP зондирований на tcp {443, 8443, 2053}, per-element counter, timeout 1h |
| `watch` (read-only) | дельта счётчиков против снапшота `/var/lib/vds/probe-watch.json` (атомарная запись 0600, FileLock) + journal-сигнатуры |
| `verified_session_ips` | IP с верифицированными двусторонними сессиями (TCP 443/8443/2053 через `ss -tniH` по порогам bytes; UDP 443/51826 через `nf_conntrack` `[ASSURED]`+bytes) исключаются из «новых RU-IP» вместе с AWG/allow-ips; кэш с TTL 24 ч |
| быстрый контур `fast_contour_check` | хук 5-мин сэмплера `vds-logs-sample`: дельта `probers4` за окно сэмпла; при ≥ `FAST_CONTOUR_PROBERS` уникальных IP — **только journal-тег `FAST-CONTOUR`, авто-действий нет** |
| RU-классификация | при наличии агрегата `/etc/vds-relay/ru-cidrs.txt` (пишет `relay-cidr` или `probe-watch ru-cidr install`) IP помечается `[RU]`; иначе `geo: unknown` — честно, без догадок |
| `--explain` | карта покрытия сигналов на этом сервере: что активно, что слепо |
| IPv6-пробы | non-goal v1 |

**Вердикты окна:** `RU-PROBE-SUSPECT` / `PROBE-BURST` / `quiet`.

**Машина threat-level** (SPEC-20261116-probe-response §2):

- уровни: **`quiet` / `elevated` / `high`**;
- `elevated` = 1 окно `PROBE-BURST` ИЛИ 1 окно `RU-PROBE-SUSPECT`; выход — 3 тихих окна;
- `high` = `RU-PROBE-SUSPECT` **2 окна подряд** (`PROBE-BURST` сам по себе — шум,
  максимум `elevated`);
- выход из `high` — 72 окна без новых RU-IP (decay), затем `elevated`, затем 3 тихих →
  `quiet`; **decay заморожен при активном lock-443** (§9.A: лок ослепляет `syn_valid`);
- `high` **недостижим при `geo: unknown`** (threat-reason обязан объяснить почему);
- flapping-защита: даунгрейд не раньше 2 окон после апгрейда;
- состояние переживает рестарт юнита (лежит в снапшоте, `SNAPSHOT_VERSION = 2`:
  `+threat/config/own_ips`).

### 2.2 Авто-реакция: `lock-443`

- **opt-in и по умолчанию ВЫКЛЮЧЕН**: `vds gateway probe-watch config --auto-lockdown on`
  + часовой тик таймера при level `high` → внутренний вызов `lock-443`
  (`reason auto:RU-SUSPECT`).
- `lock-443` удаляет широкие правила 443/tcp (в undo-журнал `state.json["ufw_lockdown"]`),
  добавляет изоляцию; **TTL-автоснятие** тиком probe-watch (`--lockdown-ttl`),
  забытый лок невозможен; **downgrade лок НЕ снимает** (OQ-3).
- Параметры: `--lockdown-allow` (белый список адресов), `--lockdown-ttl`.
- `vds system ufw harden` **уважает** активный лок-443: отказ без `--force` (§9.C),
  обход пишется в журнал лока.
- Важно: **лок = отдельное состояние** (`state.json["ufw_lockdown"]`), а не «третий
  уровень threat».

### 2.3 Healthcheck

`vds gateway healthcheck` (`src/gateway/health.py`, таймер `vds-gateway-health.timer`
каждые 5 минут): страховка от тихих сбоев — упавший юнит или истекающий сертификат;
read-only, кроме **rate-limited рестарта** упавшего юнита.

### 2.4 Шлёт ли сервер письма **сейчас**

**Нет.** Проверено: в `src/` и `systemd/` отсутствуют любые следы
`telegram|smtp|smtplib|notify-send|alert.env|webhook` (grep пуст). Сейчас:

- `probe-watch` пишет только в свой JSON (`/var/lib/vds/probe-watch.json`) и journal;
- `vds relay status` (`--json`) отдаёт машиночитаемый снимок, но никуда его не отправляет;
- `vpn guard` пишет локальный `findings.jsonl` и умеет показать всплывающее окно
  `notify-send` **на экране ноутбука** (флаг `--notify`).

То есть **уведомлений наружу (email/Telegram) нет ни на одном узле.**

## 3. Текущая картина по узлам (что где видно)

Архитектура на 2026-11-17: **RU-релей** (`185.80.91.135`, LandVPS) ↔ **зарубежный
exit-узел asv2** (`213.108.23.119`), плечо релея — AmneziaWG UDP/443 (`awg0` на релее),
нога до exit — `awg1` → AWG-сервер exit-узла на UDP/51825 (`RELAY_EXIT_PORT`).

| Что | Где видно | Чем |
|---|---|---|
| Active Probing по 443/8443/2053 | exit-узел (и релей, если на нём стоит probe-watch) | `probe-watch.json` (threat + вердикты окна), journal-теги `FAST-CONTOUR` |
| Пропал пульс плеча relay → exit | **на exit-узле** (сторона AWG-сервера: `latest_handshake` пира-релея) | `awg show` / `vds relay status --json` → `exit_handshake_age_sec` (на самом релее); на exit — метрика handshake пира |
| Доступность релея снаружи | exit-узел | TCP-коннект до `185.80.91.135:443` |
| Блокировка «первой мили» (провайдер владельца до exit) | **только ноутбук** | `vpn guard` G-01/G-04/G-09, `findings.jsonl`, `notify-send` |
| Лок 443 / auto-lockdown | exit-узел | `state.json["ufw_lockdown"]`, `lock-443` |

**Ключевой вывод:** связка из двух узлов по разные стороны границы позволяет
детектировать блокировку даже когда ноутбук выключен — **но только если на exit-узле
есть сторож, который сам умеет отправлять сообщение наружу.**

## 4. Варианты решения: как получать уведомления

### Вариант 1 (рекомендуемый, 24/7) — сторож на asv2 → Telegram-бот и/или Email

**Идея:** уведомления всегда отправляет **зарубежный** сервер (asv2), потому что:

- на зарубежном VDS не заблокированы ни Telegram API, ни внешние почтовые серверы
  (Gmail SMTP / Resend / Mailgun);
- на **российском релее хранить токены бота или почтовые пароли нельзя** — релей
  всегда считается потенциально отчуждаемым узлом.

**Что проверяет маленький systemd-таймер на asv2 (раз в 2 минуты):**

1. **Собственный `probe-watch.json`** на asv2: смена уровня `quiet → elevated/high`
   → алерт «⚠️ На asv2 зафиксирован Active Probing (подозрение на скан ТСПУ)».
2. **Пульс туннеля `awg1` от релея** (`latest_handshake`): так как релей держит
   постоянный `PersistentKeepalive = 25` до asv2, рукопожатие обновляется каждые
   ~2 минуты. Если handshake старше 5 минут, **при этом** `185.80.91.135:443`
   пингуется снаружи → алерт «🚨 Трансграничный ТСПУ заблокировал канал
   relay → asv2 (AWG 51825/udp)».
3. **Доступность самого релея** (`185.80.91.135:443`): TCP-коннект с asv2 пропал →
   алерт «🔴 RU-relay (LandVPS) недоступен».

**Куда доставлять** (на выбор или оба сразу):

- **Канал А — Telegram-бот** (≈15 строк на Python/`urllib`, без зависимостей):
  приватный бот у `@BotFather`, токен `TG_BOT_TOKEN` и `TG_CHAT_ID` в
  `/etc/vds/alert.env` (0600) на asv2. Уведомление прилетает пушем на телефон и
  ноутбук за ~1 секунду.
- **Канал Б — Почта** через SMTP (Gmail App Password / Яндекс) или HTTP Email API
  (Resend): `smtplib.SMTP_SSL('smtp.gmail.com', 465)` из стандартной библиотеки —
  **без** поднятия своего Postfix, DKIM и работы со спам-фильтрами.

### Вариант 2 (локальный, без внешних сервисов) — desktop-алерт `vpn guard` + авто-диагноз

Когда владелец работает за ноутбуком, ТСПУ может ударить по «первой миле» (домашний
провайдер режет прямое соединение до asv2, хотя связка relay ↔ asv2 жива). **Сервер об
этом не узнает первым — первым узнаёт `vpn guard` на ноутбуке.**

Как работает:

- включается штатный desktop-нотификатор `vpn guard` (`notify-send` с уровнем
  `critical` при открытии инцидента `high` по правилам `G-01`, `G-04`, `G-08`, `G-09`);
- на экране всплывает баннер:
  - при сбое прямого канала: «Блокировка прямого канала до asv2 (G-04: AWG tx без rx).
    Переключись на релей: `vpn start relay`»;
  - при сбое релея: «Релей недоступен. Переключись на прямой или резервный профиль:
    `vpn start`»;
- опционально тот же локальный хук досылает сообщение в Telegram/почту (если после
  переключения или через DoH/релей наружу достучаться можно).

### Рекомендация

**Вариант 1 + Вариант 2 вместе:**

1. **На ноутбуке:** включить desktop-уведомления `vpn guard` только для боевых
   транспортных инцидентов (`G-01..G-04`, `G-08`, `G-09` уровня `high`/`medium`) —
   при блокировке провайдером сразу видно всплывающее окно.
2. **На asv2:** добавить лёгкий юнит `vds-alert-watch.timer` (без внешних библиотек,
   на штатных `urllib.request` / `smtplib`), который следит за probe-watch и живым
   рукопожатием от релея и шлёт пуш в Telegram и/или письмо.

## 5. Механизмы живучести: три эшелона

### Эшелон 1 — постоянная мимикрия и «криптографическое молчание»

Работает каждую секунду, до того как сервер смогли классифицировать.

**443/tcp (Xray Reality) — «живой двойник» (L4 splice):** в первом же пакете TLS
ClientHello сервер за микросекунды проверяет криптографическую метку (`shortId` + ключ
X25519), которую знает только клиент. Если метки нет (сканер) — сервер **не сбрасывает
соединение и не выдаёт поддельный сертификат**, а прозрачно пробрасывает байты на
настоящий сайт-донор. Сканер видит настоящий сертификат, настоящие заголовки HTTP/2 и
настоящую страницу. Отличить от реального фронтенда без знания приватного ключа
невозможно.

> ⚠️ Сверка с проектом: механику «L4 splice» даёт сам Xray Reality; текущий `dest`
> на узлах — `www.google.com` (дефолт), это признанная точка роста (см. TECHDEBT /
> банк идей, И20/И27). Утверждение про «донор в той же стойке /24 с задержкой <1 мс»
> относится к конфигурации релея с RU-SNI — **требует проверки на живом конфиге**.

**443/udp и 51825/udp (AmneziaWG) — «чёрная дыра» + 9 параметров мусора:** обычный
WireGuard палится по фиксированным заголовкам (`0x01000000`) и размерам пакетов (148 и
92 байта). В AWG включены параметры обфускации (`Jc`/`Jmin`/`Jmax` — случайные мусорные
пакеты перед рукопожатием, `S1`/`S2` — случайный префикс, `H1..H4` — нестандартные
заголовки типов пакетов). На пробный UDP-пакет ядро проверяет заголовки `H1..H4` и
криптографический `MAC1` (на базе публичного ключа сервера); не совпало — пакет
уничтожается молча (даже без ICMP Port Unreachable). Для внешнего сканера UDP-порт
выглядит полностью закрытым.

> ✅ Подтверждено проектом: параметры обфускации AWG реальны (`vds amneziawg obfs`,
> разные наборы на `awg0`/`awg1` релея), молчаливое уничтожение пакетов — свойство
> протокола.

### Эшелон 2 — активная защита сервера при атаке (probe-watch + lock-443)

Если ТСПУ увидел подозрительную активность по косвенным признакам (объём трафика) и
запустил серию проверочных подключений:

1. **Детектирование волны проб:** `probe-watch` анализирует телеметрию входов (сколько
   соединений ушло в Reality-фолбэк = пришли без ключа, попытки перебора TLS/SNI,
   аномальные всплески с чужих AS/подсетей).
2. **Переход в защитный режим:** при превышении порога аномальных проб уровень
   `elevated → high`, и (если включён `--auto-lockdown`) срабатывает `lock-443`.
3. **Изоляция источников сканирования:** IP/подсети сканеров отсекаются на уровне
   файрвола / прижимаются веб-приманкой (Reality-фолбэк).
4. **Приглушение шумных каналов:** вторичные транспорты, легче компрометируемые
   активным зондированием, временно уходят в защитный режим, снаружи остаётся
   максимально неотличимый веб-порт.
5. **Синхронизация с ноутбуком (`vpn guard sync`):** когда guard видит на сервере
   статус лока, он помечает паузу как `expected_lockdown` — «сервер не упал, он в
   режиме защиты от сканирования; не перезапускай и не долби реконнектами, чтобы не
   мешать маскировке».

> ⚠️ Точность формулировок: «подсети сканеров блокируются файрволом» — на практике
> сейчас блокируется **443/tcp целиком** на TTL (`lock-443`), а не отдельные
> src-подсети; `probers4` — это множество для наблюдаемости, а не блок-лист.
> Инвариант ADR-014: `probe-watch watch` **без `--record`** — read-only; `--record`
> только у юнита таймера; `guard sync` никогда не ходит с `--record`.

### Эшелон 3 — RU-релей продлевает жизнь зарубежному узлу

Самая частая причина бана зарубежных VPS в 2025–2026 — корреляция «много домашних/
мобильных IP из РФ → один зарубежный IP хостера».

С RU-релеем картина меняется:

- **зарубежный asv2 исчезает с радаров абонентских ТСПУ:** ни ноутбук, ни Android, ни
  Windows при работе через релей не посылают ни одного пакета на `213.108.23.119` —
  домашний провайдер и мобильный оператор не знают о существовании asv2;
- **разделение ролей при ударе:** если пострадает связь с релеем, asv2 остаётся чистым —
  одной командой `vpn start` возвращаешься на прямой канал; если провайдер режет прямое
  соединение с зарубежными подсетями — `vpn start relay` уводит трафик через российский
  ДЦ.

### Три практических шага (максимальный прирост без усложнения для клиентов)

#### Шаг 1. Жёсткий whitelist на межузловой порт `awg1` (51825/udp) на asv2

Порт `51825/udp` на asv2 используется **только** туннелем от релея (`185.80.91.135`);
ни ноутбук, ни телефоны на него не ходят.

```bash
ufw allow from 185.80.91.135 to any port 51825 proto udp
# и удалить общее правило 51825/udp Anywhere
```

Эффект: ни один сканер (РКН/Shodan/Censys) с любого другого IP не достучится до порта
даже на уровне сетевого фильтра ядра.

> ⚠️ Проверить перед применением: не занят ли 51825 на asv2 **другим** назначением
> (на asv2 это и есть основной AWG-порт `vds-amneziawg` для клиентов — тогда whitelist
> по одному IP **сломает** клиентов; нужен либо второй порт, либо
> `--lockdown-allow`-подобный механизм). См. §7, OQ-1 — это главный риск шага.

#### Шаг 2. Быстрый «манёвр смены порта/протокола» на плече Relay ↔ asv2 (без перенастройки клиентов)

Красивое свойство релея: все устройства знают **только адрес релея**
(`185.80.91.135:443`) и не знают, как релей общается с asv2.

Если трансграничный ТСПУ когда-либо заблокирует UDP-поток
`185.80.91.135 → 213.108.23.119:51825`, серверный скрипт (триггер — потеря handshake
в течение 3 минут) может:

- либо автоматически сменить порт и заголовки `H1..H4` между релеем и asv2;
- либо переключить ногу `vds-relay-exit` с UDP (`awg1`) на резервный TCP/Reality-туннель
  до asv2.

Эффект: блокировка обходится за секунды, на ноутбуке/телефоне/ПК не меняется ничего.

> ✅ Есть опора в коде: `vds relay status --json` уже отдаёт `exit_handshake_age_sec`
> и `_fmt_age` уже считает «ПОДОЗРИТЕЛЬНО» при возрасте > 6 ч (порог 180 с — «живая»,
> далее «в пределах PersistentKeepalive/25*3»). Триггер 3 мин — **новая логика**,
> её нет.

#### Шаг 3. Уведомление о начале атаки (watchdog на asv2 → Telegram / Email)

Как только probe-watch на asv2 фиксирует `elevated/high` или пропажу пульса от релея,
сервер сразу шлёт короткую сводку: какой узел под воздействием, какой эшелон защиты
сработал, нужно ли участие владельца. (= Вариант 1 из §4.)

## 7. Вопросы и ограничения для ТЗ (вход для архитектора)

### Ограничения (из конвенций проекта)

1. **Без внешних зависимостей** — только stdlib (`urllib.request`, `smtplib`, `json`);
   никаких `python-telegram-bot` / `requests` сверх уже принятых.
2. **Секреты:** `/etc/vds/alert.env` (0600, атомарная запись), значения **не** попадают
   в лог, journal, git и вывод команд. Фикстуры в тестах — только `FIXTURE_*` /
   зарезервированные IP (RFC 5737).
3. **Токены только на exit-узле.** На RU-релее — никогда (отчуждаемый узел).
4. **`probe-watch.json` не мутировать:** алерт-сторож читает снапшот/`watch --json`
   **без `--record`** (инвариант ADR-014). Иначе ломаются дельты таймера.
5. **Идемпотентность + dry-run по умолчанию** для установки/снятия юнита, `--apply`
   + подтверждение; `FileLock` на мутации; `run_list`, без `shell=True`; ленивые импорты.
6. **systemd-юниты — только из шаблонов** `systemd/*.tpl`; `ReadWritePaths` при
   необходимости (`/var/lib/vds`, `/var/run` для FileLock).
7. **Doc-sync:** коммит = код + тесты + mapped-доки (`tools/docsync.py explain <path>`),
   обновить `AGENTS.md`/`README.md`/`SERVER-BASELINE.md` при новой команде/юните.
8. **Не логировать UUID/пароли/ключи**; имена и IP не печатать в чат владельцу при
   выдаче секретов (в файлы 0600).

### Открытые вопросы (OQ)

| # | Вопрос | Почему важно |
|---|---|---|
| **OQ-1** | На asv2 `51825/udp` — это основной AWG-порт клиентов или только нога релея? | Если общий: whitelist по IP релея **сломает** мобильные/Windows-пиры. Варианты: второй порт для ноги релея, либо `AllowedIPs`-фильтр, либо отдельный `awg2` |
| **OQ-2** | Канал доставки: Telegram / email / оба? | Влияет на объём кода, хранение секретов, надёжность доставки |
| **OQ-3** | Нужен ли **heartbeat** («жив, всё ок» раз в сутки)? | Иначе «нет алертов» неотличимо от «сторож умер / сеть до TG упала». Dead-man switch — отдельное требование |
| **OQ-4** | Дедупликация и анти-флаппинг: окно подавления, cooldown, «не более N сообщений / час»? | `elevated` может дрожать; спамить владельца нельзя |
| **OQ-5** | Что делать при `high`/`lockdown` — только уведомить или разрешить авто-действия (auto-lockdown уже есть)? | Явно разделить «наблюдатель» и «исполнитель»; по умолчанию — только уведомление |
| **OQ-6** | Где хранить состояние сторожа (последний отправленный алерт, cooldown) и как переживать рестарт? | `/var/lib/vds/alert-state.json` (0600), атомарно, FileLock |
| **OQ-7** | Интеграция с `vds gateway healthcheck` (5-мин таймер) или отдельный юнит? | Healthcheck read-only + rate-limited restart; смешивать роли — риск |
| **OQ-8** | Плечо relay↔exit: манёвр порта `H1..H4`/TCP-fallback — в scope этого ТЗ или отдельный WP? | Это уже не «уведомления», а автоматика; другой риск-профиль (может оборвать канал) |
| **OQ-9** | Нужны ли алерты в `journal` структурированным тегом (`ALERT-SENT`/`ALERT-FAILED`) для форензики `vds logs`? | `logs/` уже собирает journal; тег даст аудит доставки |
| **OQ-10** | IPv6: слать алерты с v4 или v6, и что если v6-only? | asv2 имеет /48 v6, но egress-политика не подтверждена |
| **OQ-11** | Проверять ли доступность релея `185.80.91.135:443` **с** exit-узла — не создаёт ли это ложных «down» при TSPU-шейпинге в обратную сторону? | Двусторонняя проверка (ping + TCP + handshake) обязательна, иначе ложные алерты |

### Критерии приёмки (черновик, для ТЗ)

- AC-1: `vds alert ... --help` доступна, установка/снятие юнита идемпотентны, dry-run
  по умолчанию.
- AC-2: при `probe-watch` level `quiet→elevated` на asv2 — сообщение приходит в канал
  доставки; повтор в пределах окна подавления **не** отправляется.
- AC-3: при остановке `vds-relay-exit`/пропаже handshake > порога — сообщение
  «канал relay→exit заблокирован/мёртв» приходит; при живом handshake — не приходит
  (нет ложных срабатываний на 15-минутном прогоне).
- AC-4: секреты не появляются в `journalctl`, `--help`, логах, `git grep`; файл 0600.
- AC-5: сторож **не** пишет в `probe-watch.json` (проверка mtime/содержимого до/после).
- AC-6: при недоступном канале доставки — запись `ALERT-FAILED` в journal + повтор по
  backoff, без падения юнита.
- AC-7: живая приёмка на asv2 (реальный канал доставки), протокол — в отчёте.
- AC-8: `pytest -q` зелёный; новые тесты не требуют root/сети/docker.

## 8. Итог одной фразой

Сейчас сервер **видит** сканирование (probe-watch: `quiet/elevated/high`, вердикты
`RU-PROBE-SUSPECT`/`PROBE-BURST`) и **умеет** ответить (`lock-443` при включённом
`--auto-lockdown`), но **не умеет сообщать** — наружу не уходит ни письмо, ни пуш;
уведомление о блокировке видит только `vpn guard` на ноутбуке. Минимальное достаточное
решение — сторож на зарубежном exit-узле (Telegram и/или SMTP, stdlib) + desktop-алерты
guard; усиление живучести — whitelist межузлового порта (с оговоркой OQ-1), быстрый
манёвр порта/протокола на плече relay↔exit и heartbeat-канал.
