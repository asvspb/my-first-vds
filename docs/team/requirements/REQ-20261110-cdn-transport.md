# REQ-20261110-cdn-transport

## Мета
- **Источник:** скоуп G0, утверждён владельцем в чате 2026-11-10: пятый канал —
  **CDN-режим VLESS через Cloudflare** (VLESS+WS или XHTTP за CF-proxy,
  оранжевое облако), чтобы egress-IP для цензора был IP Cloudflare.
  Контекст: [REQ-20261109-domain-xhttp-acme](REQ-20261109-domain-xhttp-acme.md),
  [SPEC-20261109](../specs/SPEC-20261109-domain-xhttp-acme.md),
  [ADR-003](../adr/ADR-003-xhttp-reality-coexistence.md),
  [STATUS.md](../STATUS.md), [CENSORSHIP-ROADMAP.md](../../CENSORSHIP-ROADMAP.md).
- **Автор:** аналитик (vds-analyst)
- **Дата:** 2026-11-10
- **Статус:** ready (G1)

## 1. Контекст

Живой asv1 после ACCEPT-20261109 (PASS): Reality TCP 443 (клиент `phone`),
Hysteria2 UDP 443 с LE-сертификатом (клиент `mob`), XHTTP vless+xhttp+tls
**mode=port, публичный TCP 8443**, домен `103-45-247-172.eu-cloud-xip.com`,
path `/xhttp` (ADR-003, [факт] src/xray/config.py:22-25 — `XHTTP_PATH = "/xhttp"`,
mode=port → инблэнд на всех интерфейсах; src/gateway/paths.py:50 —
`XHTTP_INTERNAL_PORT = 8443`). Все прямые (direct) каналы заканчиваются на
IP сервера 103.45.247.172 — один заблокированный IP роняет весь gateway-стек
одновременно.

Цель цикла: добавить канал, у которого цензор видит **IP Cloudflare**, а не
сервер. Классическая схема — VLESS за CF-proxy: клиент → CF-edge (TLS,
оранжевое облако) → HTTP/WebSocket на origin-порт сервера → Xray.

### Установленные факты (проверено 2026-11-10)

- **DNS** [факт, dig]: домен `103-45-247-172.eu-cloud-xip.com` A →
  `103.45.247.172` (прямая запись на сервер, **без Cloudflare**). NS зоны
  `eu-cloud-xip.com` = `ns1..ns4.eu-cloud-xip.com` — собственный DNS
  регистратора, **зона НЕ в Cloudflare**. Следствие: включить CF-proxy
  (оранжевое облако) для любой записи этого домена можно **только перенеся
  зону в Cloudflare** (смена NS у регистратора) — или заведя второй домен
  уже в CF. Это владелец-уровень действие, не скриптовое.
- **XHTTP и CDN** [факт, доки Xray/обзоры]: XHTTP (splithttp) спроектирован
  для CDN. Режимы загрузки: `packet-up` — серия мелких POST, работает
  практически через любой CDN (включая CF free); `stream-up` — один
  стриминговый POST без Content-Length, быстрее, но исторически проблемен
  за Cloudflare; `auto` — по умолчанию, пробует stream-up и откатывается на
  packet-up. ([XTLS discussion 4113 «XHTTP: Beyond REALITY»](https://github.com/XTLS/Xray-core/discussions/4113),
  [Hiddify CDN-гайд](https://hiddify.com/manager/domain-worker-cdn-and-tunneling/How-to-use-Cloudflare-CDN))
- **Клиентская поддержка** [факт]: VLESS+WS за CF — классика, работает во
  всех клиентах (v2rayNG, Hiddify, NekoRay, sing-box) —
  [MoaV clients](https://moav.sh/docs/CLIENTS). XHTTP за CF — новее:
  Hiddify заявляет поддержку XHTTP ([App Store](https://apps.apple.com/pk/app/hiddify-proxy-vpn/id6596777532));
  v2rayNG — только на свежих сборках ядра [предположение — проверить на
  реальных устройствах владельца при приёмке].
- **Reality за CF НЕ работает** [факт, архитектура]: Reality требует прямого
  TCP-соединения клиент→сервер (сервер сам терминирует TLS и принимает
  ClientHello). CF-proxy терминирует TLS на edge и проксирует только
  HTTP(S) на HTTP-порты — Reality-хендшейк за оранжевым облаком не
  доходит до сервера. Также CF не проксирует UDP → Hysteria2 за CF
  невозможен.
- **Текущий XHTTP-inbound 8443 уже «CF-ready» по TLS** [факт по коду]:
  mode=port, публичный 8443, TLS с LE-сертификатом домена, path `/xhttp`
  — форма origin, совместимая с CF Full(strict), но транспорт `xhttp`,
  не `ws`; новый WS-inbound потребовался бы только если выбран WS-вариант.

### Главный риск (не пропустить)

**Включение CF-proxy на записи, которой пользуются существующие каналы,
ломает их.** Если CF-proxy включить на апексе/записи `103-45-247-172`:
DNS станет отдавать IP Cloudflare → Reality-клиенты по доменной ссылке
(адрес = домен, WP-4 прошлого цикла) и Hysteria2-клиенты (`sni=<домен>`)
перестанут доходить до сервера; HTTP-01 certbot для LE-продления пойдёт
через CF edge. Инвариант прошлого цикла «Reality/Hysteria2 не ломаются»
напрямую конфликтует с «проксировать тот же домен». Единственные
безопасные варианты: (а) отдельный **проксируемый поддомен** при зоне в
CF (апекс остаётся grey-cloud, direct-каналы не тронуты) или (б) второй
домен. См. OQ-1.

## 3. Функциональные требования

Маркировка AC: **[локально]** — pytest/команда без root; **[VDS]** — живой asv1.
Сквозной критерий: после любого шага цикла Reality (TCP 443, `phone`),
Hysteria2 (UDP 443, `mob`) и XHTTP-direct (TCP 8443) остаются рабочими —
см. §4 «Не ломать».

### FR-1. CDN-инблэнд VLESS за Cloudflare

**User story:** Как оператор, я хочу добавить inbound VLESS (WS или XHTTP),
доступный через CF-proxy, чтобы клиенты ходили через IP Cloudflare, а не IP
сервера.
**AC:**
- **Given** живой asv1 (Reality 443 / Hysteria2 443 / XHTTP-direct 8443 active)
- **When** команда установки CDN-канала (имя/флаги — SPEC; шаблон:
  `vds xray add-transport cdn --transport ws|xhttp --domain <поддомен>
  --port <p>`)
- **Then** юнит `vds-xray` перезапущен и снова active; Reality/Hysteria2/
  XHTTP-direct части config.json не изменены (diff) **[VDS]**
- **Given** отрендеренный CDN-инблэнд
- **When** юнит-тест рендера
- **Then** валидный JSON, детерминированный; для ws — `network: websocket`
  + `settings.path`; для xhttp — `network: xhttp` + path; приватный
  материал (ключи) не в снапшоте **[локально]**
- **Given** зона НЕ перенесена в CF / поддомен не создан (прекондишн OQ-1)
- **When** запуск установки
- **Then** отказ ДО изменений с `[error]` (DNS поддомена не резолвится в
  CF-IP / зона не в CF — условие проверки определяет SPEC), без traceback
  **[VDS]**
- **Given** установленный CDN-канал
- **When** `ss -tlnp`
- **Then** origin-порт CDN-инблэнда слушается (тот же процесс Xray или
  отдельный — OQ-3); 443/8443 не изменены **[VDS]**

### FR-2. Egress через Cloudflare (главная ценность)

**User story:** Как владелец, я хочу, чтобы трафик CDN-канала шёл через
CF-edge, чтобы цензор видел IP Cloudflare вместо IP сервера.
**AC:**
- **Given** включённый CF-proxy на CDN-поддомене (оранжевое облако)
- **When** `dig +short <поддомен>` с внешней машины
- **Then** ответ — IP из диапазонов Cloudflare (публичный список
  cloudflare.com/ips), НЕ 103.45.247.172 **[VDS/внешняя проверка]**
- **Given** клиент, подключённый по CDN-ссылке
- **When** через туннель `curl https://ifconfig.me` (или эквивалент)
- **Then** exit-IP = 103.45.247.172 (asv1), при этом внешний путь
  клиент→домен идёт через CF (первый hop / `traceroute` / провайдер-независимая
  проверка `whoami.cloudflare`-типа показывает CF-edge) **[VDS]**
- **Given** CF-proxy временно выключен (grey-cloud) на поддомене
- **When** подключение по той же ссылке
- **Then** канал деградирует предсказуемо (соединение идёт direct на origin —
  поведение совпадает с форматом ссылки), состояние не «молча ломается»:
  это задокументировано в выводе `vds xray status`/доке как известное
  свойство **[VDS]** (проверка владельцем)

### FR-3. TLS между CF-edge и origin

**User story:** Как оператор, я хочу настроенный режим TLS CF→origin с
осознанным выбором (Full strict vs Flexible), чтобы канал не был уязвим к
пассивному прослушиванию сегмента CF→origin.
**AC:**
- **Given** выбран Full (strict): origin обязан предъявлять валидный
  сертификат
- **When** рендер CDN-инблэнда
- **Then** TLS-сертификат на origin — валидный для CDN-поддомена (LE от
  существующего certbot-механизма прошлого цикла или self-signed при
  осознанном выборе владельца — OQ-4); права файлов 0600 **[VDS]**
- **Given** выбран Flexible (CF→origin без TLS)
- **When** ревью решения
- **Then** риск-заметка зафиксирована письменно в SPEC/ADR: трафик
  CF→origin идёт открытым HTTP по сети интернет→датацентр, VLESS-пейлоад
  (в т.ч. uuid) наблюдаем на этом участке; выбор — только при явном
  принятии владельцем **[локально]** (ревью артефакта)

### FR-4. CDN share-link

**User story:** Как оператор, я хочу выдавать клиенту vless://-ссылку
CDN-варианта (CF-порт 443, SNI/host = CDN-поддомен, транспортные параметры),
чтобы клиент импортировал её без ручной правки.
**AC:**
- **Given** установленный CDN-канал и добавленный клиент
- **When** команда добавления клиента / выдачи ссылки (интерфейс — SPEC,
  должен появиться в `vds gateway links`-выдаче отдельной записью CDN)
- **Then** ссылка формата `vless://<uuid>@<CDN-поддомен>:443?security=tls&...`
  с транспортными параметрами (для ws: `type=ws&path=...&host=...`; для
  xhttp: `type=xhttp&path=...` + mode), адрес — CDN-поддомен, порт — 443
  (CF edge), НЕ origin-порт **[VDS]** (формат строки — **[локально]**
  юнит-тестом)
- **Given** выведенная ссылка и серверные файлы
- **When** grep
- **Then** приватные ключи (Reality private-key, cert-key) и внутренний
  origin-порт в ссылке отсутствуют; origin-порт не раскрывается цензору
  через ссылку **[локально]**
- **Given** ссылка импортирована в реальный клиент (v2rayNG и/или Hiddify)
- **When** e2e-подключение с внешней машины
- **Then** туннель работает через CF **[VDS]** (частичная приёмка владельцем)

### FR-5. Status и удаление CDN-канала

**User story:** Как оператор, я хочу видеть CDN-канал в статусе и уметь
удалить его без влияния на остальные, чтобы управлять каналом как
самостоятельной сущностью.
**AC:**
- **Given** установленный CDN-канал
- **When** `vds xray status` / `vds gateway status`
- **Then** CDN-канал показан отдельной записью: поддомен, транспорт
  (ws/xhttp), origin-порт, признак CF-proxy (насколько верифицируемо —
  DNS-чек), дата/сертификат **[VDS]** (парсинг — **[локально]** тесты на моках)
- **Given** команда удаления CDN-канала (dry-run по умолчанию + `--apply`)
- **When** удаление
- **Then** CDN-инблэнд и CDN-клиенты удалены из config.json/store; Reality,
  Hysteria2, XHTTP-direct не затронуты; повторный запуск после удаления —
  идемпотентный отказ «канал уже удалён» **[VDS]**

## 4. Не ломать (сквозной инвариант приёмки)

Выполняется после полного цикла и по промежуточным гейтам, на живом asv1:

| Инвариант | Проверка |
|---|---|
| Reality active, TCP 443, конфиг Reality-части байт-в-байт прежний | `systemctl is-active vds-xray`; `ss -tlnp`; diff config.json **[VDS]** |
| Клиент `phone` (Reality, доменная ссылка) работает e2e — **включая случай, если зона уже перенесена в CF: апекс-запись обязана остаться grey-cloud** | подключение по старой ссылке **[VDS]** |
| Hysteria2 active, UDP 443, клиент `mob` работает e2e | `systemctl is-active vds-hysteria2`; `ss -ulnp`; подключение **[VDS]** |
| XHTTP-direct (8443, path `/xhttp`) работает e2e без изменений | подключение по прежней XHTTP-ссылке **[VDS]** |
| Probe-resistance Reality не деградировал | curl с чужим SNI на 443 → ответ сайта-маски **[VDS]** |
| LE-продление certbot не пострадало от переноса зоны (если было) | `certbot renew --dry-run` или статус таймера; продление проходит **[VDS]** |
| Секреты не в логах/journal/выводе | grep **[VDS]** |

Определение Breaking: любое из перечисленного не выполняется после цикла →
цикл НЕ принят, откат по плану (NFR), блокер G4. Прямое следствие: **вариант
«CF-proxy на апексе/записи 103-45-247-172» противоречит инварианту и может
быть выбран только если владелец явно отменит часть инварианта** (см. OQ-1).

## 6. Границы

**Входит:**
- CDN-инблэнд VLESS (ws и/или xhttp — OQ-2) за CF-proxy: установка, конфиг,
  клиент, share-link, status, remove.
- Требования к DNS-подготовке как прекондишн (перенос зоны в CF / выбор
  поддомена / второй домен — решение OQ-1; сами DNS-действия — ручной шаг
  владельца либо опциональная автоматизация OQ-5).
- TLS CF→origin: выбор режима (OQ-4) и обеспечение origin-сертификата.
- Частичная приёмка на живом asv1 (AC [VDS] + §4).

**Не входит (явно):**
- Изменение/замена существующих Reality (443 direct), Hysteria2 (443 UDP),
  XHTTP-direct (8443) — CDN-канал дополнительный, не замена.
- CF за Hysteria2 или Reality (технически невозможно: CF не проксирует UDP,
  Reality требует прямого TLS) — зафиксировано, не оспаривается.
- Cloudflare Workers/tunnels (cloudflared) как альтернативный транспорт —
  отдельный сценарий, в этот цикл не входит.
- Покупка/оплата второго домена и регистрация; платные планы CF.
- Автоматизация панели CF (включение оранжевого облака скриптом) — только
  если архитектор выберет в OQ-5 и владелец предоставит API-токен; иначе
  ручной шаг в панели CF с чеклистом.
- Watchdog/метрики CDN-канала, failover-переключение direct↔CDN на клиенте
  (двойные ссылки с автовыбором) — будущий сценарий.
- AmneziaWG-цикл (идёт параллельно, G3) — не пересекается.

| E9 | Origin-порт занят (конфликт с будущими сервисами) | проверка `ss -tlnp` до изменений, отказ с внятной ошибкой | FR-1 |
| E10 | CF edge недоступен/блокирован с клиентской сети (CF сам под фильтром — известный сценарий) | канал просто не работает; direct-каналы не зависят от CF; задокументировать в доке как известное ограничение CDN-канала | FR-2 |
| E11 | LE-продление CDN-поддомена при оранжевом облаке | HTTP-01 идёт через CF edge — должно проходить; при отказе — запасной путь (grey-cloud на время продления / DNS-01 при наличии токена) — SPEC | FR-3 |
| E12 | Откат цикла (remove CDN) | direct-каналы не затронуты; при переносе зоны — план возврата NS | NFR, §4 |

## 8. Открытые вопросы (архитектору, G2)

**Блокирующих G1 нет** — скоуп утверждён владельцем (G0, 2026-11-10);
«главный риск» зафиксирован как инвариант-блокер приёмки, а не открытый вопрос.

- [ ] **OQ-1 (архитектор + воля владельца на исполнении):** CF-proxy на том
  же домене vs отдельный поддомен vs второй домен. Установленный факт: зона
  сейчас в DNS регистратора — **любой** CF-proxy требует переноса зоны в
  Cloudflare (смена NS). Безопасная конфигурация: апекс-запись остаётся
  grey-cloud (direct), для CDN заводится отдельная proxied-запись
  (например `cdn.103-45-247-172.eu-cloud-xip.com`). Проксировать апекс/
  запись 103-45-247-172 нельзя без ломки Reality/Hysteria2 (§4) — либо
  явная отмена части инварианта владельцем, либо этот вариант запрещён.
  Перенос зоны — ручное действие владельца (NS у регистратора); побочный
  эффект: после переноса все прочие записи зоны обслуживает CF.
- [ ] **OQ-2 (архитектор):** WS vs XHTTP за CF. WS — 100% клиентская
  поддержка, проверенная классика; XHTTP mode=auto — современнее, но CF
  free исторически проблемен со stream-up, клиентская поддержка свежая.
  Возможен и оба (вне этого цикла — если архитектор решит добавить только
  один, второй зафиксировать как future).
- [ ] **OQ-3 (архитектор):** origin-порт и инблэнд: отдельный inbound
  (CF→origin на своём порту) vs совместное использование текущего
  8443 XHTTP-inbound (он уже public+TLS+LE — но транспорт xhttp, не ws,
  и mode/path рассчитаны на direct-сценарий). Требование-критерий одно:
  §4 инвариант, XHTTP-direct-ссылки клиентов не меняются.
- [ ] **OQ-4 (архитектор/владелец):** Full (strict) с LE-сертификатом
  поддомена vs Flexible. Риск-заметка Flexible — в FR-3; по умолчанию
  рекомендация Full strict.
- [ ] **OQ-5 (архитектор):** CF API-автоматизация (включение proxy,
  создание записи скриптом через CF API) или ручной шаг в панели CF с
  чеклистом. API-токен = новый секрет (NFR); ручной путь — проще и без
  новых секретов.
