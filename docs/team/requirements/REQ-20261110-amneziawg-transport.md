# REQ-20261110-amneziawg-transport

## Мета
- **Источник:** скоуп G0 intake, утверждён владельцем в чате 2026-11-10. Четвёртый
  транспорт **AmneziaWG** (обфусцированный WireGuard) — независимый UDP-канал,
  не-QUIC, фаза 4 roadmap. Три направления: (1) серверный модуль `src/amneziawg/`,
  (2) клиентская сторона (vpn-manager / выдача .conf) — вариантно по OQ-2,
  (3) sudo-гвард `_check_vpn_active` (.zshrc, ubuntuInstaller) — минорный FR.
  Контекст: [CENSORSHIP-ROADMAP.md](../../CENSORSHIP-ROADMAP.md) (фаза 4),
  [VPN-PROTOCOLS.md](../../VPN-PROTOCOLS.md) §1 (второй эшелон),
  [DEPLOY.md](../../DEPLOY.md),
  [REQ-20261109-domain-xhttp-acme.md](REQ-20261109-domain-xhttp-acme.md) (формат,
  фактическое состояние asv1).
- **Автор:** аналитик (vds-analyst)
- **Дата:** 2026-11-10
- **Статус:** ready (G1)

## 1. Контекст

Три транспорта уже работают на живом asv1 (ACCEPT-20261109 PASS): Xray VLESS
Reality (TCP 443, клиент `phone`), Hysteria2 (UDP 443, LE-сертификат, клиент
`mob`), VLESS XHTTP (TCP 8443, домен). Водитель фазы 4 roadmap: «UDP-резерв
на случай, когда Reality/XHTTP детектированы или TCP 443 резанут»
(CENSORSHIP-ROADMAP.md §стратегия, фаза 4, P1).

AmneziaWG — проверенные факты (RTFM 2026-11-10):

- **[факт]** AmneziaWG — форк WireGuard (userspace-реализация `amneziawg-go`,
  Go-форк wireguard-go, MIT) с обфускацией: «мусорные» пакеты (junk), паддинг,
  подмена заголовков. Репо: github.com/amnezia-vpn/amneziawg-go.
- **[факт]** На репо `amneziawg-go` **нет ни одного GitHub release** (страница
  Releases пуста, проверено 2026-11-10) — готовых prebuilt-бинарей из релизов
  нет; установка — сборка из исходников (`make`, нужен Go-тулчейн) или пакеты
  дистрибутивов (существование/качество Ubuntu 24.04-пакетов `amneziawg`,
  `amneziawg-tools`, `amneziawg-dkms` — **[предположение]**, подтвердить в SPEC).
- **[факт]** Конфигурация — WG-совместимые секции (`Interface`/`Peer`) +
  обфускационные параметры: `Jc` (число junk-пакетов, рекомендовано 4–12),
  `Jmin`/`Jmax` (диапазон размеров junk, Jmin ≤ Jmax, Jmax < MTU),
  `S1`–`S4` (паддинг handshake init/response/cookie/transport; в AWG 3+ требование
  ≥12 для header protection), `H1`–`H4` (подмена uint32-полей заголовков; в
  AWG 2.0+ — **диапазоны** `x-y`, не фиксированные значения). Источники:
  README amneziawg-go, docs.amnezia.org, docs.gl-inet.com.
- **[факт]** Серверные параметры обфускации должны **совпадать** на клиенте и
  сервере, кроме `Jc`/`Jmin`/`Jmax` (vpnsmith.com, gl-inet docs).
- **[факт]** Инструменты: `amneziawg-tools` дают `awg` (в т.ч. `awg genkey`,
  `awg pubkey`) и `awg-quick` (форк wg-quick); запуск userspace-интерфейса —
  `amneziawg-go <iface>`; для kernel-модуля — отдельный DKMS-модуль
  (**[предположение]** вариант за архитектором).
- **[факт]** Клиент AmneziaVPN (приложение) импортирует .conf-профиль AWG.
- **[факт — код]** WG-класс работает **tun-интерфейсом и требует root**, а не
  socks-портом: vpn-manager (`~/Dev/ubuntuInstaller/scripts/vpn-manager`,
  `vpnm/runners.py`) — user-level socks-раннер (порты 2080/2083), гвард
  `~/.zshrc:_check_vpn_active` (строка 448) сейчас проверяет ZeroTier
  (`zt*`), WireGuard (`wg*` по `wg show` / `ip link`) и vpn-manager socks —
  AWG-интерфейс там не покрыт. Это ключевое архитектурное отличие от трёх
  существующих транспортов, честно учтено в FR-6.

Существующий `src/wireguard/install.py` (классический WireGuard, отдельный
модуль) — вне скоупа, не мигрируется.

## 3. Функциональные требования

Маркировка AC: **[локально]** — pytest/команда без root/сети; **[VDS]** — живой
asv1. Сквозной критерий для всех FR: **после любого шага этого цикла Reality
(TCP 443, `phone`), Hysteria2 (UDP 443, `mob`) и XHTTP (TCP 8443) остаются
рабочими** — см. §4 «Не ломать».

### FR-1. Установка AmneziaWG-сервера (`src/amneziawg/`, `vds amneziawg install`)

**User story:** Как оператор, я хочу установить AmneziaWG-сервер одной командой
(бинарь/tools, systemd-юнит, серверный .conf с приватным ключом и обфускационными
параметрами, UDP-порт), чтобы получить независимый UDP-резерв рядом с работающими
транспортами.
**AC:**
- **Given** живой asv1 с active Reality/Hysteria2/XHTTP
- **When** `vds amneziawg install` (интерфейс и флаги — SPEC)
- **Then** юнит AmneziaWG (имя — SPEC, шаблон в `systemd/`) создан и active;
  `ss -ulnp` показывает слушающий AWG UDP-порт; UDP 443 по-прежнему занят
  **только** процессом Hysteria2; TCP 443/8443 не изменены **[VDS]**
- **Given** рендер серверного .conf из параметров (ключи, порт, обфускация)
- **When** юнит-тест рендера (снапшот)
- **Then** результат — валидный .conf: WG-секция (`ListenPort`, `PrivateKey`,
  `Address`, `SaveConfig=false`) + обфускационные параметры `Jc`/`Jmin`/`Jmax`/
  `S1`–`S4`/`H1`–`H4`; параметры детерминированы при фиксированном seed, при
  повторной установке (новая генерация) значения обфускации **отличаются**
  (уникальность на установку — acceptance roadmap); эталон-снапшот не содержит
  реальных приватных ключей **[локально]**
- **Given** сгенерированные параметры `H1`–`H4`, `Jmin`/`Jmax`
- **When** валидация генератора (unit-тест на ограничения)
- **Then** `Jmin <= Jmax`, `Jmax < MTU-запас` (конкретный запас — SPEC),
  `H1..H4` в допустимом формате диапазона и попарно различимы; нарушение
  ограничений — ошибка генерации, а не тихий невалидный конфиг **[локально]**
- **Given** установка на asv1, github.com недоступен (RKN-DPI)
- **When** `VDS_GITHUB_MIRROR` задан
- **Then** установка проходит (конвенция gh-proxy-префикса, как у Xray/
  Hysteria2-инсталляторов); без mirror — поведение как у существующих
  инсталляторов **[VDS]** (конфигурация mirror — **[локально]** тест на моках)
- **Given** повторный запуск `install`
- **When** AWG уже установлен и active
- **Then** идемпотентно: exit 0, «уже установлен», ключи/порт/пиры не
  перегенерированы молча; существующие клиенты AWG продолжают работать
  **[VDS]**

### FR-2. Добавление клиента (`vds amneziawg add-client NAME`)

**User story:** Как оператор, я хочу добавить клиента и получить готовый
**клиентский .conf-файл** для импорта в AmneziaVPN (с адресом/портом сервера,
публичным ключом сервера, приватным ключом клиента, PSK и копией обфускационных
параметров), чтобы клиент импортировал профиль без ручной правки.
**AC:**
- **Given** установленный AWG
- **When** `vds amneziawg add-client mob-awg` (пример)
- **Then** peer создан в серверном конфиге (public-key клиента), клиент
  сохранён в store (`protocol="amneziawg"`, имя, порт; секреты только в
  state.json 0600 — см. NFR); на диске создан клиентский .conf (путь — SPEC,
  рекомендация: `$INSTALL_DIR/gateway/clients/` или аналог — SPEC) с правами
  0600 **[VDS]**
- **Given** клиентский .conf
- **When** валидация содержимого (юнит-тест рендера по фикстурам)
- **Then** содержит `[Interface]` (PrivateKey клиента, Address клиента,
  DNS — опционально/SPEC), `[Peer]` (PublicKey сервера, PresharedKey,
  Endpoint = `<адрес>:<порт>`, AllowedIPs — значение по выбору SPEC
  (0.0.0.0/0 или раздельно v4/v6), PersistentKeepalive) **и те же**
  обфускационные параметры, что у сервера, кроме `Jc`/`Jmin`/`Jmax`;
  импорт фикстурного .conf в AmneziaVPN-формат не вызывает ошибок парсинга
  формата (**[локально]** — структурная проверка; полный импорт в приложение —
  **[VDS]**, частичная приёмка владельцем)
- **Given** клиент с тем же именем
- **When** повторный `add-client mob-awg`
- **Then** ошибка `[error]` «клиент уже существует», exit != 0, ничего не
  изменено (паттерн существующих add-client) **[локально]** (unit-тест store),
  подтверждение **[VDS]**
- **Given** вывод команды и journal
- **When** grep по приватным ключам клиента/сервера и PSK
- **Then** приватный материал отсутствует в stdout/journal (в выводе — только
  путь к файлу); сам .conf пользователь забирает/пересылает сам **[VDS]**

### FR-3. Статус (`vds amneziawg status`)

**User story:** Как оператор, я хочу видеть статус AWG (юнит, порт, число
активных пиров, последние handshake), чтобы диагностировать туннель без ручного
`systemctl`/`awg show`.
**AC:**
- **Given** установленный AWG
- **When** `vds amneziawg status`
- **Then** показан: `systemctl is-active`, слушающий UDP-порт (`ss -ulnp`),
  peer-статистика (`awg show`-эквивалент: имена клиентов, последние handshake,
  transfer-байты — маскировано, ключи не выводятся); exit 0 **[VDS]**
- **Given** journal-фрагмент статуса
- **When** grep
- **Then** приватные ключи/PSK не присутствуют (маскирование, как у
  `xray status`/`hysteria2 status`) **[локально]** (тест на моках) + **[VDS]**

### FR-4. Удаление (`vds amneziawg remove [--apply]`)

**User story:** Как оператор, я хочу удалить AWG-транспорт (или клиента)
с dry-run по умолчанию и бэкапом, чтобы откат был безопасным.
**AC:**
- **Given** установленный AWG
- **When** `vds amneziawg remove` без `--apply`
- **Then** dry-run: печатается план (юнит, конфиг, бинарь/tools, клиенты
  из store), ничего не удалено, exit 0 **[локально]** (unit-тест) +
  подтверждение **[VDS]**
- **When** `vds amneziawg remove --apply`
- **Then** юнит остановлен/disabled, конфиг и клиентские .conf удалены (или
  перемещены в бэкап — SPEC), клиенты AWG удалены из store; Reality/XHTTP/
  Hysteria2 не затронуты; порт освобождён **[VDS]**
- **Given** `remove --apply` при неустановленном AWG
- **When** запуск
- **Then** идемпотентно: «не установлен», exit 0, без traceback **[VDS]**

### FR-5. Интеграция с gateway store / links

**User story:** Как оператор, я хочу, чтобы AWG-клиенты были видны в
`vds gateway status` (и с минимальным выводом в `gateway links`), чтобы вся
панель протоколов была единой.
**AC:**
- **Given** добавленный AWG-клиент
- **When** `vds gateway status`
- **Then** клиент присутствует с `protocol="amneziawg"`; структура state.json
  (version=1, `ClientProfile.extra` для AWG-специфики) не ломает
  существующих клиентов `phone`/`mob` — `pytest -q` на store зелёный,
  реальные клиенты читаются **[локально]**
- **Given** WG-класс не имеет share-link-формата URI
- **When** `vds gateway links`
- **Then** поведение для существующих протоколов (xray/hysteria2) не изменилось;
  для AWG выводится либо путь к .conf, либо помеченная строка-плейсхолдер
  (точная форма — SPEC; критерий: отсутствие ошибки/traceback и отсутствие
  секретов в выводе) **[локально]** (unit-тест) + **[VDS]**

### FR-6. Клиентская сторона (vpn-manager) — ВАРИАНТНО, решение по OQ-2 в SPEC

> Архитектурное отличие, зафиксированное владельцем: WG-класс поднимает
> tun-интерфейс и требует root; vpn-manager сейчас — user-level socks-раннер
> (факт по коду `vpnm/runners.py`, `~/.zshrc:_check_vpn_active`).
> Владелец предложил три варианта (a/b/c); REQ формулирует их вариантно,
> SPEC выбирает ровно один и оформляет ADR.

#### FR-6a. Вариант (a): root-mode runner в vpn-manager
**AC (если выбран):**
- **Given** AWG-профиль (.conf) на локальной машине
- **When** команда vpn-manager запуска AWG-туннеля
- **Then** туннель поднимается через root-путь (sudo/политика — SPEC:
  systemd system-юнит, `sudoers`-правило или `pkexec`), интерфейс виден в
  `ip link`, egress через AWG подтверждён probe **[VDS-клиент]** (приёмка
  на локальной машине с доступом к asv1)
- **Given** root недоступен (нет sudo-пароля)
- **When** запуск
- **Then** внятная ошибка до изменений, инструкция как получить root-права,
  без partial-состояния интерфейса **[локально]**

#### FR-6b. Вариант (b): vpn-manager только хранит/раздаёт .conf + инструкция для AmneziaVPN
**AC (если выбран):**
- **Given** AWG-профиль, выданный сервером
- **When** импорт профиля в vpn-manager (`vpnm` команды — SPEC)
- **Then** профиль сохранён в хранилище профилей с правами 0600, в списке
  `vpnm` виден; runner-компонент для AWG **не** запускается (нет socks) —
  это честно отражено в выводе/доке («подключение через AmneziaVPN-приложение,
  шаги: …») **[локально]**
- **Given** удаление профиля
- **When** команда удаления
- **Then** .conf удалён, без остатков приватного материала в temp **[локально]**

#### FR-6c. Вариант (c): гибрид (хранение + опциональный root-раннер)
**AC (если выбран):** FR-6b целиком + FR-6a как opt-in (флаг/подкоманда);
по умолчанию — вариант (b); запуск root-раннера без явного opt-in невозможен.
**[локально]** (unit-тесты на дефолт) + **[VDS-клиент]** для opt-in-пути.

### FR-7 (минор). sudo-гвард `_check_vpn_active` (ubuntuInstaller, .zshrc)

**User story:** Как локальный пользователь, я хочу, чтобы антивирус-гвард
признал AWG-туннель как активный VPN и не блокировал запуск Antigravity,
когда AWG поднят.
**AC:**
- **Given** AWG-туннель активен (интерфейс — имя определяется решением
  FR-6/SPEC: `wg*` уже покрыто; для userspace amneziawg-go имя может быть
  произвольным, напр. `awg0` — паттерн `awg*` добавить)
- **When** `_check_vpn_active`
- **Then** гвард возвращает 0 (VPN признан активным), без изменений логики
  ZeroTier/vpn-manager-веток **[локально]** (проверка функции в изолированном
  shell на mock-окружении/фальшивом интерфейсе в netns или dummy-link)
- **Given** ни один VPN не активен
- **When** `_check_vpn_active`
- **Then** поведение без изменений (блокировка, как сейчас) **[локально]**

## 4. Не ломать (сквозной инвариант приёмки)

Отдельная секция приёмки на живом asv1, выполняется ПОСЛЕ полного цикла и по
промежуточным гейтам:

| Инвариант | Проверка |
|---|---|
| Reality active, TCP 443 слушается, конфиг Reality-части не изменён | `systemctl is-active vds-xray`; `ss -tlnp`; diff `config.json` **[VDS]** |
| XHTTP active, TCP 8443 слушается, LE-сертификат не тронут | `ss -tlnp`; `openssl x509 -enddate` **[VDS]** |
| Hysteria2 active, UDP 443 слушается, LE-сертификат/автопродление не тронуты | `systemctl is-active vds-hysteria2`; `ss -ulnp`; timer acme **[VDS]** |
| Клиенты `phone` (Reality) и `mob` (Hysteria2) работают e2e по старым ссылкам | подключение с внешней машины **[VDS]** |
| state.json: существующие клиенты не потеряны/не изменены; версия формата совместима | diff state.json (допустимо только добавление AWG-записей); чтение через `gateway status` **[VDS]** |
| `pytest -q` зелёный после всех изменений | локальный прогон **[локально]** |
| Секреты: AWG-ключи, PSK, uuid/пароли существующих клиентов не в логах/journal/выводе/git | grep **[VDS]** + **[локально]** |
| `src/wireguard/` (классический WG) не изменён | `git status --short` не содержит `src/wireguard/` **[локально]** |

**Определение Breaking:** любое из перечисленного не выполняется → цикл НЕ
принят, откат по плану (NFR), блокер G4.

## 5. Нефункциональные требования

| Категория | Требование | Как проверить |
|---|---|---|
| Безопасность — секреты | приватный ключ сервера, приватные ключи клиентов, PSK — только в конфигах (0600) и state.json; не в логах, journal, stdout, git, клиентском выводе | grep вывода/journal [VDS]; тесты на моках [локально] |
| Безопасность — права | серверный .conf, клиентские .conf, обновлённый state.json — 0600 (клиентский .conf выдаётся оператору — права в точке создания 0600) | `stat` [VDS]; тесты [локально] |
| Безопасность — обфускация | параметры Jc/Jmin/Jmax/S1–S4/H1–H4 уникальны на установку (не дефолтные константы); серверные параметры совпадают с клиентскими (кроме Jc/Jmin/Jmax) | тест генератора [локально]; diff сервер/клиент конфигов [VDS] |
| Идемпотентность | install/add-client повторно — безопасны; ключи и пииры не перегенерируются молча | двойной прогон каждого шага [VDS] |
| Блокировки | мутирующие операции под `core.lock.FileLock` | code review |
| Shell | только `run_list([...])` через `core/shell.py`, без `shell=True`; `docker_exec` не применим | grep/review |
| Root-only | все AWG-команды сервера без root — читаемая ошибка до изменений, без traceback | прогон без sudo [VDS] |
| Mirror | загрузка исходников/бинарей AWG уважает `VDS_GITHUB_MIRROR` (ADR-001) | установка при режущем github [VDS] |
| Откат | план отката: восстановление серверного .conf из бэкапа, disable/remove юнита, откат state.json из бэкапа; задокументирован в SPEC | ревью SPEC; репетиция remove [VDS] |
| Бэкап перед мутацией | серверный .conf и state.json бэкапируются перед изменением | вывод команды [VDS] |
| Downtime | единственный допустимый downtime — рестарт юнита AmneziaWG (или awg-интерфейса) при add-client/remove клиента; остальные протоколы не перезапускаются | статус после шага [VDS] |
| Локальная тестируемость | `pytest -q` зелёный без root/сети/docker (генераторы конфигов, store, mirror-логика — на моках) | локальный прогон |
| Вывод | rich-теги через `core.logger`; конфликты портов проверяются `ss -ulnp` перед изменениями | code review [локально] |

## 6. Границы

**Входит:**
- Сервер: `src/amneziawg/` по образцу `src/hysteria2/` — install / add-client /
  status / remove, серверный .conf с обфускацией, systemd-юнит из шаблона
  `systemd/`, UDP-порт без конфликта с существующими.
- Выдача клиентских .conf-файлов для AmneziaVPN.
- Клиентская сторона vpn-manager — вариантно (ровно один из a/b/c, выбор в SPEC
  + ADR).
- Минорный FR-7: паттерн AWG-интерфейса в `_check_vpn_active` (.zshrc,
  ubuntuInstaller — отдельный репозиторий, изменение синхронизируется с ним).
- Интеграция store (`protocol="amneziawg"`), `gateway status`/`links`.
- Приёмка на живом asv1 по чеклисту (AC [VDS] + §4).

**Не входит (явно):**
- AmneziaVPN GUI-обвязка: сборка/установка AmneziaVPN-приложения, автозапуск
  его сервиса, десктоп-интеграция — клиент импортирует .conf штатными
  средствами приложения.
- Мультихоп / цепочки (AWG поверх XHTTP и т.п.), split-tunneling-редакторы,
  роутинг-политики в клиенте.
- Миграция существующего классического WireGuard (`src/wireguard/`) на AWG и
  совместное использование их конфигов.
- QR-коды для раздачи .conf (упомянуты в roadmap фазы 4, в скоупе владельца
  2026-11-10 отсутствуют; возвращается в roadmap как отдельный минорный WP).
- NAT/firewall-тюнинг за пределами открытия AWG-порта (UFW-политика — как для
  существующих портов; глобальный hardening — фаза 6).
- Подписки/hub/reconcile (фаза 5), dashboard-карточки AWG (отдельный WP, если
  архитектор включит — по умолчанию нет).
- Multi-AWG-инстансы на одном сервере (один интерфейс, один порт — если не
  решит SPEC явно).

## 8. Открытые вопросы

**Блокирующих G1 нет.** Скоуп утверждён владельцем (G0, чат 2026-11-10);
все оставшиеся — архитектурные решения, которые по определению не аналитик
(правило «не предполагай молча» соблюдено: каждый оформлен как OQ с трассировкой).

Вопросы архитектору (решаются в SPEC, G2):
- [ ] **OQ-1 (архитектор):** UDP-порт AmneziaWG. Критерий из REQ: не конфликтовать
  с Hysteria2 UDP 443 и существующими слушателями; конкретное значение/политика
  подбора (фиксированный, напр. 51820 с проверкой, или динамический выбор
  свободного) — решение SPEC + ADR.
- [ ] **OQ-2 (архитектор):** клиентский режим a/b/c (FR-6). Ключевой вводный
  факт: WG-класс = tun + root, vpn-manager — user-level socks. Требование-критерий
  одно: клиент получает рабочий AWG-туннель; выбор механизма + ADR за архитектором.
- [ ] **OQ-3 (архитектор):** источник бинаря AWG. Факт: в amneziawg-go **нет
  GitHub releases** — варианты: сборка из исходников (Go-тулчейн на сервере),
  пакеты Ubuntu/PPA, prebuilt из другого источника; pin версии + контроль
  целостности — как у Xray/Hysteria2 (пин + SHA256). Существование пригодных
  Ubuntu 24.04-пакетов — [предположение], подтвердить в SPEC.
- [ ] OQ-4 (архитектор/владелец): линия версий AWG (1.x vs 2.0/3+: S3/S4,
  header-диапазоны H1–H4, HeaderProtectionKey). Влияет на совместимость с
  версией AmneziaVPN-приложения у владельца — уточнить у владельца целевое
  клиентское приложение/версию; параметр-набор конфига — следствие.
- [ ] OQ-5 (допущение): kernel-модуль (amneziawg-dkms) vs userspace amneziawg-go
  — выбор механизма интерфейса за архитектором; REQ не фиксирует.
- [ ] OQ-6 (допущение): PSK (PresharedKey) — включать по умолчанию в клиентские
  .conf или опционально; влияние на совместимость AmneziaVPN — SPEC.
