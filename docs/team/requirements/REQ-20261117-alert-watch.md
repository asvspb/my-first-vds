# REQ-20261117-alert-watch

## Мета
- **Источник:** [docs/research/notifications-and-resilience-2026-11-17.md](../../research/notifications-and-resilience-2026-11-17.md) (snapshot диалога с внешней моделью, сверен с кодом)
- **Автор:** аналитик (по поручению владельца)
- **Дата:** 2026-11-17
- **Статус:** ready (G1) — с блокирующими OQ, вынесенными в §7; решения по каналу доставки приняты (FR-2: оба канала, конфигурируемо)

## 1. Контекст

Сейчас узел **видит** активное зондирование и умеет реагировать, но **не умеет сообщать**:

- `vds gateway probe-watch` пишет threat-level (`quiet/elevated/high`) и вердикты окна
  (`RU-PROBE-SUSPECT`/`PROBE-BURST`) в `/var/lib/vds/probe-watch.json` и journal;
- `--auto-lockdown` (по умолчанию **выключен**) при level `high` включает `lock-443`;
- `vds gateway healthcheck` каждые 5 минут проверяет юниты/сертификаты и может
  rate-limited рестартнуть упавший юнит;
- `vds relay status --json` отдаёт `exit_handshake_age_sec`;
- уведомлений наружу (email/Telegram) **нет ни на одном узле** (подтверждено grep).

Владелец узнаёт о блокировке только когда ноутбук рядом и `vpn guard` показал
`notify-send`. Если ноутбук выключен — блокировка (трансграничный ТСПУ на плече
relay→exit, недоступность релея, волна проб) остаётся незамеченной.

Цель: владелец получает пуш/письмо за минуту о (а) волне Active Probing на exit-узле,
(б) пропаже пульса плеча relay→exit, (в) недоступности релея; и не получает ложных
алертов, а также отличает «всё хорошо» от «сторож умер» (heartbeat).

## 2. Пользователи и сценарии

| Роль | Сценарий | Частота |
|---|---|---|
| `vds-owner` | Получает пуш в Telegram/письмо при угрозе; по heartbeat знает, что сторож жив | при инциденте; heartbeat 1/сутки |
| `vds-orchestrator` / кодер | Ставит/снимает сторож на exit-узле одной идемпотентной командой | при деплое/изменении |
| `vds-debugger` | По `journalctl` и `vds alert status` разбирает, что и когда отправлялось | при разборе |

## 3. Функциональные требования

### FR-1. Сторож на exit-узле (основной)
**User story:** Как владелец, я хочу, чтобы зарубежный exit-узел сам уведомлял меня об
угрозе, чтобы узнавать о блокировке без включённого ноутбука.

**Состав проверок (каждая — отдельный источник сигнала):**
1. **threat-level** из `/var/lib/vds/probe-watch.json`: переход `quiet → elevated/high`
   (и обратно `high → quiet` — «отпустило», отдельным типом сообщения).
2. **Пульс плеча relay→exit**: возраст `latest_handshake` пира-релея на стороне
   AWG-сервера exit-узла. Порог по умолчанию 300 с (5 мин = 12× keepalive 25),
   конфигурируемый. Сигнал валиден **только вместе с** (3): «handshake мёртв, но релей
   пингуется» = блокировка плеча; «handshake мёртв и релей недоступен» = релей лёг.
3. **Доступность релея** с exit-узла: TCP-коннект до `endpoint:port` из `state.json`
   (relay), плюс, при наличии, ICMP. Результат — двухсторонняя классификация (см. §6).
4. **Активный `lock-443`** (если включён auto-lockdown): факт лока и его TTL —
   уведомление «защита включена, 443/tcp закрыт на N ч».

**AC (Given/When/Then):**
- **Given** сторож установлен, level `quiet`; **When** probe-watch переходит в `elevated`;
  **Then** в канал доставки уходит одно сообщение с уровнем, причиной (`threat_reason`),
  периодом; повторные тики в окне подавления новых сообщений не шлют.
- **Given** handshake пира-релея старше порога, релей пингуется; **When** тик сторожа;
  **Then** сообщение «трансграничный ТСПУ: канал relay→exit мёртв, релей жив».
- **Given** handshake свежий; **When** любой тик; **Then** сообщений о пульсе нет
  (проверка ложных срабатываний на 15-мин прогоне).

### FR-2. Каналы доставки: Telegram и SMTP (оба, конфигурируемо)
**User story:** Как владелец, я хочу получать уведомления в Telegram и/или на почту,
чтобы выбрать удобный канал и иметь резервный.

- Оба канала реализуются на **stdlib** (`urllib.request` для Telegram Bot API,
  `smtplib`+`email` для SMTP). Никаких новых зависимостей.
- Секреты — `/etc/vds/alert.env` (0600, атомарная запись): `TG_BOT_TOKEN`,
  `TG_CHAT_ID`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`,
  `SMTP_TO`, опционально `ALERT_CHANNELS=tg,smtp`.
- Канал(ы) включаются наличием конфигурации; отсутствие конфигурации = канал выключен
  (без ошибки установки, но с предупреждением).
- Значения секретов **не** попадают в лог/journal/`--help`/вывод команд/тесты.
- SMTP: `SMTP_SSL` по умолчанию (465), таймаут; App Password, не основной пароль.
- Отправка — с таймаутом и ретраем по backoff (см. FR-6).

**AC:**
- **Given** заданы оба канала; **When** тестовое сообщение; **Then** приходит и пуш, и
  письмо; в journal — одно `ALERT-SENT` на канал.
- **Given** секретов нет; **When** `--help`/`status`; **Then** ни одного значения секрета
  в выводе; тест `grep` по выводу пуст.
- **Given** канал недоступен; **When** отправка; **Then** `ALERT-FAILED` + повтор по
  backoff, юнит не падает.

### FR-3. Состояние, дедупликация, анти-флаппинг
- Состояние сторожа — `/var/lib/vds/alert-state.json` (0600, атомарно, `FileLock`):
  последний уровень/тип по каждому источнику, время последней отправки, cooldown,
  счётчик неудач.
- Окно подавления по умолчанию: 30 мин на один и тот же тип события; изменение уровня
  вверх (`elevated→high`) проходит **всегда** (эскалация не подавляется).
- Лимит: не более N сообщений в час (по умолчанию 6), при превышении — сводка вместо
  потока.
- Состояние переживает рестарт юнита; битый JSON не валит сторож (сброс в пустое
  состояние + `ALERT-FAILED`-запись «state corrupted»).

**AC:** повторный тик с тем же уровнем → сообщений нет; `quiet→elevated→high` → два
сообщения (эскалация проходит); битый `alert-state.json` → сторож работает, пишет
предупреждение, состояние пересоздано.

### FR-4. Heartbeat (dead-man switch)
- Раз в сутки (по умолчанию 24 ч, конфигурируемо) — короткое «жив, уровень N, лок нет/
  есть, handshake N с» в тот же канал.
- **Отсутствие heartbeat = сигнал владельцу проверить узел.** Требование: heartbeat
  не подавляется cooldown'ом.
- Heartbeat может быть выключен конфигом (`--heartbeat off`), но по умолчанию **включён**.

**AC:** в течение суток приходит ровно одно heartbeat-сообщение; при `--heartbeat off` —
ни одного.

### FR-5. CLI `vds alert` (install / remove / test / status)
- `vds alert install [--apply] [--channel tg,smtp] [--interval 2m] [--handshake-threshold 300s]
  [--heartbeat 24h]` — dry-run по умолчанию: печатает, какие файлы/юниты создаст, какие
  секреты ожидает; `--apply` требует root.
- `vds alert remove [--apply]` — снимает юнит, **не** удаляет `alert.env` без `--purge`.
- `vds alert test` — отправить тестовое сообщение по всем включённым каналам (без записи
  в state/cooldown).
- `vds alert status [--json]` — конфиг (без секретов), состояние юнита, последние
  отправки, cooldown, «какие проверки активны / слепы» (по аналогии с
  `probe-watch explain`).
- Идемпотентность: повторный `install` не дублирует юнит/таймер, не перезаписывает
  `alert.env` без `--force`.

**AC:** два подряд `install --apply` → одна пара юнитов, `alert.env` не изменён;
`remove --apply` → юниты сняты, `alert.env` на месте; `--purge` → удалён.

### FR-6. Наблюдаемость и форензика
- Journal-теги: `ALERT-SENT <channel> <type>`, `ALERT-FAILED <channel> <errclass>`,
  `ALERT-SKIP <reason:cooldown|duplicate|disabled>`. Без секретов и без полных IP
  клиентов.
- `vds logs` (ADR-012) должен уметь видеть эти теги в общем конвейере (не ломая
  существующие сигнатуры).
- `vds alert status --json` — машиночитаемо (для будущего монитора).

**AC:** после отправки/неудачи теги в `journalctl -u vds-alert-watch` видны и
соответствуют факту; `vds logs analyze --live --since 1h` не падает на новых тегах.

### FR-7. Разделение ролей: только уведомление, без авто-действий
- Сторож по умолчанию **только уведомляет**. Включение/управление `--auto-lockdown`
  остаётся за `probe-watch config` (существующий механизм) и **не** дублируется в
  стороже.
- Сторож **никогда** не вызывает `probe-watch watch --record` и не пишет
  `probe-watch.json` (инвариант ADR-014).

**AC:** после 15 минут работы сторожа mtime и содержимое `probe-watch.json` не
изменились (кроме изменений от штатного таймера probe-watch).

### FR-8. (Отдельная фаза, риск-гейт) Изоляция межузлового порта на exit-узле
**User story:** Как владелец, я хочу, чтобы `51825/udp` на exit-узле принимал пакеты
только с IP релея, чтобы сканеры вообще не доставали до порта.

**Блокер:** на asv2 `51825/udp` — **основной AWG-порт клиентов** (мобильные/Windows-
пиры). Прямой `ufw allow from <relay>` с удалением общего правила **сломает клиентов**.
Требуется решение (один из вариантов): отдельный порт для ноги релея, отдельный
интерфейс/`awg2`, либо фильтр по `AllowedIPs`/`nft`-правило «51825 от не-релея →
в отдельную цепочку с ограничением». **До решения OQ-1 FR-8 не реализуется.**

**AC (после решения OQ-1):** клиентские пиры (mobile/win) сохраняют handshake;
нога релея на изолированном порту жива; внешний скан с произвольного IP не получает
ни ответа, ни ICMP.

### FR-9. (Отдельная фаза, риск-гейт) Манёвр порта/протокола на плече relay↔exit
**User story:** Как владелец, я хочу, чтобы при блокировке UDP-потока relay→exit связь
восстанавливалась автоматически, без перенастройки клиентов.

- Триггер: потеря handshake > 3 мин **при** живом релее (двухсторонняя классификация).
- Действие (по выбору в ТЗ, минимум одно): смена порта ноги; смена `H1..H4`;
  fallback на TCP/Reality-туннель до exit.
- Клиенты не перенастраиваются (они знают только endpoint релея).
- Обязательна защита от «пинг-понга»: не более одной попытки манёвра в N минут,
  откат по таймауту, журнал попыток.

**AC:** имитация блокировки UDP (drop на тестовом стенде/Docker или iptables на одном
узле) → канал восстанавливается за < 60 с; клиентский handshake не рвётся дольше
T секунд; после снятия блокировки состояние стабилизируется.

## 4. Нефункциональные требования

| Категория | Требование | Как проверить |
|---|---|---|
| Зависимости | только stdlib | `grep -r "import requests\|python-telegram" src/` пуст в новых файлах |
| Секреты | 0600, атомарная запись, не в лог/journal/git/вывод | тест + `git grep` + grep вывода `--help`/`status` |
| Расположение секретов | **только exit-узел**, никогда RU-релей | ревью + чеклист приёмки |
| Идемпотентность | повторный install/remove не ломает | прогон дважды |
| Dry-run | по умолчанию для install/remove | ручной прогон |
| Root | install/remove требуют root | тест на непривилегированном запуске |
| Блокировки | `FileLock` на state/env | ревью |
| systemd | только из `systemd/*.tpl`, `ReadWritePaths` для `/var/lib/vds` + `/var/run` | ревью |
| Отказоустойчивость | недоступный канал не валит юнит; backoff | тест |
| Ложные срабатывания | 15-мин прогон при живом канале без алертов | приёмка |
| Нагрузка | тик ≤ 2 с CPU-времени, без внешних пакетов | замер |
| Откат | `vds alert remove --apply` + восстановление UFW при FR-8 | чеклист |
| Совместимость | не менять существующий CLI/state/UFW-политику | регресс-прогон + docsync |

## 5. Границы

- **Входит:** сторож на exit-узле (FR-1..FR-7), оба канала доставки, heartbeat,
  CLI, journal-теги; FR-8/FR-9 — только при закрытом OQ-1/OQ-8 (отдельные WP).
- **Не входит:**
  - правки `vpn guard` в **ubuntuInstaller** (desktop-нотификатор, `--notify`,
    `expected_lockdown`) — отдельный репозиторий/цикл; здесь только рекомендация
    конфигурации в документе;
  - поднятие собственного почтового сервера (Postfix/DKIM/SPF) — сознательно нет;
  - изменение `--auto-lockdown` семантики;
  - IPv6-мониторинг зондирований (non-goal v1 по probe-coverage);
  - автоперенос `dest` Reality / И27 SNI-rotation;
  - multi-tenant уведомления (несколько получателей) — v1 один владелец.

## 6. Крайние случаи

- `probe-watch.json` отсутствует/битый → сигнал «телеметрия недоступна» (не «тихо»).
- `awg show` недоступен / пир-релей не найден в конфиге → `ALERT-SKIP` + предупреждение,
  не алерт «канал мёртв» (не путать отсутствие данных с блокировкой).
- Релей недоступен **и** handshake мёртв → одно сообщение «релей лёг», а не два.
- `lock-443` активен и decay threat заморожен → не эскалировать бесконечно, слать
  напоминание не чаще cooldown.
- Смена IP релея (миграция) → сторож берёт endpoint из `state.json`, не хардкод.
- DST/часовые пояса — всё в UTC.
- Двойная доставка (tg+smtp) при частичном отказе — каждый канал независим.
- Юнит-таймер пропустил тик (suspend/reboot) → при старте не спамить «догоняющими»
  алертами, а отправить сводку текущего состояния.
