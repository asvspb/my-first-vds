## 0. TL;DR для архитектора и техлида

1. **Стадии уже видны, но не различаются.** Текущие T-01…T-17 ловят эффект
   («TCP душат», «UDP упал») и пробы, но не отвечают на вопрос «какой сценарий
   смерти»: RST-инъекция, тихий дроп ClientHello, дроп ответного UDP или L3-бан.
   Предлагаются **T-18…T-23** и поле `stage` в отчёте.
2. **Две технические поправки к исходной гипотезе** (важно для правил):
   - `TcpInRsts` в `nstat` **нет**; есть `TcpEstabResets`, `TcpExtEmbryonicRsts`,
     `TcpOutRsts`. Чистого «входящие RST» счётчика нет — нужен pcap или
     дифференциал `EstabResets − OutRsts`.
   - `syn_bare/syn_valid` **не видят ClientHello**: `syn_valid` — это SYN с
     TCP-опциями, а не с полезной нагрузкой. Тихий дроп ClientHello
     `syn_valid` не останавливает; детект — только pcap/app-log.
3. **Δt < 15 мс — сильная улика, но не «100 % математика».** Локальный aborts
   клиента тоже может дать RST сразу после ClientHello. Абсолютным признаком
   делает **RTT-floor** (`Δt < rtt_est`, где `rtt_est` измерен на этом же
   хендшейке) плюс несовпадение TTL/TSopt/seq с легитимным потоком. Это
   повышает точность и снижает ложные обвинения цензора.
4. **Портфель мер — пять контуров:** невидимость, разнообразие, эфемерность,
   управляемая деградация, наблюдаемость/дисциплина. Порядок: P0 — ранбук,
   гигиена, аудит периметра, XMUX; P1 — failover, canary, пул CDN-фронтов;
   P2 — SPA/dynamic whitelist (ADR-013), ротация IP, anti-fingerprint.
5. **Главный операционный вывод:** под обстрелом сервер **не рестартить** и не
   менять конфиг. Живучесть даёт переключение канала и молчание, а не «починка»
   исправного демона. Это уже зафиксировано в probe-response; здесь добавляется
   stage-aware процедура.

## 1. Проблема

| Пробел | Следствие |
|---|---|
| Детект не различает сценарии | «RST-инъекция», «тихий дроп CH», «дроп ответного UDP» и «L3-бан» лечатся по-разному, а в отчёте выглядят как один `effect_only` |
| Нет packet-level доказательства middlebox | нельзя отличить цензора от сбоя клиента/апстрима, решения принимаются по одному счётчику |
| Меры живучести разрознены по трём документам | нет приоритетов, зависимостей, DoD и метрик; каждый инцидент — импровизация |
| Самые сильные меры не реализованы | SPA/dynamic whitelist, multi-transport failover, ротация IP, пул CDN-фронтов остаются идеями |
| Нет stage-aware реакции | под обстрелом делают рестарт/смену SNI — это ухудшает профиль и не помогает |
| Нет метрик живучести | нельзя ответить «стало ли лучше» после внедрения мер |

Цель — дать архитектору и техлиду **согласованный пакет**: что детектировать,
как доказывать, что внедрять в каком порядке и по каким метрикам принимать.

## 2. Packet-level модель: три стадии и что видит сервер

### 2.1. Стадия 1 — data-phase blackhole / TCP freeze

| Шаг | Направление | Пакет/событие | Что видно на сервере |
|---|---|---|---|
| 1 | клиент → сервер | `SYN` | `syn_valid` (SYN с опциями) |
| 2 | сервер → клиент | `SYN, ACK` | — |
| 3 | клиент → сервер | `ACK` | handshake завершён, `ss` ESTAB |
| 4 | клиент → сервер | `TLS ClientHello` (~517–1200 Б) | app-log (Reality/XHTTP), pcap |
| 5 | сервер → клиент | `ServerHello` + CCS + Certificate (несколько сегментов) | `ss` Send-Q растёт |
| 6 | клиент → сервер | **тишина**: нет ACK на данные сервера или дропается payload после 2–4 КБ | `TcpRetransSegs`↑, `TcpExtTCPTimeouts`↑, `TcpExtTCPLostRetransmit`↑ |
| 7 | — | сокет висит ESTABLISHED-зомби с ненулевым Send-Q и `timer:(on,…)` | `ss -tin` |

Ключевое: **handshake проходит**, поэтому «порт открыт/закрыт» и `syn_valid`
ничего не говорят. Признак — неподтверждённые данные и ретрансмиссии.
Текущий T-01 уже учитывает зомби-сокеты (ревью G2-2), но требует доли зомби
≥60 % и `syn_validΔ>0`; на single-tenant узле с 1–2 сокетами это работает
не всегда — нужен T-22 (ниже).

### 2.2. Стадия 2 — активное зондирование

| Признак | Как выглядит | Что видит сервер | Ограничение |
|---|---|---|---|
| Источники | 2–5 разных RU-IP, не IP клиента | `probers4`, `syn_valid` | geo только при наличии RU-CIDR |
| J3-серия | 6–8 разных ClientHello за 3–10 с | pcap: CH, длины, SNI, JA3/JA4 (tshark) | без pcap — только счётчики |
| Мусор | HTTP GET / случайные байты вместо `0x1603` | pcap: первый PSH-байт | app-log при default loglevel слеп |
| Соседние порты | `SYN` на 8443/2053/2083/51820/51826/Диапазон hop + SSH-порт | kernel/UFW, `sshd`, pcap | masscan делает то же — нужен контекст |

Текущие T-03/T-07 покрывают источники и серию, но **не** соседние порты и не
связывают серию с конкретным сценарием смерти. Добавляется T-20.

### 2.3. Стадия 3 — три сценария смерти

#### A. UDP response drop (AmneziaWG / Hysteria2)

| Фаза | Пакеты | Серверные счётчики |
|---|---|---|
| До бана | Handshake Initiation ↔ Response ↔ data | `latest-handshake` свежий, `rx`/`tx` растут |
| После бана (запросы доходят, ответы дропаются) | Initiation доходит, Response уходит, данных от клиента нет | `latest-handshake` застывает, `tx` растёт, `rx`≈0 |
| После бана (запросы не доходят) | тишина в обе стороны | `rx`≈0, `tx`≈0 |

Различие критично: в первом случае сервер **отвечает**, но ответ не доходит;
во втором — до сервера не доходит запрос. T-21 ловит первый, T-23 — второй
(если тишина по всем транспортам).

#### B. RST injection / silent ClientHello drop

**B1. RST injection:**

```
клиент → сервер: SYN
сервер → клиент: SYN, ACK
клиент → сервер: ACK
клиент → сервер: ClientHello
сервер → клиент: ServerHello ...
       ↳ через 1–5 мс от имени клиента: RST, ACK  ← инъекция middlebox
```

Сервер видит RST от `src = клиент`, закрывает сокет. Реальный клиент физически
не мог получить ServerHello и отреагировать за 1–5 мс (RTT РФ↔Европа ~40–60 мс).
Это T-18.

**B2. Silent ClientHello drop:**

```
клиент → сервер: SYN
сервер → клиент: SYN, ACK
клиент → сервер: ACK
клиент → сервер: ClientHello  ← дропается до сервера
       ↳ тишина; клиент ретранслирует CH, сервер его не видит
```

Сервер видит завершённый handshake и **ни одного байта данных**. Это T-19.
Важно: `syn_valid` при этом **растёт** (SYN с опциями), поэтому исходная
гипотеза «syn_bare растёт, syn_valid стоит» для реального клиента неверна.

#### C. L3 ACL / null-route

| Признак | Что видно |
|---|---|
| RU-IP исчезают полностью | нет TCP/UDP ни на один порт, включая 22 |
| Фоновые сканеры из других гео | `syn_bare` продолжает расти |
| ICMP | иногда проходит (фильтр только tcp/udp) |
| Пробы | обычно нет: цензор уже не зондирует, а блокирует |

Это T-23. С сервера диагноз вероятностный: нужен внешний vantage или
подтверждение клиента.

### 2.4. Асимметрия наблюдения

| Поведение | Видно с сервера | Максимум вывода |
|---|---|---|
| Пассивный DPI | ❌ | только последствия |
| Активное зондирование | ✅ (pcap/nft) | `probing` |
| Data-phase freeze | ✅ (`ss`/nstat) | `effect_tcp` |
| UDP response drop | ✅ (AWG-счётчики) | `effect_udp_response` |
| RST injection | ✅ при pcap; ⚠️ без pcap | `middlebox_rst` |
| Silent CH drop | ✅ при pcap; ❌ без pcap | `middlebox_silent_drop` |
| L3-бан | ⚠️ косвенно | `effect_ip` |
| SNI/DNS/whitelist | ❌ | `client_side` |

### 2.5. Хронология

```
t=0          SYN
t+RTT        handshake ok
t+2RTT       ClientHello
t+3RTT       ServerHello...
             │
             ├─ Stage 1: данные душатся → retrans / Send-Q / timeouts
             │           (T-01, T-22)
             │
t+2…40 s     ├─ Stage 2: 2–5 RU-IP, 6–8 ClientHello, мусор,
             │           соседние порты (T-03, T-07, T-20)
             │
t+…          └─ Stage 3: RST (T-18) | silent CH drop (T-19)
                         | UDP response drop (T-21) | L3 (T-23)
```

### 2.6. Стадия 0 — первый контакт и прогрев (риск, не детект)

Свежий IP — самый уязвимый: пассивный DPI видит первый же поток, а профиль
ещё не накоплен. В дампах это окно 15–30 минут до Stage 1. Сервер не может
«спрятать» первый контакт, но может не добавлять к нему лишние сигналы:

| Правило прогрева | Почему |
|---|---|
| первые 24–48 ч — низкий объём, только целевой трафик | не выделяться объёмом/скоростью |
| никаких панелей, сканов, «диагностических» портов | каждый лишний порт — сигнатура |
| split-tunnel: RU/CDN-трафик мимо туннеля | профиль абонента выглядит обычным |
| не тестировать из цензурируемой сети сериями | серия ClientHello = active probing |
| фиксировать `exposure_age_h` в отчёте | решения зависят от возраста IP |

`exposure_age_h` — новое контекстное поле отчёта (не правило): сколько часов
IP используется с момента первого клиентского трафика. Оно не влияет на
severity, но печатается в MD/JSON и учитывается в рекомендациях.

## 3. Технические поправки к исходной гипотезе

Эти поправки — не придирки: от них зависит, какие правила вообще реализуемы
без pcap и какие обещания можно давать в отчёте.

| Утверждение | Факт | Следствие |
|---|---|---|
| «`TcpInRsts` растёт при RST-инъекции» | В Linux `nstat`/`/proc/net/snmp` нет `TcpInRsts`. Есть `TcpEstabResets` (закрытия из ESTAB по RST, включая локальные), `TcpOutRsts` (наши RST), `TcpExtEmbryonicRsts` (RST в SYN_RECV), `TcpInErrs` | Чистый «входящие RST» — только pcap. Агрегат: `ΔTcpEstabResets > ΔTcpOutRsts` + `ΔTcpExtEmbryonicRsts` |
| «При тихом дропе CH `syn_bare` растёт, `syn_valid` стоит» | `syn_bare` = SYN ровно 40 б, `syn_valid` = SYN с TCP-опциями. Реальный клиент всегда с опциями → `syn_valid` растёт, даже если CH дропнут | T-19 не может опираться на nft; нужен pcap/app-log. `syn_valid` остаётся индикатором «кто-то стучится», а не «дошёл CH» |
| «Δt < 15 мс = 100 % middlebox» | Локальный abort клиента (отмена, закрытие приложения) тоже может дать RST через 1–5 мс | Δt — сильная улика; абсолютным делает `Δt < rtt_est` (RTT измерен на этом же хендшейке) **или** несовпадение TTL/TSopt/seq |
| «estab=0 — признак blackhole» | При data-phase freeze сокеты висят ESTABLISHED-зомби; estab не обнуляется мгновенно | Уже исправлено в T-01 (G2-2): доля зомби-сокетов, Send-Q, retrans |
| «UDP: rx≈0 — всегда response drop» | Если дропаются запросы, rx≈0 **и** tx≈0; если ответы — rx>0, tx>0, handshake застыл | T-21 требует `rx_delta>0` и `tx_delta>0`; иначе это T-23/тишина |
| «RST всегда виден серверу» | Часть middlebox инжектит RST только в сторону клиента | Серверный T-18 ловит только двустороннюю/серверную инъекцию; клиентский RST — в `client_report` |

### 3.1. RTT-floor: как превратить Δt в доказательство

Для каждого соединения pcap считает:

```
rtt_est   = t(ACK) − t(SYN,ACK)          # оценка RTT + обработка клиента
t_min     = t(ClientHello) + rtt_est     # раньше этого genuine RST не придёт
Δt        = t(RST) − t(ClientHello)
```

- `Δt < rtt_est` — RST **не может** быть реакцией на ServerHello; остаётся
  локальный abort клиента или middlebox.
- `Δt < 15 мс` — жёсткий порог для «быстрого» RST.
- Абсолютный признак: `Δt < rtt_est` **и** хотя бы один маркер подмены
  (TTL/TSopt/seq). Иначе — `high` только при серии и RU-контексте.

| Маркер | Как проверять | Вес |
|---|---|---|
| TTL | `TTL(RST)` отличается от `TTL(SYN)`/`TTL(ACK)` более чем на 1 | сильный |
| TCP timestamps | в SYN/ACK есть TSopt, в RST нет; или TSval немонотонен | сильный |
| seq/ack | RST.seq не соответствует `snd_nxt`/`rcv_nxt` потока | средний |
| Серия | ≥3 RST-после-CH за 10 мин с одного/нескольких RU-IP | средний |
| Отсутствие локального abort | в app-log нет закрытия/ошибки клиента, `TcpOutRsts` не растёт | усилитель |

## 4. Новые правила T-18…T-23

### 4.0. Карта «стадия → правило → вердикт»

| Стадия | Правило | Вердикт отчёта |
|---|---|---|
| 1. Freeze | T-01, **T-22** | `stage1_freeze` |
| 2. Probing | T-03, T-07, **T-20** | `stage2_probing` |
| 3A. UDP response drop | **T-21** | `stage3_udp_response_drop` |
| 3B. RST injection | **T-18** | `stage3_rst_injection` |
| 3B. Silent CH drop | **T-19** | `stage3_silent_clienthello_drop` |
| 3C. L3 block | **T-23** | `stage3_l3_block` |
| Локальный сбой | T-09/T-10/T-11/T-12/T-17 | `local_fault` |
| Масс-скан | T-04 | `mass_scan` |

Правило приоритета: **stage 3 > stage 2 > stage 1**. Если в окне есть и
freeze, и RST-инъекция, отчёт показывает stage 3 и перечисляет оба finding.

### 4.1. T-18 `rst_injection`

**Смысл:** RST от имени клиента пришёл раньше, чем клиент мог получить ответ
сервера, и/или несёт признаки подмены.

| Поле | Значение |
|---|---|
| Источники | `pcap` (прямой), `nstat` (агрегат), `probe` (контекст), `app-log` (исключение локального abort) |
| Прямой триггер | flow `(src_ip, sport, 443)`: есть SYN, SYN-ACK, ACK, ClientHello, затем RST от `src_ip`; `Δt < min(15 мс, rtt_est)` |
| Усилители | TTL/TSopt/seq-маркер (§3.1); ≥3 эпизода/10 мин; `RU`-тег; ранняя инъекция до ESTAB → `TcpExtEmbryonicRsts`↑, после CH → `TcpEstabResets`↑ при `TcpOutRsts` без роста |
| Агрегатный fallback | `ΔTcpEstabResets > ΔTcpOutRsts` **и** `ΔTcpExtEmbryonicRsts > 0` **и** нет локальных abort в app-log, 3 сэмпла подряд |
| Severity | `high` при `Δt < rtt_est` + маркер; `medium` при `Δt < 15 мс` + серия; `low` при одиночном Δt |
| FP-guard | локальный abort клиента (app-log), рестарт юнита, healthcheck-пробы, собственные IP; одиночный эпизод без маркеров — не `high` |
| Стадия | 3B |

**Почему не `TcpInRsts`:** см. §3. Агрегат — прокси, прямой источник — pcap.

**Пример evidence:**

```json
{
  "source": "pcap",
  "metric": "ch_to_rst_ms",
  "value": 3.2,
  "rtt_est_ms": 48.0,
  "ttl_syn": 52,
  "ttl_rst": 61,
  "tsopt": "missing_in_rst",
  "seq_consistent": false,
  "episodes_10m": 4
}
```

### 4.2. T-19 `client_syn_no_clienthello`

**Смысл:** от известного клиента завершается TCP-handshake, но ClientHello
до сервера не доходит — тихий дроп на пути.

| Поле | Значение |
|---|---|
| Источники | `pcap` (прямой), `app-log` (нет CH/ошибки), `ss`/`nft` (контекст) |
| Прямой триггер | `src` в `known_clients` (AWG-endpoints, allow-ips, успешный CH за 24 ч); SYN → SYN-ACK → ACK; **нет** записи `0x16 0x03` за 2 с; повтор ≥3/10 мин |
| Агрегатный fallback | без pcap **не выдаётся** как `high`; допускается `low`-контекст «handshake без данных» по `ss` + app-log, с пометкой `coverage.pcap=missing` |
| Severity | `high` при pcap + known client + серия; `medium` при pcap без known client; `low` — контекст |
| FP-guard | клиент открыл TCP и молчит (healthcheck, порт-чек), сканеры, собственные IP; требовать «был успешный CH за 24 ч» и отсутствие app-ошибки |
| Стадия | 3B |

**Важно:** `syn_valid` при этом растёт; правило **не** использует
`syn_bare/syn_valid` как доказательство дропа CH.

### 4.3. T-20 `adjacent_port_sweep`

**Смысл:** тот же источник за короткое время стучится на «прокси-порты» —
профиль активного зондирования.

| Поле | Значение |
|---|---|
| Источники | `pcap`/`kernel` (UFW), `journal:sshd`, `nft` |
| Прямой триггер | один `src_ip` за 60 с задел ≥2 порта из `{8443, 2053, 2083, 51820, 51826, 20000–20500}` + **фактический SSH-порт** (49222 на asv2; не хардкодить 22) **и** в ±5 мин был контакт на 443 |
| Усилители | `RU`-тег; совпадение с T-07/T-18; SYN без payload; серия с 2–5 IP |
| Severity | `medium` при RU+443; `high` при совпадении с T-07/T-18; `info` — фон без 443 |
| FP-guard | masscan/Shadowserver бьют десятки портов; требовать ≤6 портов и наличие 443; ночной фон не эскалировать |
| Стадия | 2 |

### 4.4. T-21 `udp_response_blackhole`

**Смысл:** запросы от пира доходят, сервер отвечает, но ответы/данные не
доходят до клиента — `latest-handshake` застывает при растущем `tx`.

| Поле | Значение |
|---|---|
| Источники | `awg` (прямой для AWG), `net`/`nft` (UDP-объём), `app-log` (hy2), `probe` |
| Прямой триггер (AWG) | 3 сэмпла подряд (15 мин): `rx_delta > 0`, `tx_delta > 0`, `peers_fresh = 0`, при этом у пира был handshake <60 мин назад |
| Прямой триггер (Hy2) | `udp_443` rx-объём выше floor, интерфейс `tx` растёт, но нет успешных сессий/`auth ok` в app-log за окно; при активном hop — то же по диапазону |
| Severity | `high` для AWG-счётчиков; `medium` для Hy2 (нет per-peer метрик) |
| FP-guard | пир реально idle (нет handshake >60 мин) — пропуск; рестарт/сброс счётчиков (`reset=true`) — пропуск; клиент в роуминге без трафика |
| Стадия | 3A |

**Отличие от T-02:** T-02 — обвал объёма UDP (путь деградировал); T-21 —
запросы есть, ответы не доходят (асимметрия). Оба могут сработать вместе.

### 4.5. T-22 `sendq_freeze`

**Смысл:** на single-tenant узле одного зависшего сокета достаточно, а
процентный порог T-01 (≥60 % зомби) не достигается.

| Поле | Значение |
|---|---|
| Источники | `ss` (прямой), `nstat` (retrans), `app-log` |
| Прямой триггер | ≥1 ESTAB `:443` с `Send-Q ≥ 1 KB`, который не дренируется 3 сэмпла подряд (стабилен/растёт), `retrans_total > 0`, `bytes_acked` не растёт |
| Усилители | `Send-Q > 64 KB`; ≥3 таких сокета; `TcpExtTCPTimeouts`↑; клиент активен |
| Severity | `medium`; `high` при ≥3 сокетах или `Send-Q > 64 KB` + timeouts |
| FP-guard | медленный клиент/большая загрузка (bytes_acked растёт) — не finding; проверить app-log на slow consumer |
| Стадия | 1 |

T-22 — доказательная база для T-01, а не замена: T-01 смотрит на долю и
новые SYN, T-22 — на конкретный застрявший поток.

### 4.6. T-23 `l3_ip_silence`

**Смысл:** с RU-адресов исчезает **весь** трафик на все транспорты, при этом
фон из других гео продолжается.

| Поле | Значение |
|---|---|
| Источники | `nft`, `net`, `probe`, `app-log`, `client_report` (опционально), внешний canary |
| Прямой триггер | 3 сэмпла подряд: `syn_bare/syn_valid` от RU-IP (или known clients) = 0, `udp_443` от них = 0, AWG `rx` = 0, SSH-коннектов нет; при этом фон non-RU `syn_bare > 0`; ICMP может присутствовать |
| Усилители | Внешний vantage подтверждает «сервер жив извне»; клиент сообщает «нет связи»; T-18/T-19/T-21 отсутствуют |
| Severity | `high`; confidence не выше `medium` без внешнего vantage |
| FP-guard | ночное окно/отсутствие клиентов (baseline), авария RU-провайдера, плановые работы; без RU-CIDR/known clients — `inconclusive`, не `high` |
| Стадия | 3C |

**Рекомендация:** не чинить локально, не рестартить; переключить на CDN/relay
или ротировать IP. В отчёте — `alternatives: ["ru_isp_outage", "client_offline"]`.

### 4.8. Stage-классификатор и поле отчёта

```json
{
  "stage": {
    "id": 3,
    "name": "rst_injection",
    "since": "2026-11-16T12:03:00Z",
    "rules": ["T-18"],
    "confidence": "high",
    "alternative": ["client_local_abort"]
  }
}
```

Правила классификатора:
- stage определяется по максимальному id среди сработавших правил;
- `probing_only` (T-03/T-07 без эффекта) → stage 2; `probing_plus_effect` →
  stage 2 или 3 по наличию T-18/T-19/T-21/T-23;
- `local_fault`/`mass_scan`/`inconclusive` — вне стадий, но сохраняются в
  `incidents`;
- stage **не** исполняет действий: рекомендация в отчёте, решение — оператор
  или `probe-response`.

### 5.7. Чего не делать

| Антипаттерн | Почему |
|---|---|
| Рестарт xray/hy2/awg под обстрелом | сбрасывает счётчики/аптайм-профиль, ответ цензору не меняется |
| Смена SNI/конфига в середине инцидента | ломает сравнение «до/после», усиливает подозрение |
| Агрессивные реконнекты (каждые 5 с) | кормят скоринг цензора; серия CH выглядит как проба |
| Открыть «диагностический» порт/панель | возвращает публичную мишень; панель — сигнатура |
| Непрерывный фоновый pcap | диск/CPU/приватность; ловит payload |
| Тот же IP для нового домена сразу после бана | репутация IP переносится |
| Частые тесты из цензурируемой сети | сами провоцируют active probing |
| Верить `systemctl is-active` как «туннель жив» | статус не равен проходимости (§0 CENSORSHIP-PATTERNS) |

## 7. Тест-план и критерии приёмки

### 7.1. Unit (без root/сети, синтетика)

| Что | Проверка |
|---|---|
| T-18 Δt/RTT | синтетический pcap: CH→RST 3 мс при rtt_est 48 мс → high; 60 мс → нет |
| T-18 маркеры | TTL mismatch / TSopt missing / seq inconsistent — каждый усиливает; одиночный Δt без маркеров — low |
| T-18 агрегат | `EstabResets > OutRsts` + `EmbryonicRsts` → medium; локальный abort в app-log → нет |
| T-19 | handshake без CH 3 раза от known client → high; 1 раз → нет; сканер без known → medium |
| T-20 | 8443+2053+443 за 60 с → medium; 10 портов masscan → info/нет |
| T-21 | AWG: rx>0, tx>0, peers_fresh=0 → high; idle peer → нет; reset → нет |
| T-22 | Send-Q 8 KB, bytes_acked не растёт, 3 сэмпла → medium; bytes_acked растёт → нет |
| T-23 | RU-трафик 0, non-RU syn>0, 3 сэмпла → high/medium; без RU-CIDR → inconclusive |
| Stage | T-22+T-18 → stage 3; T-03+T-22 → stage 2; T-09 → local_fault |
| Детерминизм | два прогона → идентичный JSON (кроме `created_at`) |
| Redaction | в отчёте нет UUID/ключей/паролей; IP по политике |

### 7.2. Integration (temp-каталог, моки источников)

1. Bundle с pcap-сводкой RST-инъекции → T-18 + `stage3_rst_injection`.
2. Bundle «handshake без CH» → T-19; без pcap → `coverage.pcap=missing`,
   не `high`.
3. Bundle «соседние порты + RU» → T-20 + `stage2_probing`.
4. Bundle «AWG response drop» → T-21; «idle peer» → нет.
5. Bundle «L3» + внешний canary → T-23; без canary → `inconclusive`.
6. `surface audit --json` на фикстуре `ss`/`ufw` → ports/owners/recs.

### 7.3. Ручная приёмка (живой VDS)

- Синтетика: на тестовом порту `iptables -A INPUT -p tcp --dport <test> -j DROP`
  после CH — T-19 (не на боевом 443).
- Синтетика: `tc netem`/iptables DROP на исходящие данные тестового сокета —
  T-22/T-01 (лабораторный юнит, не xray).
- Реальный инцидент: pcap-серия проб → T-07 + T-20; RST — T-18.
- Проверка слепоты: без pcap T-18/T-19 не `high`; отчёт честно пишет
  `coverage.pcap=missing`.
- `surface audit` на asv1/asv2: список портов совпадает с `ss -tulnp`.
- Canary: внешний vantage видит сервер, RU-клиент — нет → T-23.

### 7.4. AC

- **AC-1:** каждый stage 1/2/3 имеет правило и доказательство; нет «голых»
  вердиктов.
- **AC-2:** T-18/T-19 без pcap не дают `high`; слепота отражена в `coverage`.
- **AC-3:** stage не исполняет действий; рестартов/локов из анализа нет.
- **AC-4:** все новые пороги — в `rules.json` + `rules_hash`.
- **AC-5:** `surface audit` read-only; ни одного `--apply`.
- **AC-6:** SPA (если принят) не ломает established-сессии и имеет откат.
