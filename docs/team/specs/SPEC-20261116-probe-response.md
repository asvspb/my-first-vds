## 1. Цель и принципы

Превратить вердикты probe-watch из «информации для человека» в **управляемую
серверную реакцию** с главной гарантией плейбука: **не трогать сервисы под
обстрелом**. Реакция = изменение только сетевой видимости (UFW), никогда —
xray/hysteria2/amneziawg юнитов и конфигов.

Железные инварианты:
1. Никаких рестартов/правок демонов в ответ на вердикты (счётчики и
   аптайм-профиль не сбрасываются — ответ цензору не меняется).
2. Любая мутация — за явным opt-in (`--auto-lockdown` в конфиге) + TTL
   (само-разблокировка; забытый лок невозможен).
3. Откат любой реакции — одна команда, журнал применённого в state.
4. Сухой прогон по умолчанию везде.

## 2. Машина состояний threat-level (в probe-watch)

Хранится в снапшоте `/var/lib/vds/probe-watch.json` (уже атомарно, 0600,
FileLock — переиспользуем), отдаётся в `watch --json` → поле `threat_level`.

| Уровень | Условие входа | Условие выхода |
|---|---|---|
| `quiet` | — | — |
| `elevated` | 1 окно с `PROBE-BURST`, ИЛИ 1 окно `RU-PROBE-SUSPECT` | 3 тихих окна подряд |
| `high` | `RU-PROBE-SUSPECT` **2 окна подряд** (hysteresis: 2/3 скользящих) | 72 ч (72 окна) без новых RU-IP → `elevated` → ещё 3 тихих → `quiet` |

Правила:
- `high` достижим ТОЛЬКО через RU-сигнал (BURST сам по себе — шум, максимум
  `elevated`); если RU-CIDR недоступен (`geo: unknown`) — `high` недостижим,
  поле `threat_reason` пишет почему.
- Flapping-защита: даунгрейд не раньше чем через 2 окна после апгрейда.
- Окно = тик таймера (1 ч). Состояние переживает рестарт юнита (снапшот).

## 3. RU-CIDR на exit-серверах (рас unlocks SUSPECT)

`ru-cidrs.txt` сегодня ставит relay-модуль — но релея ещё нет. Переиспользуем
`src/relay/cidr.py` (ipdeny-загрузка уже написана и протестирована):

- `vds gateway probe-watch ru-cidr install --apply` — кладёт агрегат в
  `/etc/vds-relay/ru-cidrs.txt` (тот же путь, что ждёт relay) + еженедельный
  таймер обновления `vds-probe-rucidr.timer` (копия паттерна relay-CIDR);
- без relay-модуля файл независим; relay init при будущем деплое детектит
  его и не перезатирает (проверка наличия + идемпотентность).

Это включает RU-PROBE-SUSPECT на asv1/asv2 немедленно, не дожидаясь релея.

## 4. Реакция: изоляция 443 (lockdown)

### 4.1 Команда (в `src/system/ufw.py`, не в probe-watch — разделение слоёв)

```bash
sudo vds system ufw lock-443 [--allow-from <IP[,IP…>]] [--ttl 48h] \
     [--reason "RU-PROBE-SUSPECT"]            # dry-run: план
sudo vds system ufw lock-443 … --apply        # исполнить
sudo vds system ufw lock-443 --status         # состояние лока + TTL
sudo vds system ufw lock-443 --unlock --apply # досрочное снятие
```

Семантика:
- Удаляет широкие `443/tcp` + `443/udp` (записав их в undo-журнал state),
  добавляет `allow from <каждый IP>` для 443 (если список пуст — 443 закрыт
  всем; основной канал ноутбука AWG 51825/udp НЕ трогается и остаётся жив).
- `2053/tcp` (CDN), `51825/udp`, ssh — не трогаются (плейбук Фаза 3).
- TTL обязателен (default 48h): systemd-timer или метка в state + проверка
  на каждом тике probe-watch → auto-unlock. Пропавший таймер = лок висит
  вечно — недопустимо.
- Повторный `lock-443 --apply` идемпотентен: продлевает TTL, список
  allow-from заменяется.
- `--unlock` восстанавливает широкие правила из журнала (ровно то, что
  было; если владелец за время лока сам менял 443 — merge-подсказка, не
  молчаливая перезапись).

### 4.2 Автоматика (opt-in, связка с probe-watch)

```bash
sudo vds gateway probe-watch config \
     --auto-lockdown on|off \
     [--lockdown-allow <RELAY_IP[,CF_none>]] \
     [--lockdown-ttl 48h] --apply
```

- При `threat_level: high` таймер probe-watch вызывает lock-443 c
  configured allow-list/TTL и `--reason auto:RU-SUSPECT`.
- При downgrade ниже `high` — **НЕ** автоснимает (человек решает; TTL
  подстрахует), но `watch` печатает `[warning] лок активен, уровень снизился`.
- `elevated` никогда не триггерит лок.
- Если `lockdown-allow` пуст и allow-файл `/etc/vds-probe-watch/allow-ips.txt`
  отсутствует/пуст — конфиг отказывается принимать `auto-lockdown on`
  (fail-fast: лок закрыл бы всё входящее). Ужесточение HF-1
  (SPEC-20261116-surface-hardening §1.3): наличие резервных портов 51825/2053
  в state.protocols больше НЕ основание — заполненный allow-ips.txt достаточен
  без `--lockdown-allow`, но без любого allow-источника отказ всегда.
- Один лок-на-восход: повторный high во время активного лока = только
  продление TTL, не дубль правил.

## 7. Тест-план / AC

- **Unit (без root/сети):** все машины состояний; undo-журнал lock/unlock
  восстанавливает ровно исходные правила; TTL-автоснятие симуляцией тиков;
  запрет авто-лока при только-443-профиле; `--json`-контракт полей.
- **Живая приёмка (asv2, по go владельца):** `ru-cidr install --apply` →
  `watch` показывает ru-классификацию живых сканеров (6+ IP уже в сете);
  ручной drill: `lock-443 --apply` (allow пуст) → с ноутбука Reality:443
  таймаут, **AWG 51825 жив** (`vpn start` работает), 2053 жив →
  `--unlock --apply` → Reality вернулся. Плюс негативная проверка: юниты
  xray/hy не рестартовали (uptime до/после).
- **AC:** вердикт high за N≤2 окон при реальном RU-зонде (после релея);
  лок не переживает TTL; откат = одна команда.

## 9. Краевые случаи (ревью G2, 2026-11-16) — обязательны к реализации

### 9.A Ослепление syn_valid при активном локе (conntrack + DROP)
Лок 443/tcp пропускает SYN через vds_probe (hook −140, растёт syn_bare),
но UFW роняет его → нет SYN-ACK → нет ClientHello → **syn_valid = 0 всё
время лока**; RU-SUSPECT повторно не сработает (гейт delta.syn_valid>0).
Установленные сессии живут по ESTABLISHED (conntrack) — ожидаемо.
**Следствия (в код):** (1) decay-отсчёт выхода из `high` ЗАМОРОЖЕН, пока
`lockdown.active == true` (тикать начинает только после unlock);
(2) повторное продление TTL при high-в-локе реализуется не по syn_valid,
а по появлению НОВЫХ RU-IP в probers4 по SYN (наблюдательное поле
`ru_syn_new`, продлевает TTL, вердикт не поднимает).

### 9.B lock-443 ↔ Hysteria2 port hopping (asv1)
Нat-PREROUTING REDIRECT 20000:20500 → 443/udp переписывает dport ДО
ufw-user-input: удаление `allow 443/udp` убивает hop, даже при живом правиле
диапазона. **Семантика WP-3:** по умолчанию lock-443 закрывает ТОЛЬКО
`443/tcp`; при обнаруженном hop (state.protocols + ufw-правило диапазона):
`443/udp` НЕ трогается + `[warning] Hy2-hop остаётся открытым (канал
уклонения)`; полное молчание — только явным `--with-udp` (закрывает и
443/udp, и hop-диапазон, записав оба в undo-журнал). Обоснование: asv1-hop —
целевой канал Фазы 1 плейбука, убивать его автолоком нельзя.

### 9.C Конфликт журналов harden ↔ lockdown
Лок-состояние в `state.json["ufw_lockdown"]` (отдельно от applied_rules).
Guard в `ufw harden`: при `lockdown.active` — отказ с подсказкой
`lock-443 --unlock` (обход только `--force`, с записью в журнал).

### 9.D Dual-stack unlock (asv2, /48)
Unlock восстанавливает пары v4+v6 стандартными `ufw allow 443/tcp|udp`
(идемпотентно создаёт оба при IPV6=yes) со сверкой со снимком правил до
лока; allow-from только v4 → v6-443 закрыт на время лока (корректно).

### 9.E Ошибка тест-плана §7 (asv2)
На asv2 НЕТ :2053 (CDN — на asv1). Живая приёмка asv2: во время лока
живы **AWG 51825/udp и ssh 49222/tcp**; 2053 проверяется в drills на asv1.

## 10. Решения OQ (G2, 2026-11-16)

- **OQ-1:** auto-lockdown default **off** (обкатка WP-1/2 на реальных
  вердиктах до включения автоматики).
- **OQ-2:** TTL default **48h**, CLI-валидация диапазона **1h..168h**.
- **OQ-3:** снятие лока — **только вручную или по TTL** (авто-по-downgrade
  запрещён: из-за §9.A давал бы «мигалку» закрылся→открылся→пробы→закрылся).
- **OQ-4:** RU-CIDR ставим **сейчас, WP-2 первым шагом** (asv1+asv2;
  read-only классификация, включает аналитику по живым 6+ IP).

## 11. Поправки DoD (ревью G2)

- **WP-1:** исключение собственных клиентов из new_ru_ips: IP эндпойнтов
  активных AWG-пиров (`awg show` endpoints, кэш в снапшоте) + серверный IP
  + ручной whitelist `/etc/vds-probe-watch/allow-ips.txt` (по строке IP,
  комментарии #). Тест: ноут+телефон в одном окне ≠ SUSPECT.
- **WP-1:** decay заморожен при lockdown.active (§9.A).
- **WP-3:** TTL-проверка — ВНУТРИ часового тика probe-watch (отдельный
  systemd-timer не плодим): `now >= ttl_until` → auto-unlock
  (`reason=ttl-expired`) через внутренний вызов ufw-модуля.

### 11.1 own_ips: verified_session_ips + кэш + conntrack (HF-1)

Поправка HF-1 (SPEC-20261116-surface-hardening §1.2): own_ips на входе в
RU-классификацию = `awg_endpoints ∪ allow-ips.txt ∪ own_ips_cache` —
клиенты на Reality/XHTTP/Hy2 без активного AWG-туннеля больше не попадают
в new_ru_ips как «зондировщики» (anti Self-DoS):

- **verified_session_ips (TCP 443/8443/2053):** `ss -tniH state established`
  с порогами `bytes_acked >= 16384` И `bytes_received >= 4096` — проба
  ТСПУ/Censys не проходит авторизацию VLESS/XHTTP и двусторонний трафик не
  качает. IPv4-mapped префикс `::ffff:` срезается (dual-stack listener),
  строки без обоих bytes-полей игнорируются fail-closed (голый ESTABLISHED
  бота не верифицируется).
- **UDP (Hy2 443/udp, 51826/udp):** `/proc/net/nf_conntrack` (без пакета
  conntrack): `[ASSURED]` всегда; при `nf_conntrack_acct=1` (включаем в
  `systemd/sysctl/99-vds-gateway.conf.tpl`) — дополнительно
  `bytes_orig + bytes_reply > 32768`; полей bytes нет (acct=0) — фолбэк на
  один `[ASSURED]`. Файла нет — тихая деградация до TCP+AWG+кэш (тег
  источника в выводе `watch` / поле `own_ips_sources` JSON).
- **Кэш-аффинность:** verified-IP пишутся в `snapshot["own_ips_cache"]`
  (пары ip/last_seen, TTL 24 ч, чистка на каждом тике): клиент, закрывший
  сессию между тиками таймера, не выпадает из own_ips, пока last_seen < 24 ч;
  last_seen обновляется на каждом тике, пока сессия верифицируется. Запись
  кэша — только в `--record`-прогоне тика; ручной `watch` без `--record`
  объединяет свежие verified с кэшем ТОЛЬКО в памяти (файл не мутируется —
  совместимость с vpn guard ADR-014/M1).

## 12. Стратегический контекст: теневые архитектуры (ревью владельца, 2026-11-16)

Публичные комбайны (3x-ui/Marzban) умирают первыми: набрав 5k+ звёзд,
дефолтные профили (keepalive-интервалы, структура TLS-расширений, порты
API, пути XHTTP/WS) разбираются аналитиками ГРЧЦ/GFW на сигнатуры за
недели. Живучесть закрытых операторских сеток (Иран/Китай/РФ; Red Shield,
китайские «аэропорты» 机场) держится на 4 принципах:

1. **Индивидуальная энтропия (anti-fingerprinting)** — у каждого узла
   рандомизированный профиль: AWG junk-заголовки/паддинг (S1/S2/H1–H4)
   генерируются под мимикрию конкретного UDP-протокола (DTLS/WebRTC/
   голосовой звонок), а не просто случайные числа.
2. **Асимметричный вход (decoupled ingress/egress)** — Exit никогда не
   светит IP напрямую клиентам из цензурируемой зоны: перед ним релеи,
   резидентские прокси, облачные балансировщики, XHTTP-схемы с разными
   путями uplink/downlink. (= наш RU-relay + exit-cascade.)
3. **Эфемерность входов (moving target defense)** — авто-ротация входных
   IP (BGP/API хостера, floating IP за ~30с) по сигналу сенсора +
   подписки с коротким TTL. (= наш probe-watch → реакция; ротация IP —
   при появлении API хостера.)
4. **Тишина на нецелевых портах** — никаких открытых UDP-портов «для
   всех»: Single Packet Authorization (fwknop) / port-knocking, порт
   открывается nftables для одного IP на ~1 час.

Открытые строительные блоки этого класса: Hiddify/Marzban (каскады
Domestic Relay → Foreign Exit, XHTTP из иранской практики),
Xray XHTTP+XMUX (раздельные пути up/down), Geph/Lantern
(Binder → Bridge → Exit, выдача мостов по одному через domain fronting),
fwknop (SPA-стук). Закрыта в них обвязка: списки живых SNI, профили
фрагментации, скрипты ротации, репутация клиентов.

**Оценка внешнего ревью против нашей архитектуры:** закрыто ~80% отличий
живучего приватного узла от публичной мишени. Главные наши преимущества:
single-tenant 1–2 клиента (нет «общежития» из 200 пользователей — ТСПУ
тяжело выделить статистику одного человека), ядерная телеметрия vds_probe
(раннее предупреждение вместо постфактум), каскад + lock-443 («play dead»).

## 13. Бэклог v2: три теневых паттерна (вне этого SPEC; банк идей И42–И44)

| # | Паттерн | Маппинг на наш стек | Оценка |
|---|---|---|---|
| 1 | **Dynamic Whitelist / SPA для 51825/udp (и 49222/tcp)** — порт закрыт миру, открывается nft-сетом с timeout ~1ч после однопакетного стука или авторизации; для сканеров AWG-порта «не существует» | nft dynamic set (механика уже обкатана в probers4 timeout!) + клиентский SPA-отправитель в vpnm/Tasker; asv2: Reality 443 остаётся легальным фасадом | самый большой прирост живучести; после вылизывания probe-response |

## 14. Поведенческая корреляция сессий 24/7 (ревью владельца, 2026-11-16)

Три демаскирующих фактора круглосуточного туннеля (для UDP-каналов — AWG/Hy2):

- **А. Keepalive-метроном:** `PersistentKeepalive = 25` = ~1150 пакетов за
  ночь строго с Δt=25.0с в полной тишине канала — 100% маркер постоянного
  туннеля для поведенческого DPI, даже при идеальной обфускации содержимого.
- **Б. Бесконечный поток:** живущая 18–72ч сессия без смены ephemeral
  source-port прокачивает гигабайты — штрафные очки в скоринге цензора
  («работал сутки → скорость в ноль до переподключения»).
- **В. Эффект одной трубы:** 24/7 Full-Tunnel без сплита = весь фоновый шум
  ОС в одну зарубежную точку и почти ноль RU/CDN-трафика с абонентского IP —
  аномалия профиля, выводящая сервер на active probing быстрее.

**Что уже защищает нас (оценка ревью):** доменный сплит ноутбука снимает
половину проблемы — RU/GitHub/PyPI идут мимо туннеля, абонент выглядит
«обычным живым», в туннель попадают только целевые потоки; туннель молчит,
когда никто не смотрит YouTube (если его не будит keepalive).

### 14.1 Практические меры (бэклог; И44/И45 + конфиг-правки)

| Клиент | Риск 24/7 сейчас | Мера |
|---|---|---|
| Ноутбук (split) | низкий днём, **фоновый маяк ночью** (keepalive 25 в laptop.conf/win.conf) | `PersistentKeepalive = 0` (полное радиомолчание в простое; NAT-дырка не нужна — инициируем всегда мы) или `113` (нестандартное простое число, ×4.5 меньше фона); при агрессивном NAT-роутере и теряющихся пушах — 113 |
| Смартфоны (Full-Tunnel AllowedIPs 0.0.0.0/0) | **высокий**: одна труба + Wi-Fi↔LTE миграция светит IP сервера в разных ASN/ТСПУ | split-tunneling на заблокированные приложения; либо канал с hopping'ом (Hy2 asv1 20000:20500, hopInterval 30s — «длинной сессии» физически нет), либо RU-relay |
| Reality/XHTTP-клиенты | long-lived TCP-сокет | XMUX-лимиты (И43): maxConcurrency 16–32, cMaxReuseTimes 64–128, cMaxLifetimeMs 180000–300000 — ротация сокета каждые 3–5 мин, имитация браузера |

**И45 (новая): суточная ротация ephemeral-порта** — ночной systemd-таймер
на ноутбуке (04:30): секундный `awg set laptop listen-port 0` / быстрый
реконнект iface → новое случайное значение SRC_PORT; суточная сессия в
таблицах ТСПУ закрывается, утром начинается новая. Дёшево, client-only.

Мера И44 (keepalive) применима к генераторам: `amneziawg add-client` /
`relay add-client` — рендер без дефолтного 25 (0 или персональное простое
20–35с на клиента). Серверная часть SPEC не меняется; всё — клиентские
и генераторные правки.

## 15. Карта покрытия зондирования после W1-1 (SPEC-20261116-probe-coverage)

Реализация W1-1 меняет наблюдаемую поверхность probe-watch; вердиктная логика
этого SPEC не меняется. Итоговая карта (живая копия — `probe-watch explain`):

| Сигнал | Покрытие | Механизм |
|---|---|---|
| TCP 443 (Reality) | ✅ полное | `syn_valid`/`syn_bare` (база PROBE-BURST) + `probers4` |
| TCP 8443 (XHTTP), TCP 2053 (CDN origin) | ✅ probers4 + объём | `syn_valid_extra`/`syn_bare_extra` (аддитивно, телеметрия); сканер этих портов → `probers4` → `new_ru_ips` → RU-PROBE-SUSPECT |
| UDP 443 (QUIC/Hy2), UDP 51826 (AWG) | ❌ слепы в probers4 | только объёмный счётчик `udp_443` + verified-conntrack (HF-1); per-element UDP — вне скоупа v1 (QUIC-клиенты дали бы ложные срабатывания) |
| IPv6-зонды | ❌ non-goal v1 | — |
| Серии ТСПУ 2–15 с | ⚠️ телеметрия | быстрый контур `fast_contour_check` (5-мин сэмплер vds-logs-sample): тег FAST-CONTOUR в journal при ≥ 10 уникальных probers/5 мин; АВТО-ДЕЙСТВИЙ НЕТ — lockdown остаётся исключительной прерогативой часового probe-watch (§4.2, §10) |

Инварианты сохранены: JSON-контракт `watch --json` расширен только
аддитивно (`syn_valid_extra`, `syn_bare_extra`, `extra_ports: [8443, 2053]`)
— guard sync старой версией клиента работает без ошибок; PROBE-BURST-пороги
считаются только по 443; `watch --json` без `--record` не мутирует snapshot
(быстрый контур пишет verified-IP в сайдкар `/var/lib/vds/probe-fast-cache.json`,
часовой watch вливает их при record).

## 16. Ответ на вопрос владельца: что происходит при активном сканировании (2026-11-18)

**Вопрос:** «если начнётся активное сканирование — сервер отключит протокол?
переключит меня на запасной?»

> **Актуальность:** раздел описывает поведение **до** WP-FAILOVER. Как только
> будет принят и реализован [SPEC-20261118-vpn-failover](SPEC-20261118-vpn-failover.md)
> (клиентское авто-переключение, ADR-015), абзац «клиент не переключается сам»
> перестанет быть верным — там агент `vpn-failover` делает это по узкому набору
> триггеров. Серверная половина (этот SPEC) не меняется.

**Короткий ответ: ничего не переключится само.** Ни сервер не «отключает
протокол», ни клиент не переходит на запасной канал автоматически. Это
зафиксировано явно, потому что интуиция здесь обманывает.

### 16.1 Сервер: по умолчанию только наблюдает

`probe-watch` детектит `RU-PROBE-SUSPECT` / `PROBE-BURST` и ведёт машину
`threat-level` (§2), но **реакции по умолчанию нет**:

| Условие | Поведение |
|---|---|
| `auto_lockdown` выключен (**дефолт**, §10 OQ-1; `src/gateway/probing.py::2268`) | пишется только `threat_level`; при установленном `vds alert` — уведомление. Блокировок нет |
| `auto_lockdown` включён + `threat == high` | `apply_auto_lockdown()` → UFW `lock-443`, reason `auto:RU-SUSPECT` (`src/gateway/probing.py::2090-2120`) |

Что именно делает авто-лок (`src/system/ufw.py::apply_auto_lockdown`,
`build_lockdown_plan`):

- закрывает **только 443/tcp** (по умолчанию); `--with-udp` добавляет 443/udp
  и hop-диапазон (§9.B);
- **TTL 48 ч** (`LOCKDOWN_TTL_DEFAULT_H`, `src/system/ufw.py::1375`), затем
  авто-unlock по `ttl-expired`; повторный `high`/новый RU-IP продлевает TTL, а
  не дублирует правила;
- понижение уровня ниже `high` лок **не** снимает (анти-«мигалка», §10 OQ-3);
- fail-fast: отказывается запирать, если allow-list пуст **и** нет канала вне
  443 (51825/2053) — иначе закрыл бы всё входящее.

**Формулировка «сервер отключит протокол» неверна:** при включённом авто он
изолирует входящий порт 443/tcp. Протокол как таковой никто не выключает.

Что выживает при локе по умолчанию:

| Канал | Порт | При `lock-443` (tcp-only) |
|---|---|---|
| Reality (direct) | 443/tcp | **падает** — это и есть лок |
| XHTTP | 8443/tcp | жив |
| CDN (origin) | 2053/tcp | жив |
| Hysteria2 | 443/udp | жив (умирает только при явном `--with-udp`) |
| AWG | 51825/udp | жив |
| Релей (LandVPS) | AWG udp/443 → exit | жив; лок на exit-узле его ногу не трогает |

### 16.2 Клиент: автопереключения не существует

| Компонент | Сеть/действие | Автоматика |
|---|---|---|
| `vpn guard` (демон) | read-only, в сеть не ходит | **нет** — ничего не рестартит и не переключает |
| `vpn guard sync` | один ssh `vds gateway probe-watch watch --json` | только явным вызовом |
| `vpn scout` | read-only probe + скоринг | только явным вызовом; видит свежий вердикт сервера (≤10 мин) и штраф `lock-443`, поэтому Reality уезжает вниз и рекомендация смещается на hy2/relay/AWG |
| `vpn up --scout` | поднимает рекомендованное | только явным вызовом; для не-AWG рекомендации выполняет `vpn up <profile>` (`vpnm/scout/cli.py::up_target`) |
| `guard-notify` (десктоп) | баннер | **единственное автоматическое** действие: уведомление, когда *текущий* канал попал в hard-fail (`SERVER_LOCKDOWN`, `TSPU_TLS_FILTER`, `refused`, `timeout`, `no_route`, `dns_error`, `tls_error`, `udp_refused`, `error`, `budget`) + подсказка `vpn switch <profile>` / `vpn start` |

Итоговая механика: **уведомят и порекомендуют, но переключишься ты сам.**

### 16.3 Практический вывод

Прямой Reality (443/tcp) — ровно тот канал, который первым упадёт при
сканировании, если авто-лок включён. Страховка:

1. держать `asv2-hy2` (443/udp — tcp-only лок его не трогает);
2. либо релей: `vpn start relay` (переживает лок 443 на exit-узле);
3. перед стартом 443/tcp — `vpn scout --sync`: подтянет серверный вердикт и
   покажет, стоит ли сейчас лезть в Reality.

Проверка состояния на сервере: `sudo vds gateway probe-watch config`
(`auto_lockdown: true/false`) и `sudo vds gateway probe-watch watch`
(текущий `threat_level`).
