## Слайд 1. Проблема: клиент видит то, чего не видит сервер

**Тезис.** Серверный `vds logs` видит эффекты на NIC и активные пробы. Класс
отказов «SNI-drop / DNS-подмена / whitelist / handshake прошёл — данные
умерли» виден **только с клиента**, и сейчас клиент отвечает тремя снимками.

| Инструмент | Что даёт | Чего не даёт |
|---|---|---|
| `vpn monitor` | матрица каналов, пробы | историю: «упало 40 с назад» |
| `vpn doctor` | окружение, DNS, порты | поток ошибок и их порядок |
| `vpn repair` | снимок + починка DNS | запускается уже после инцидента |

**Цена.** Окно ТСПУ 2–15 минут: пользователь замечает отказ, когда лог
прокручен; типичная реакция (рестарт юнита) уничтожает улики (тот же вывод,
что §5.9/§5.11 SERVER-BASELINE).

**Просьба к аудитории:** согласиться, что это отдельный vantage, а не дубль
`monitor`/`doctor`.

## Слайд 2. Что предлагается: один потоковый конвейер

**Тезис.** `vpn guard` — клиентский демон, который читает журнал **в живом
времени** и за секунды говорит «что сломалось, на каком слое, насколько
уверены, что делать».

```text
journalctl -f → parse (structured-first) → окна (mono) → G-01…G-12
→ корреляция/инциденты → findings.jsonl + human/--json + notify (opt-in)
```

- один долгоживущий reader на источник, bounded queue 10k, drop-oldest;
- задержка «строка → finding»: медиана ≤ 300 мс, p95 ≤ 2 с;
- RSS ≤ 80 МБ, CPU ≤ 1% ядра в покое, диск ≤ 20 МБ.

**Почему не батч:** `journalctl --since` по cron — это минуты и пропуски;
inotify/tail файлов — systemd владеет stdout, ротация. Подробности — SPEC §5.2.

## Слайд 3. Границы: read-only, без root, без сети, без LLM

**Тезис.** В v1 guard **ничего не чинит** — только объясняет.

| Ограничение | Как обеспечено |
|---|---|
| Нет действий | ни `systemctl`, ни `vpn switch/repair`, ни UFW; в finding только `action`-текст |
| Нет root | `awg show` не вызывается; системный журнал — best-effort |
| Нет сети в демоне | тест с monkeypatch `socket` → любой вызов = fail |
| Нет LLM | правила детерминированы, пользовательские regex запрещены |
| Нет утечек | сырой текст не персистится; только счётчики и хэши шаблонов |

**Авто-реакции** (авто-DNS, авто-переключение) — отдельный ADR после ≥ 30 дней
полевых данных. Это решение G2, переоткрывать сейчас не предлагаю.

## Слайд 4. Три канала, включая AmneziaWG (правка G2 №2)

**Тезис.** Основной канал ноутбука — AWG, а не Xray/Hy2. Если его не видеть,
guard уходит в `idle` и «молчит» ровно там, где живёт пользователь.

| Канал | Наблюдение | Правило |
|---|---|---|
| Xray Reality/XHTTP | user-journal (`vpnm-*.service`) | G-01…G-03, G-09 |
| Hysteria2 | user-journal + QUIC-сигналы | G-04 (основная ветка) |
| **AmneziaWG** | system-journal + **sysfs-счётчики** | G-04 (ветка `awg_tx_no_rx`) |

- `proto: amneziawg`; юниты `vpn-awg-split@*` / `awg-quick@*`, резолвер
  сплита — `dnsmasq` (добавлены в S2);
- интерфейс: имя инстанса из lifecycle → fallback `ARPHRD_NONE (65534)`;
  **`awg0` не хардкодится**, `sudo` не нужен;
- `tx↑` при `rx≈0` в двух окнах по 120 с → G-04 `awg_tx_no_rx`
  (`awg_tx_min_bytes` 256 КБ, `awg_rx_ratio` 0.05);
- `armed ≠ idle`: интерфейс есть, трафика нет — часы идут, правило ждёт;
- `awg_iface_gone` → ветка подавлена, событие уходит в G-10/G-07.

**Почему не G-13:** каталог правил заморожен на G2; ветка внутри G-04 не
меняет контракт и не плодит правило.

## Слайд 5. Правила G-01…G-12: каталог и пороги заморожены

**Тезис.** 12 правил покрывают слои: туннель, цензура, конфиг/креды, DNS,
локальная сеть, TLS, недоступный эндпоинт, flap юнита, деградация, self-health.

| ID | Правило | Ключевой порог |
|---|---|---|
| G-01 | `no_handshake_after_start` | 25 с, при доказанном покрытии |
| G-02 | `reset_storm` | 3 / 60 с после handshake |
| G-03 | `post_handshake_drop` | 3 цикла / 120 с, разрыв ≤ 5 с |
| G-04 | `udp_response_blackhole` (+AWG-ветка) | 2 / 10 мин / 2 окна счётчиков |
| G-05 | `auth_failure` | 1 fail и нет ok 5 мин |
| G-06 | `dns_broken` | 2 / 60 с |
| G-07 | `local_network_down` | route/iface событие |
| G-08 | `tls_cert_error` | нет успешного TLS 5 мин |
| G-09 | `endpoint_silent` | 5 / 10 мин, 0 handshake |
| G-10 | `unit_flap` | 3 / 10 мин |
| G-11 | `degraded_throughput` | 2 отчёта < 2 Мбит/с / 24 ч |
| G-12 | `guard_selfdegraded` | источник lost > 60 с, unparsed > 30% |

**Что важно архитектору:** порядок фиксирован, ID finding детерминирован,
severity и confidence независимы, есть гистерезис (`confirm_windows=2`,
`quiet_windows=3`), cooldown 300 с и cap 12 уведомлений/час.

**Что важно техлиду:** все пороги — в `guard.json`, без regex; изменение
порога не меняет `rules_hash` контракта, но пишется в `config_hash`.

## Слайд 6. Честная слепота: G-01 больше не «мёртв на первом старте»

**Тезис.** Absence-правило опасно: при default loglevel приложение может не
печатать handshake. Раньше G-01 требовал «сигнал за 10 минут **до** старта» —
и на первом запуске мёртвого профиля не срабатывал никогда.

**Решение (правка G2 №5).** Покрытие доказывается **после** `unit_start`,
внутри того же `INVOCATION_ID`:

1. `app_banner_ok` — стартовый баннер Xray/Hysteria2 ≤ 15 с; или
2. `dial_start` / `dial_timeout` / `conn_refused` ≤ 25 с.

| Что видим | Исход |
|---|---|
| banner/dial есть, handshake нет | **G-01** `tunnel_down`, high / medium |
| handshake есть | норма, `last_lifecycle.cause=vpn_up` |
| ни banner, ни dial, ни handshake | `insufficient_data` (`no_app_banner`) + G-12, **не** finding |

**Тонкость:** баннер доказывает «приложение живо», но **не** трафик — для
`no_signal_window` он не считается app-активностью, иначе маскировал бы
полную слепоту.

## Слайд 7. Приватность: что хранится и что нет

**Тезис.** Артефакты постоянные, поэтому приватность — часть контракта, а не
«потом».

| Хранится | Не хранится |
|---|---|
| счётчики, окна, `evidence`, `fp_checks` | сырой текст строки |
| `sha1(template)[:12]` | UUID, пароли, ключи, `shortId`, obfs |
| хэши контракта (`schema_hash`, `rules_hash`) | share-ссылки, URL с токенами |
| домен эндпоинта локально (`<host>` в экспорте) | payload, SNI третьих сторон, IP из `ru_top` |

- retention: findings **14 дней / 20 МБ** (5 × 4 МБ), trace 1 ч / 10 МБ;
- сниппеты по умолчанию **выключены**;
- **пост-сканер не блокирует собственный контракт** (правка G2 №4):
  allowlist `*_hash`, `*_sha256`, `template`, `id`, `evidence_hash`;
  значение `sha256:<64 hex>` — не секрет. Иначе любой экспорт падал бы на
  `schema_hash`;
- при хите в свободном поле: finding без сниппета + `[warning]`,
  `export` — код 2 со списком **полей**, не значений.

## Слайд 8. Кросс-vantage: сервер только через файл

**Тезис.** Демон не сетевой. Единственная сетевая команда — `vpn guard sync`,
один ssh-вызов, результат — файл `server-verdict.json` по allowlist.

**Как доказано, что это read-only (правка G2 №1).** По коду
`cmd_watch(record=False)` пишет только под `if record:`; но «подтверждено по
коду» — не доказательство для контракта. Поэтому в WP-G4 добавляется
**серверный regression-тест**: `mtime`+`sha256`
`/var/lib/vds/probe-watch.json` и gateway `state.json` до/после `watch`
не меняются (touch `vds-probe-watch.lock` — не состояние).

**Тайминги под часовой серверный тик:** opt-in timer `vpn-guard-sync.timer` —
**60 мин** (15 мин давали бы 96 SSH-сессий/сутки без выигрыша), свежесть
`fetched_at` ≤ **65 мин**. Реальный охват данных честно виден по полю
`window` вердикта; `stage` — опциональное поле (`str`/`None`), отсутствие не
блокирует.

**Merge:** свежий `high` поднимает confidence; `lockdown.active=true` даёт
`expected_lockdown` (цензуру не заявляем); «сервер quiet» не переклассифицирует
локальную сеть.

## Слайд 9. Эксплуатация: юнит, sandbox, деградация

**Тезис.** Имя юнита — вопрос безопасности, а не вкуса.

- **`vpn-guard.service`**, не `vpnm-*`: `runners.enabled_vpnm_units()` считает
  любой `vpnm-*.service` профилем, и `vpn down` / `vpn autostart off` могли бы
  отключить сам guard (реальный конфликт, найден в коде; есть регрессионный
  тест);
- установка — только явная (`vpn guard install`), по умолчанию не ставится;
- sandbox: `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`,
  `ReadWritePaths=~/.local/share/vpn-manager/guard`, `RestrictAddressFamilies=AF_UNIX`,
  `SystemCallFilter=@system-service`, `MemoryMax=128M`, `CPUQuota=10%`.

**Риск, который проверяем на живом юните (правка G2 №3):**
`ProtectSystem=strict` в `systemd --user` идёт через user-namespace; на Ubuntu
24.04 с `apparmor_restrict_unprivileged_userns` возможен `226/NAMESPACE`.
Поэтому два профиля — `hardened` (default) и `compat` (без
namespace-опций), выбор **только по факту** с записью в
`install-state.json` и `sources.unit_profile`. Молчаливого ослабления нет.

Отдельно проверяется `notify-send` при `notify.desktop=true`: D-Bus — это
`AF_UNIX`, значит `RestrictAddressFamilies` его пропускает; проверяем
фактическую доставку, а не `rc=0`.

## Слайд 11. Риски и что с ними делаем

| Риск | Митигация | Остаточный |
|---|---|---|
| Дрейф форматов Xray/Hy2 | golden-корпус по версиям, `unparsed_ratio`, G-12 | средний, ловится полем |
| AWG не виден (idle) | R-11/AC-15: sysfs всегда, `armed`, ветка G-04 | низкий, но ветка требует поля |
| Sandbox `226/NAMESPACE` | AC-17, профили `hardened`/`compat`, три проверки на чистом десктопе | низкий |
| Пост-сканер ломает экспорт | AC-13, allowlist ключей и `sha256:<64>` | снят |
| `sync` мутирует сервер | AC-16, серверный regression-тест | снят контрактом |
| Шум/FP на своих пробах | маркеры `activity.json`, grace ±30 с, cooldown, cap | средний до полевой недели |
| Кросс-репо дрейф схем | `schema_hash` в CI обоих репозиториев | **открыт** (§13, вопрос 2) |

**Полевой критерий выхода:** recall ≥ 80%, ≤ 1 ложный high/сутки (после
тюнинга — ≤ 1 за 3 суток), 0 секретов, AWG ни разу не в `idle`.

## Слайд 13. Вопросы к архитектору и техлиду (решения до WP-G1)

1. **Путь схем.** OQ-8 говорил `scripts/vpn-manager/schemas/guard/`, фактически
   схемы лежат **внутри пакета** — `vpnm/guard/schemas/`. Иначе `pip install`
   не довезёт файлы и `schema_hash`/`selftest` падают (AC-12). Подтвердить
   отклонение от буквы OQ-8 (SPEC и ADR уже обновлены).
2. **CI-контракт `schema_hash`.** Где считается эталон: только клиентский CI
   публикует `schema_hashes.json`, а `vds` его вендорит? Или `vds` держит
   копию схем для сверки? Нужно решение — от него зависит AC-16/RSK-7.
3. **`guard.incident/1`.** Схема существует отдельным файлом **и** встроена в
   `$defs` `guard.status/1` (чтобы статус валидировался без резолвера).
   Равенство копий проверяет тест. Подтвердить, что дублирование с
   инвариантом допустимо, либо требовать единый файл + registry в CI.
4. **Политика `compat`-профиля.** Техлид: считаем ли `compat` аварийным
   состоянием (требует записи в `STATUS`/`TECHDEBT`) или нормой для десктопов
   без userns? Сейчас — наблюдаемое состояние с записью в `sources`.
5. **Стык с survivability.** Подтвердить, что `stage` добавляется в
   `guard.server_verdict/1` аддитивно в WP-S1, без смены major и без
   блокировки guard.
6. **Порядок коммитов.** Предлагаю: (1) `vds` — SPEC + ADR-014 + STATUS +
   диапазон ADR; (2) клиент — `vpnm/guard/`, `pyproject.toml`, `tests/guard/`;
   после коммита зафиксировать `schema_hash` в `STATUS`/CI. Подтвердить.

## Приложение B. Что доклад **не** решает

- не запускает демон и не проверяет полевую ценность (это WP-G6);
- не утверждает авто-действия — они запрещены в v1 отдельным решением G2;
- не заменяет серверный `vds logs`: SNI/DNS/whitelist на сервере
  не наблюдаемы by design;
- не фиксирует `schema_hash` между репозиториями — это вопрос 2 из §13.
