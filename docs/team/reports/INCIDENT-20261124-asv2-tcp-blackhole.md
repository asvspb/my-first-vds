# INCIDENT-20261124-asv2-tcp-blackhole — селективный per-source blackhole входящего TCP на asv2 (edge хостера)

> **Тип:** INCIDENT (расследование, живой). **Дата начала:** 2026-11-24 ~13:35 UTC
> (первый таймаут SSH при разборе жалобы «андроид-клиент не подключается»).
> **Узел:** asv2 `ASV2-IP` (ptr.network / My.Host, РФ-хостер; reverse `wary-rainstorm.ptr.network`).
> **Статус:** ОТКРЫТ — тикет хостеру; подозреваемый = edge-фильтр/DDoS-митигация хостера.
> **Секреты:** в отчёте нет ключей/UUID/паролей; секретные префиксы (XHTTP-path) не упоминаются.

## 0. TL;DR

Машина asv2 **полностью здорова** (сервисы слушают, UFW корректен, conntrack пуст,
форвардинг жив, AWG-UDP работает весь инцидент). Входящий **TCP+ICMP к asv2
от части source-IP молча дропается ДО сетевого интерфейса** — селективно по
источнику: TCP/TLS-сессия с одного внешнего адреса прошла целиком при
валидных чек-суммах, SYNs с трёх других источников до `enp0s3` не доходят.
Дроп происходит на edge хостера/аплинка. Причина триггера неизвестна
(основная гипотеза — авто-DDoS-митигация, возможно накрученная диагностическим
штормом проб с трёх узлов). TSPU **опровергнут**; вины нашего кода/контуров **не
выявлено**; файловая система/конфигурация машины не пострадали. Сторож
`alert-watch` инцидент **не заметил** — второй подтверждённый слепой пиксель
(первый: релей 23.11).

## 1. Симптомы и первопричина жалобы

- Владелец: «андроид-клиент не подключается к серверу». Профиль телефона —
  AWG (10.9.0.3, `Endpoint asv2:51825`, обфускация Jc/S1/H* — QR от 23–24.11
  валидирован парой ключей). **AWG-UDP на asv2 при этом работал весь инцидент**
  (ноутбук весь день в интернете через exit-контур, YouTube-трафик живой).
  Прямая связь «не подключается андроид» ↔ TCP-блок **не установлена**:
  андроид ходит по UDP 51825, который не пострадал. Ожидали повторного
  теста с телефона — не получен (владелец не подтвердил).
- Параллельно вскрылось главное: с ~13:35 UTC **SSH на asv2 недоступен**.

## 3. Матрица исключённых гипотез

| Гипотеза | Вердикт | Доказательство |
|---|---|---|
| TSPU / цензурная фильтрация RU→exit | **исключена** | зарубежное облако (без ТСПУ) тоже не проходит; немецкая VPS через РФ-DC проходит |
| Падение сервисов (xray/sshd) | **исключена** | `ss -tlnp`: слушатели на месте; refusal-паттерна нет (таймаут) |
| UFW-локдаун / неудачный harden / lock-443 | **исключена** | `ufw status verbose` корректен; посторонних nft-таблиц нет |
| Переполнение nf_conntrack | **исключена** | 80/65536, dmesg пуст |
| Null-route хостера (тотальный) | **скорректирована** | не тотальный: часть source проходит полностью |
| **Итог: селективный per-source blackhole на edge хостера** | **рабочая гипотеза** | см. §2 (tcpdump №3–4) |

Характер блока: входящие **SYN-инициации** к серверным портам теряются до NIC
для конкретных source-адресов; ответные/исходящие TCP, ICMP-ответы на
установленные потоки и весь UDP проходят. Машина и наша конфигурация — вне
подозрений (все слои проверены изнутри консолью владельца).

## 4. Затронутые контуры

- ❌ Reality (443/tcp), XHTTP (8443/tcp), SSH-админка (49222) — недоступны
  с заблокированных source (в т.ч. дом. канал владельца и релей).
- ✅ AWG (51825/udp, leg 51900–51911) — работает весь инцидент; exit-контур
  (ноутбук → релей awg0 → awg1 → asv2) возил трафик непрерывно.
- ✅ wstunnel/носитель №2 (wg-ws0) — handshake жив.
- ⚠️ asv1 — offline с 23.11 (владелец), запасного exit нет: на время блока
  из RU жив **только AWG-контур через asv2**.

## 5. Слепые пиксели / методологические находки

1. **alert-watch молчал весь инцидент** (структурно: триггеры локальны —
   юниты/AWG-handshake/threat-level; отказ «source→edge» изнутри узла
   ненаблюдаем). Канал доставки при этом работоспособен (исходящий TCP жив).
   → WP: **reachability-probe с независимой точки** (релей делает TCP-connect
   к asv2:443; маркер/эскалация через AWG-канал на exit-сторож — секреты на
   реле по SPEC-20261117 не появляются). Ложится в guard v1.1 (в spirit И50).
2. **Диагностический шторм как подозреваемый-триггер**: пробы с трёх узлов
   подряд (ноутбук, релей, облако) могли накрутить авто-митигацию хостера на
   собственные source-IP. → Runbook-правило в `docs/SERVER-BASELINE.md`:
   недоступный узел диагностировать одним источником по расписанию; tcpdump-
   подтверждение прикладывать к тикету сразу.
3. **Out-of-band доступ**: единственный вход в машину — SSH (TCP); при edge-
   блоке админка отрезана вместе с клиентскими протоколами. → В baseline:
   консоль/VNC хостера = обязательный пункт чеклиста восстановления.

## 6. Действия по выходу (owner)

1. Тикет в ptr.network: снять per-source blackhole (source-IP: дом. NAT
   владельца, релей RELAY-IP, облако) — приложить tcpdump-доказательства
   (§2); **альтернатива/параллельно — запросить смену IP узла** (критерий И47).
2. Переустановка ОС — **не показана** (проблема вне VM; разрушит рабочий стек).
3. После снятия блока: пост-проверка (SSH, Reality-handshake с дом. канала,
   alert-watch `status`), закрытие инцидента + обновление этого отчёта.

## 7. Вопросы архлиду (мандат на следующую итерацию)

1. **WP «external reachability probe»**: согласовать дизайн (вантаж = релей;
   сигнализация = маркер по AWG/`wg-ws0` без секретов на реле; порог/гистерезис;
   интеграция в `vds alert watch` или отдельный юнит). Приоритет против
   guard v1.1 и A2-окна?
2. **Runbook**: утвердить правило «один источник диагностики» и добавить
   ptr.network в `docs/SERVER-BASELINE.md` как хостера с агрессивной
   edge-митигацией (+ чеклист «что приложить в тикет»).
3. **И47-критерий**: смена IP asv2 — готовить ли план миграции (DNS-gate,
   перегенерация клиентских endpoint/QR, harden-reapply) как отдельный WP

4. **Андроид-хвост**: связь исходной жалобы с инцидентом не установлена —
   после снятия блока нужен повторный тест QR `mobile-awg-asv2` (UDP 51825)
   с мобильного оператора (проверка: не режет ли оператор UDP независимо от TCP).


## 9. ДОПОЛНЕНИЕ — ответ хостера и финальный тест (~15:35 UTC)

**Ответ ptr.network** (владелец переслал): «с нашей стороны ограничены только
SMTP-порты (разблокировка через техподдержку); других ограничений нет».

**Финальный дамп (разделение «SYN не дошёл» vs «SYN-ACK не вернулся»)** —
фильтр «SYN-без-ACK в обе стороны по :443», concurrent probes с ноутбука
(3 SYN: 443/49222/8443) и из зарубежного облака:

- все 20 пакетов — **исходящие** SYN asv2 к внешним :443 (Reality-dest, NAT
  транзита клиента) — обычная жизнь exit-узла;
- **ни одного входящего SYN** от источников владельца — пакеты до `enp0s3`
  не доходят → **исход №3: фильтр на транзитном пути К asv2**.

**Финальный вердикт:**
1. Машина asv2 и вся её конфигурация — вне подозрений (подтверждено всеми
   слоями, включая «сервер не видит убитые пакеты»).
2. Фильтрация — **путь-зависимая, выше хостера** (транзит; по признакам
   RU-транзит/ТСПУ на маршрутах RU-источники→ДЦ и части облачных маршрутов).
   Хостер ограничений не признаёт — его слова не противоречат картинке,
   если фильтр на аплинке/транзите; проверку аплинка хостер не проводил.
3. **Смена IP у того же хостера может не помочь** (путь к ДЦ не меняется).
   Эскалация тикета: потребовать проверку аплинка/смену маршрута. Если
   отказ или бездействие — **перенос exit-узла на другой хостер/локацию**
   (критерии И46/И47: подсетевая плотность, история замен IP у хостера).
4. **Мобильный обход подтверждён** (~15:4x UTC): телефон через релейный
   профиль (мобильный → релей → awg1 → asv2) работает — исходная жалоба
   «андроид не подключается» закрыта рабочим контуром (временным, до решения
   с хостером; релей = единственная SPOF цепочки, см. деградацию 23.11).
   Улика для карты путей: мобильный транзит → LandVPS жив; дом. транзит →
   ptr.network ДЦ режется.
5. Слепые пиксели/вопросы архлиду — см. §5, §7; к §7 добавляется вопрос:
   «перенос exit-узла — готовить план миграции (DNS-gate, перегенерация
   endpoint/QR, релейная нога awg1 на новый exit) как основной сценарий?»
