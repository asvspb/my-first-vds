# WP-M0 — диагностика плеча relay↔exit (P24/P25, DECISION Q5)

> Дата: 2026-11-20 · Узлы: RU-релей (`185.80.91.135`) и exit asv2 (`213.108.23.119`)
> Режим: **только чтение** + два обратимых runtime-эксперимента на релее
> (persistent-keepalive 25 с последующим снятием; генерация трафика через awg1).
> Продакшн-конфиги не менялись, юниты не перезапускались.

## 1. Цель

Снять факты для G2 и проверить гипотезу «handshake мёртв ⇒ канал мёртв», на которой
построены P24/P25 (изоляция порта exit и автоматический манёвр ноги).

ss -ulnp:   0.0.0.0:51825 (awg0), [::]:51825, *:443/udp (hysteria)
ss -ltnp:   *:443/tcp (xray);  2053/8443 — нет (CDN/XHTTP не развёрнуты)
ufw:        51825/udp ALLOW Anywhere (v4+v6), 443/tcp ALLOW, 443/udp ALLOW,
            80/tcp, 49222/tcp LIMIT
awg0:       peers laptop(10.9.0.2), mobile(10.9.0.3), win(10.9.0.4), relay(10.9.0.5)
IPv6:       2a0b:4140:9a2e::2/48 (default via 2a0b:4140:9a2e::1)
```

Подтверждено: **порт ноги 51825 общий с клиентскими пирами**, ограничение по IP
релея без отдельного интерфейса порвёт клиентов ⇒ блокер P24 реален.
AWG-интерфейс на exit один (`awg0`), второго (`awg2`) нет.

IPv6:       2a12:b3c0:1:198::1/48; маршрут relay→exit через 2a12:b3c0:1::1
```

**IPv6-нога технически жива:** `ping -6 2a0b:4140:9a2e::2` — 3/3, 47 мс;
`nc -6 -z ... 443` — OPEN. Это делает вариант «IPv6-нога» (Option A) реальным
без TCP-фолбэка.

## 4. Длительности эпизодов: cooldown-коррекция

Пара «ALERT-SENT relay_blocked → первая попытка relay_recovered (SENT **или SKIP**)»
за 7 дней (SKIP-строка помечает фактическое восстановление, которое иначе
маскируется 30-минутным cooldown'ом):

| метрика | значение |
|---|---|
| эпизодов | **35** (последний открыт) |
| мин / медиана / среднее / макс | **2 / 7 / 32 / 306 мин** |

Прежняя оценка «медиана 32 мин» была артефактом cooldown'а `alert-watch`
(`cooldown_min = 30`, recovered подавлялся) — подтверждено: в журнале 19.11
восстановление фиксировалось в 23:09 (`ALERT-SKIP relay_recovered cooldown`),
а сообщение ушло только в 23:27.

## 5. Ключевая находка: handshake-возраст — не признак обрыва

Наблюдение 20.11, 04:32–04:36 UTC (эпизод «blocked»):

- `awg show awg0` на exit и `awg show awg1` на релее: `latest handshake` = **5 ч 11 мин**;
- при этом **данные через ногу шли**: `ping -I awg1 10.9.0.1` — 2/2, 47 мс;
  `curl --interface awg1 https://ya.ru` — **HTTP 200/302**;
- счётчики awg1 росли (rx 1.46 GiB, tx 2.88 GiB на момент проверки).

Контроль (тот же час):
- `awg set awg1 peer <exit-pub> persistent-keepalive 25` → новый handshake **через
  ~30–40 с** (epoch сменился; keepalive затем снят);
- при непрерывном трафике (6 запросов за 60 с) handshake обновился **ровно через 120 с**
  (epoch 04:38:27 → 04:40:27), счётчики выросли.

Вывод: AmneziaWG 1.0.0 (dkms) допускает передачу данных на давно не обновлённом
handshake; возраст handshake не эквивалентен недоступности ноги. Классификатор
`blocked` (handshake > 300 с + TCP до релея + прирост rx) в таких окнах даёт
**ложное срабатывание**.

Следствия:
1. **P25 в текущей формулировке («триггер handshake > 3 мин») строить нельзя** —
   автомат начнёт менять порт на работающем канале.
2. Нужен сигнал liveness data-plane: ICMP/TCP **внутри** туннеля
   (`ping -I awg1 10.9.0.1`, TCP до exit:443 через awg1) + отсутствие прироста
   rx при живом трафике на awg0.
3. Дешёвый кандидат-митигация: `PersistentKeepalive = 25` на `awg1` (сейчас нет),
   как у клиентских пиров (И44). Проверено, что keepalive инициирует handshake.

## 6. Что это значит для P24 / P25

- **P24 (изоляция порта) — Go, без изменений.** Нужен отдельный `awg2` + src-only
  UFW/nft + статический REDIRECT-пул; клиентские пиры (10.9.0.2–.4) не трогаются.
- **P25 — Pivot**: триггер переводится с `handshake_age` на data-plane liveness;
  ручной актуатор (`maneuver step`) сохраняется, авто-таймер — только после
  подтверждения на реальных эпизодах.
- IPv6-нога (47 мс, OPEN) — первый кандидат для fallback: не требует новых портов
  на exit и не пересекается с клиентским IPv4-портом.

## 7. Не проверено (перенос в следующие WP)

- Реакция ТСПУ на смену UDP-порта/IPv6 **в момент реального блока** (в WP-M0 не
  было живого блока с гарантированной потерей данных: наблюдался stale-handshake
  при работающем канале).
- Причина, по которой handshake не обновлялся 5 ч при идущем трафике
  (поведение dkms 1.0.0 / таймеры AmneziaWG) — нужен отдельный эксперимент
  на стенде с `awg show`-мониторингом и dump/epoch-сверкой.
- Влияние `lock-443` на TCP-пробу релея (учтено в дизайне: проба внутри туннеля,
  а не до 443).
