# PROMPT-20261124-quiet-exit-spec — запрос SPEC на профиль «тихий exit» + релей-only клиентский контур

> **От:** vds-orchestrator, по директиве владельца. **Дата:** 2026-11-24.
> **База:** Q1-PRI/Q2-PRI (вердикт архлида, WP-MR-0…6), SERVER-BASELINE §12–14
> (`6abd4cb`), TECHDEBT P37/P38→ADR-017. **Секреты:** нет.

## 0. Директива владельца (рамка SPEC)

«vpn start — только через правильно организованный релей и тихий выход».
Клиентский контур по умолчанию = **релей → тихий exit**; прямые TCP-профили
выводятся из эшелонов (решено Q6-PRI, Эшелон 2/3). Тихий exit готовим
**заранее** — до решения по asv2, на ES-1.

## 1. Что уже утверждено (SPEC опирается, не переопределяет)

- Профиль «тихий exit»: 0 публичных TCP; 51900–51911/udp + 9443/tcp —
  allowlist RELAY_IP; 51825/udp = OOB-1 до P30; ACME 30-с окно / DNS-01
  (SERVER-BASELINE §14, KPI §13).
- Двухфазность P38 (Фаза 1 = ручной DR без кода) — ADR-017 DRAFT.
- Тесты: nmap извне = 0 open TCP; carrier status зелёный; ssh 10.9.0.1 OK.

## 2. Запрос архлиду: SPEC «quiet-exit» (ответ = ТЗ на WP-срез)

- **Q-S1. vds-сторона**: состав `vds gateway init --profile quiet-exit` —
  какие модули ставятся (amneziawg + exit-leg + wstunnel; БЕЗ xray/hy2/cdn),
  как специфицируется allowlist RELAY_IP при init (env/флаг), UFW-профиль
  (новый `--profile quiet-exit` в `vds system ufw harden`?), обработка
  ACME-окна 80/tcp (pre/post-hook vs DNS-01 — что в первой версии).
- **Q-S2. Релей-сторона**: перенацеливание awg1/wg-ws0 на ES-1 как
  документированная процедура Фазы 1 (пошагово: awg1.conf Endpoint, рестарт
  awg1 **+ policy**, очистка failed_ports, wg-ws0 по домену/IP) + что должен
  валидировать orchestrator после рестарта (data-plane обоих носителей).
- **Q-S3. Клиент (ubuntuInstaller/vpnm)**: директива «vpn start = relay-only».
  Предлагаемая семантика для SPEC: `vpn start` без аргументов = relay
  (сегодня так и есть по умолчанию для релейного пути, но awg-ветка direct
  остаётся доступной) — конкретно: default-схема меняется на relay,
  direct-ветки (`awg`/`reality`/`xhttp`) помечаются deprecated (warning +
  требование явного `--allow-direct`), direct-профили — `vpn profile archive
  --reason "min-risk-cutover"` по Q2-PRI; `vpn scout`/`rank.py` — relay+awg
  выше direct+awg (весовая правка из Q6-PRI). Нужен вердикт: менять ли
  веса/дефолт в guard v1.1-цикле или отдельным клиентским WP до него.
- **Q-S4. P37-стыковка**: dead-man-switch (Healthchecks push) с ES-1 и релея
  в SPEC quiet-exit с первого дня (не послеобкаточно) — параметры (интервал,
  grace, TG-путь) + чек asv2:443 как отдельная временная диагностика.
- **Q-S5. DR-репетиция**: протокол приёмки Фазы 1 (тайминг ≤ 15 мин,
  секундомер, чеклист перехода и отката, критерий «телефон без правки QR»,
  артефакт TEST--отчёт DR) — чтобы репетиция сразу считалась evidence для
  Фазы 2 (ADR-017).
- **Q-S6. Прецондишены ES-1**: чеклист выбора/проверки хостера до деплоя
  (И46/И47: ASN/подсеть, история замен IP, политика хостера, IPv6 для
  OOB-1-запаса, NAT/L2 тип виртуализации) + pre-deploy тест пути (RU-клиент →
  ES-1 TCP/UDP-трассировка) до установки сервисов.

## 3. Ограничения

«1 окно = 1 контур»; asv2 — только read-only операции; не ломать текущий
живой контур ноутбука (релей работает); клиентские правки vpnm — после
появления живого тихого exit (иначе релей-only нечем бэкапить); деплойные
команды на целевых узлах — по конвенции «bash = команды» (скрипты/руководство,
Python = логика).
