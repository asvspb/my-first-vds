# PROMPT-20261124-min-risk-priorities — мандат архлиду: приоритеты разработки при минимально-рисковой архитектуре

> **От:** vds-orchestrator, по решению владельца. **Дата:** 2026-11-24.
> **Контекст:** INCIDENT-20261124-asv2-tcp-blackhole.md (`3e70891`, §9 + ревью-1/2
> Gemini, ответ оркестратора `8209e59`/`99e85f0`). **Секреты:** нет.

## 0. Решение владельца (рамка мандата)

«Идея комбайна протоколов не работает». Подтверждено инцидентом: 4 публичных
транспорта на одном IP (Reality 443/tcp + Hy2 443/udp + XHTTP 8443/tcp, +
ранее CDN) не пережили ни ingress-фильтрацию транзита, ни SPOF одного
exit/хостера — при этом AWG-ноги релея работали весь день. Целевая рамка:
**архитектура с минимальными рисками** — минимум публичной поверхности,
минимум лиц, минимум точек, быстрый откат. Просьба: выдать ТЗ на следующий
цикл в этой рамке.

## 1. Что сдалось проверку (строить на этом)

- **RU-релей как вход** (ADR-007): внутренний IP, минимум граничного внимания,
  клиенты за релеем не замечают переезд exit — работало весь инцидент.
- **Две обфусцированные UDP-ноги релей→exit** (awg1 + wg-ws0, ADR-016) —
  живы при лежащем TCP.
- **Клиентский QR-конвейер** (vpn qr/conf, WP-QR4..8) и селектор носителей
  (P25) — инженерная база для «сменяемого exit».

## 2. Что провалилось (резать или радикально упрощать)

- **Комбайн протоколов на exit** (И49): разные сертификаты/лица на одном IP,
  ASN-SNI mismatch (DEFAULT_SNI=google), витрина из 4 сервисов = готовый
  отпечаток (ARCH-20261116 §1). Условие минимального риска: **≤ 2
  согласованных сервиса на узел, у exit за релеем — 0 публичных TCP**.
- **Один exit / один хостер** (И46/И47): SPOF доказан; кандидат DR-exit ES-1
  (Эстония) — вне окон, до вердикта тикета ptr.network.
- **Мониторинг изнутри** (P37/P31/P32): слепые пиксели подтверждены на двух
  узлах подряд (23.11 релей, 24.11 asv2).

## 3. Вопросы архлиду (ответы = ТЗ на цикл)

- **Q1-PRI. Радикальный минимум exit**: согласовать ли профиль «тихий exit» —
  снаружи только AWG-пулы для IP релея (51825/udp от клиентов direct и
  51900–51911 + wstunnel-9443 с релея), публичный TCP на exit **отсутствует
  как класс**; весь клиентский вход — через RU-релей (Reality/tcp 443 на
  релее, мобильные — relay:443 как Эшелон 1 до вердикта Q4-INC). Альтернатива,
  если прямой TCP-вход владельцу нужен: ОДИН Reality на выделенном узле с
  Self-SNI (И48) — отдельная нода, не exit-за-релеем.
- **Q2-PRI. Судьба транспортов**: что из комбайна резать — Hy2 (очистый QUIC
  443/udp, obfs/hop не задеплоены), XHTTP 8443 (xhttp-web), CDN (уже Q6)?
  Критерий: транспорта нет на exit — QR/профили клиентов отзываются
  (`vpn profile`), а не висят мёртвыми.
- **Q3-PRI. Приоритетный порядок до ACCEPT-G6**: подтвердить/править план
  (1) ES-1 → DR-репетиция смены ноги; (2) P37-разворачивание (2 vantage);
  (3) runbook Q2-INC; (4) P30 (деплой релея ≤ 10 мин, второй RU-релей);
  (5) §6 → Q4-INC ретест андроида; (6) дамп G6 → ACCEPT-G6; (7) A2
  client-only (И44+И45+И51). Что из этого поднять в приоритете, что отложить?
- **Q4-PRI. P38 vs новый ADR**: failover exit-A/exit-B (TECHDEBT P38) —
  расширение ADR-016 или отдельный ADR-017 (сменяемый exit как first-class)?
- **Q5-PRI. Критерии «минимального риска» в цифрах**: согласовать KPI —
  MTB (И50) на каждый транспорт, поверхность = число публичных портов/лиц
  на узел, DR = время смены exit (цель ≤ 15 мин), окно-протокол для пилотов
  (NaiveProxy И52, Self-SNI И48 — только на почасовых тестовых нодах).
- **Q6-PRI. Прямые direct-профили клиентов** (Reality/Hy2-direct): выводить
  из эшелонов (аргумент: 24.11 прямые TCP ушли первыми, у релейных — 100%
  живучесть) или держать как Эшелон 3 с оговоркой «только стабильные пути»?

## 4. Ограничения (не пересматривать)

Гейты TEAM.md; «1 окно = 1 контур»; A2 = client-only (И44+И45+И51) до
вердикта по расхождению из ORCH-RESPONSE §6; asv2 — доступ через чёрную дыру
транзита (TCP-деплойные операции только после снятия/смены IP); миграционные
операции — по плану Q3-INC (послойный cutover, рестарт awg1+policy).
