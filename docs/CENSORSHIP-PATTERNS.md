> Сводка всех рассмотренных/внедрённых паттернов против RKN/TSPU-блокировок,
> с живыми доказательствами из эксплуатации (asv1, Volgograd ISP, ноябрь 2026).
> Дополняет [VPN-PROTOCOLS.md](VPN-PROTOCOLS.md) (протоколы) и

## 0. Контекст угроз (что именно наблюдали)

| угроза | живой факт (2026-11) |
|---|---|
| TSPU-троттлинг TCP к заруб. IP | XHTTP:8443 TLS-handshake висел часами, потом отпускало |
| Полный блок IP (TCP+UDP+ICMP) | asv1 11:30–12:xx: сервер жив извне (check-host), для нас мёртв |
| SNI-drop | zapret 30+ desync-стратегий не пробили youtube — режется ClientHello |
| NXDOMAIN/in-path DNS-перехват | `dig @1.1.1.1` отвечал яндексовскими адресами; youtube через plaintext-DNS «не найден» |
| Избирательная блокировка сервисов | telegram: IP/DNS-блок напрямую |
| «Юнит active ≠ туннель жив» | состояния путаются — нужны пробы, а не статусы |

## 1. Реализованные паттерны (с доказательствами)

### 1.1 Reality — TLS-маскировка крапом чужого сертификата
`vless+reality, TCP 443, sni=чужой белый сайт`. Трафик неотличим от TLS к
настоящему google; блокировка сломала бы сам Google. Жив на каналах, где
XHTTP/Hysteria2 душатся. Нюанс 2026-11: маскировка под **зарубежный** сайт с
домашнего IP — сама по себе подозрительна для TSPU (см. §2.7 RU-маскировка).
Профиль `phone`; Reality-gate — обязательный блокер приёмки любых изменений.

### 1.2 Hysteria2 — QUIC/UDP-транспорт
UDP лучше переживает потери и TSPU-троттлинг TCP (в окна душения TCP asv1
AWG-UDP продолжал работать). Быстрейший профиль, когда не задавлен
(длинный высокоскоростной UDP — самый заметный и легче всего шейпится:
рекомендация — видео на Reality, скорость на Hysteria2). Профиль `mob`.

### 1.3 XHTTP — HTTP-мультиплексирование
Обычные HTTP-запросы с телом-пакетами; но **нестандартный порт (8443)
притягивает DPI-давление** (два эпизода задушения). Крайний резерв из
socks-профилей; порт локализован флагом.

### 1.4 CDN-транспорт: VLESS+WS+TLS за Cloudflare ⭐ канал выживания
`asvpersonal.ru:2053, ws /cdnws, Full (strict)`. Клиентский трафик идёт до
**CF edge** (104.21.x/172.67.x), CF→origin из своих ДЦ — **полный блок IP
asv1 провайдером каналу не страшен** (проверено тем же днём). Цена: CF-хоп
~2.4 с (free). Правки против SPEC-плана: домен `asvpersonal.ru` вместо
непереносимого `eu-cloud-xip.com` (NS у хостера — ловушка: CF требует смену
NS на уровне реестра, недоступную владельцу субдомена), **апекс** вместо
`cdn`-поддомена. Слабое место: DoH-upstream/WS-цепочка — SPOF в TSPU-окна
(лечится fallback-деградацией, см. 1.6). Команды: `vpn scheme cdn` /
`vpn up cdn-home` (socks 2081). SPEC §11, ADR-006.

### 1.5 AmneziaWG + доменный split — системная маршрутизация по зонам
Обфусцированный UDP-туннель (`vpn-awg-split@laptop`) + dnsmasq/nft/fwmark:
зоны из `/opt/awg-split/domains.txt` (ходовые TLD **com/org/net/io/dev/ai**
+ youtube/telegram/google) — через туннель; GLM-кластер (`z.ai` и др.) и RU —
напрямую через **exclude-набор**. DNS-цепочка (resolved→dnsmasq→cloudflared)
— **обязательная часть** split'а (наполняет nft-set) с fallback
`strict-order + 77.88.8.8` (деградация вместо смерти DNS в TSPU-окна).
**Два неочевидных root cause**, без которых mark-маршрутизация не работает:
- **masquerade обязателен**: fwmark-перенаправление меняет интерфейс, но не
  source-адрес сокета (выбран по main-таблице = LAN-IP) → в туннель уходили
  SYN с LAN-адресом, сервер не мог ответить. Фикс: postrouting masquerade в
  туннельную подсеть. Диагностический приём: `curl --interface <tun>` работает,
  а через mark — нет → tcpdump src на туннеле.
- **rp_filter**: strict ронял ответные пакеты (reverse-lookup в main) →
  `sysctl net.ipv4.{all,<iface>}.rp_filter=0` в скрипте.
Команды: `vpn scheme awg` / `vpn start`; демонтаж `vpn reset`.
Открытый gap: паттерн имени интерфейса в monitor (исправлен: источник истины
`awg show interfaces`). **Третий root cause (2026-11-12): DNS-based split слеп
к хардкод-IP-приложениям.** Telegram — уникальный случай: клиент коннектится
к захардкоженным DC-адресам (149.154.x, 91.108.x) МИМО DNS → доменный split
(nftset через dnsmasq) их не видит → трафик напрямую → блок (симптом: TG мёртв
при живом youtube — youtube DNS-разрешим). Фикс: статические официальные
диапазоны TG в nft-set (`STATIC_ROUTES_NETS` в 15_domain-split.sh: 91.108.4-20/22,
91.108.56/22, 149.154.160.0/20 + 3×IPv6) — вне DNS-механики. Принцип общий:
любое приложение с вшитыми адресами требует статических диапазонов в set. ⚠️ Утечка браузерного DoH (ревью 2026-11-11): если
Chrome/Firefox резолвят встроенным DoH в обход dnsmasq — nft-set голодает и
браузер идёт напрямую в блок. Закрыто системными managed-политиками
(`/etc/opt/chrome/policies/managed/vpn-manager.json`: DnsOverHttpsMode off,
BuiltInDnsClientEnabled false; `/etc/firefox/policies/policies.json`:
DNSOverHTTPS locked off) — применять на любой машине со split'ом.

### 1.6 DNS-деградация вместо DNS-блока
Единственный апстрим = SPOF (TSPU-окно: CF таймаутил минутами → умирал весь
DNS). Фикс: dnsmasq `strict-order` + второй plaintext-сервер 77.88.8.8 — при
флапе CF резолвинг деградирует на Яндекс (заблокированные домены не откроются,
всё остальное живо). Общий принцип: **жертвуем заблокированным доменом, а не
доступностью**. Boot-guard (`vpn doh guard on`) гарантирует провайдерский DNS
при загрузке — drop-in не переживает ребут.

### 1.7 repair — самодиагностика и авторемонт «полного блока»
`vpn repair`: полный снимок (DNS-стек, dig-пробы 4 резолверов, сервисы,
порты, канал провайдера) → лог; затем авторемонт DNS (гасит мёртвую цепочку,
живой резолвер через managed drop-in) — **без nano в resolved.conf**.
Урок-паттерн: «полный блок» чаще мёртвый DNS, чем заблокированный канал;
сначала `vpn repair`, потом паника.

### 1.8 probe/monitor — наблюдаемость и ложные состояния
`vpn probe`: медиана 3 замеров, strict-fail, early-exit после первого фейла
(63 с → 31 с), прогресс в stderr. Ловушка «probe сразу после `vpn up`» —
первая проба не дожидается рукопожатия. `vpn monitor`: 6 каналов; строка
`amneziawg` показывает схему split (N зон), `cdn` — состояние резерва даже
когда он остановлен. Принцип: **юнит active ≠ туннель жив** — только пробы.

### 1.9 Схемные пресеты — симметрия вкл/выкл
`vpn scheme awg|cdn|proxy <p>|private <p>` ↔ `vpn reset`.
`private` = профиль поднят, sysproxy НЕ тронут, socks-адрес для точечного
подключения (расширение браузера/отдельный профиль Chrome/vpncli/ curl).
Политика чистого старта: при загрузке — только провайдер, всё VPN вручную.

### 1.10 vpncli — per-tab прокси в терминале
env-прокси одной вкладки (`vpncli on [порт]`), авто-порт из state, canary с
откатом (мёртвый прокси не остаётся в сессии). Урок: env-хвосты живут в
вкладке; `socks://`-схема = SOCKS4 = молча сломанная вкладка; только `socks5h://`
(remote DNS).

## 2. Паттерны ландшафта (рассмотрены, статус)

### 2.1 RU-relay («домашний» релей) ⭐ главный кандидат
Ноутбук → AWG → **RU VDS** → WG/любое → foreign exit. Ноутбук вообще не
касается foreign-IP → блоки того IP не страшны в принципе. Быстрее CDN (нет
CF-хопа). ⚠️ Нюанс ревью: «domestic UDP не трогают» — не абсолют: ТСПУ на
стыках транзитных операторов внутри РФ периодически включает профили
блокировки WG/OpenVPN **по сигнатурам даже внутри страны** (заметнее на
мобильных сетях). Поэтому плечо ноутбук→RU VDS — только **AmneziaWG**
(чистый WG уже нельзя), и на RU-релее держать запасной TCP-инбаунд (Reality
до локального RU-сайта — там RU-SNI раскрывается идеально). Цены: RU-хостер
знает о туннеле (метаданные, юрисдикция РФ), ~150–300₽/мес, +5–20 мс.
Решение — за владельцем (ADR-007 при решении).

### 2.2 CF Workers (serverless ingress) ⭐ следующий код-кандидат
VLESS как Worker-скрипт: клиент → CF edge → Worker → origin. Origin видит
только внутреннюю сеть CF; **WS-блок на origin-домен не убивает канал**
(Workers живут на edge). Бесплатно (~100k req/сут). Логичное продолжение
ADR-006 на том же exit-сервере.

### 2.3 XHTTP packet-up за CF (SPEC ADR-006 future)
Packet-up-режим XHTTP маскируется под обычные HTTP-запросы — переживает
блокировку WS на edge. Продолжение на текущем инблэнде.

### 2.3a ECH-ловушка Cloudflare (проверено 2026-11-11: была активна!)
CF автоматически включает **ECH** (Encrypted Client Hello): в HTTPS-записи
домена публикуется параметр `ech=` → современные клиенты шлют ClientHello с
расширением type 0xfe0d, которое **TSPU режет**. Симптом: флапы задержки
канала (0.5с ↔ 5с) у части клиентов. На `asvpersonal.ru` ech= был активен —
выключение: CF-панель → SSL/TLS → Edge Certificates → **Encrypted
ClientHello: Off**; контроль: `dig +short HTTPS asvpersonal.ru` — параметр
ech= должен исчезнуть. Также не привязываться к `*.workers.dev` (дефолтные
домены под ECH-раздачей) — только свой домен. Сопутствующий риск: CF-пулы
(104.21.x/172.67.x) со временем могут троттлиться точечно — кандидат-скрипт:
скан живых edge-IP + локальная подстановка через dnsmasq/`--resolve`.

### 2.4 Второй exit-гео
Один непокрытый класс отказа — **сам asv1** (хостер/отключка). Второй VDS
(другая юрисдикция) + `11_vds-deploy.sh` (one-shot) + `20_vds-migrate.sh`
(перенос state) = полный дубль стека за ~15 минут. Диверсификация юрисдикций.

### 2.5 MTProto-proxy (Telegram-специфичный)
Нативный протокол TG; держится, когда остальное зарезано. Установка одна
команда; вне vpnm (телефон).

### 2.6 Tor bridges (obfs4/webtunnel) — аварийный люк
Единственный слой без единой вашей точки (нет VDS/CF/домена). Не для работы —
для «если всё, включая CF». 0₽.

### 2.7 Смена маскировки Reality (поправлено ревью 2026-11-11)
Сейчас Reality с домашнего IP «ломится на google» — подозрительно. Но
**не** RU-сайт: (а) трафик к чисто российским ресурсам не должен уходить в
зарубежные AS — SNI ozon.ru на foreign IP для TSPU аномальнее, чем google;
(б) geo-fencing — RU-сайты капчуют/отбрасывают зарубежные IP, asv1 не сможет
стянуть реальный сертификат для handshake. Правильный dest: зарубежный
CDN/ресурс, легально используемый из РФ, **желательно в той же подсети/ДЦ
(или стране), что и asv1**, TLS 1.3 + H2. Отдельный бонус: RU-релей (§2.1)
с Reality до **локального RU-сайта** — там RU-SNI раскрывается идеально
(RU→RU). Малый WP.

### 2.8 Зарубежный eSIM — физически неблокируемый канал
Чужой оператор = чужой TSPU. Дорого ($1–3/ГБ) — только аварийный админ-канал
к серверам (сегодняшние блоки ssh бы закрыл).

### 2.9 Ротация портов/путей
Душение привязано к порту (8443 дважды). Два параллельных порта на инблэнде +
probe перебирает. Дёшево, почти покрыто.

### 2.10 Не внедрять (отвергнуты с причинами)
- **classic domain fronting** — мёртв (SNI-проверка у CDN)
- **Shadowsocks/Trojan в чистом виде** — фингерпринтится TSPU; есть строго
  лучше (Reality/AWG)
- **zapret/DPI-desync на этом ISP** — доказано иммунен (SNI-drop, 30+
  стратегий UNAVAILABLE); установлен-выключен, ревизия blockcheck раз в
  пару месяцев
- **I2P/децентрализованные сети** — экзотика, не для работы

## 2a. Заметность каналов для DPI (анализ 2026-11-12)

Два слоя «незаметности»: **(a) протокольная** — чем handshake отличается от
нормального трафика; **(б) поведенческая** — объём/ритм/энтропия/репутация IP.
ТСПУ сегодня живёт в основном слоем (a) — сигнатуры и списки; слой (б) —
растущая угроза (эпизоды адресного троттлинга asv1 — уже элемент (б)).

| канал | (a) DPI-handshake | (б) поведение | суммарно |
|---|---|---|---|
| **Reality** | невидим (форж handshake к реальному сайту) | долгие TLS-сессии к foreign IP — видны как аномалия 2-го порядка | ⭐⭐⭐⭐ |
| **CDN-WS** | обычный HTTPS к CF-IP (рутина миллионами) | WS-стрим — обычное веб-приложение | ⭐⭐⭐⭐⭐ |
| **AWG** | сигнатур нет (обфускация) | высокоэнтропийный UDP к одному IP — классический VPN-профиль | ⭐⭐⭐ (пока ТСПУ сигнатурный) |
| Hysteria2 | QUIC-маска, но к нелеловому IP | громкий sustained UDP — шейпится первым | ⭐⭐ |
| XHTTP:8443 | HTTP норм | нестандартный порт — маркер (душился дважды) | ⭐⭐ |

Выводы:
- Парадокс основного канала: AWG статистически заметнее Reality/CDN, но
  выбран за **живучесть** (работает в TSPU-окна, когда «тихие» мертвы).
  Незаметность без живого канала ничего не стоит.
- Росток риска AWG: при переходе ТСПУ к поведенческому анализу UDP —
  лечение: смена обфускационных параметров (Jc/порт), UDP-over-TCP.
- Опция «тихого» Hysteria2: **obfs salamander** (маскировка UDP под шум;
  в проекте НЕ реализована — обе стороны протокола поддерживают из коробки;
  кандидат-WP: сервер `obfs:` + share-link `obfs=salamander`, клиент-парсер;
  rollout — новый порт + obfs одновременно, старый порт гасить после
  пере-импорта ссылок клиентами).
- ECH-слои: браузеры с DoH пробуют ECH (extension 0xfe0d — режется ТСПУ);
  на ноутбуке закрыто managed-политиками DoH off (см. §1.5), на телефоне —
  выключить «защищённый DNS» вручную.
- **Exclude-принцип (дополнение 2026-11-12): инструментальные домены — в
  exclude по умолчанию.** Туннель — для контента, а не для разработки:
  git-хостинги (github.com/api/codeload/objects), pypi/pythonhosted и прочие
  инструменты, НЕ блокируемые РКН, должны идти напрямую — через asv1 это
  лишний хоп с деградацией (живой случай: git push через AWG→asv1→github
  буксовал; прямой путь — 1.4 c). Exclude-набор (`/opt/awg-split/exclude.txt`)
  = GLM-кластер + pypi + github-кластер; при добавлении нового
  инструментального сервиса — сначала exclude, туннель только если он реально
  заблокирован. Проверка: `dig @127.0.0.1 <домен>` → IP попал в nft excluded,
  curl --noproxy быстрый.

### 2.11 Обзор рынка коммерческих TG-VPN (видео «Дэви», 2026-11-12: 100 ботов)

Воронка 100 → ping(-26) → **обход белых списков(-56!)** → скорости(-9) →
цена/UX(-4) → топ-5 (Quatra, Velvet, Skip, Nsock, Durev). Выводы для стека:
(1) 82% коммерческих TG-VPN не проходят базовые проверки — подтверждение
self-hosted стратегии; (2) **новый вектор: mobile whitelist** (режим
оператора «только RU-ресурсы») — убивает все каналы с foreign входной точкой
(socks-профили, CDN — CF edge не в списке); единственное покрытие —
**RU-relay** (ещё один аргумент ADR-007); (3) «автоподбор» у топов = наш
`vpn probe`; (4) exit-IP-проверка нейросетей (Gemini) = наш egress-тест.

| угроза | покрывает |
|---|---|
| TSPU-троттлинг TCP | Hysteria2 (UDP), AWG (UDP), CDN |
| Полный блок IP foreign | CDN ✅, RU-relay, CF Workers, eSIM |
| SNI-drop / DPI-фингерпринт | Reality, AWG-обфускация, packet-up |
| DNS-подмена/перехват | DoH (dnsmasq-цепочка), remote-DNS через socks5h |
| Блок протокола (WS/QUIC) | XHTTP packet-up, второй транспорт в probe |
| Отказ своего exit-VDS | второй exit-гео, CDN (origin не единственная нога) |
| Отказ CF | RU-relay, socks-профили, Tor (люкс-кейс) |
| Mobile whitelist (только RU-ресурсы) | RU-relay (ADR-007, W-soft); W-strict — полевой test-plan |
| «Всё сразу» | Tor bridges + зарубежный eSIM |

## 3a. IP-троттлинг: механика и контрмеры (2026-11-12)

Троттлинг привязан к **координатам пути** (src-IP резидента ↔ dst-IP сервера,
иногда ко всему dst-IP; эпизод 2026-11-11: ssh:22 и 443 легли одновременно —
душили по IP, не по порту). Прямолинейно не лечится: другой протокол/порт/
шифрование меняют содержимое, но не пару координат. Побеждается только
**обходом пути**:

| # | способ | механика | статус в проекте |
|---|---|---|---|
| 1 | сменить dst-IP | второй exit-VDS / ротация exit'ов: троттлинг адресный — новый IP чист | roadmap (второй exit-гео), переезд = MIGRATE-VDS |
| 2 | сменить src-путь | RU-relay: нога ноутбук→RU VDS domestic; RU VDS→asv1 = DC↔DC (другой класс политик) | ADR-007 кандидат |
| 3 | сменить видимое направление | CDN: dst = CF edge (троттлить = ломать CF региону), CF→asv1 из ДЦ CF | ✅ реализован (пережил полный блок IP) |
| 4 | port-hopping (частное) | помогает ТОЛЬКО при порто-специфичном шейпинге | опция Hysteria2 (range+DNAT) |
| 5 | сменить транспортный стек (частное) | TCP душили — AWG-UDP жил; это обход TCP-троттлинга, не IP- | ✅ основная схема |

Кандидат-WP **speed-probe**: троттлинг виден только на bulk-трафике —
generate_204 (204 байта) быстр даже под душением, поэтому probe слеп к
«тихой деградации» (известный GAP). Лечение: в probe добавить speed-sample
(1–2 MB на профиль, сравнение MB/s) → автоматическое переключение при
деградации пропускной способности.

## 3b. Модель обнаружения DPI и пределы необнаружимости (2026-11-12)

### Как обнаруживают VPN-трафик — 4 слоя

1. **Протокольные сигнатуры (DPI)**: известные handshake'и (WireGuard 148/92-байт
   структура, OpenVPN-TLS, IKE), фиксированные порты, JA3/JA4-фингерпринт TLS,
   не совпадающий с браузерами.
2. **Статистический/поведенческий анализ**: энтропия payload; форма потока —
   туннель несёт ВСЁ (видео+чаты+обновления вперемешку), двунаправленный,
   круглосуточный, keepalive через равные интервалы — на «человеческий
   веб-серфинг» не похоже; репутация адресата (DC-подсети, ASN VPN-провайдеров,
   постоянство пары домашний IP → один DC IP).
3. **Активное зондирование**: ТСПУ стучится на подозрительный IP:порт и
   классифицирует по реакции (WG — специфичный ответ на валидный initiation,
   OpenVPN — RST, Shadowsocks — молчание).
4. **Обогащение данных**: списки VPN-ASN, cert-transparency, корреляция
   «домен зарегистрирован → поток резидентских IP на один DC-IP».

### Теоретический предел

Против глобального пассивного наблюдателя (виден обе стороны) необнаружимость
**доказуемо недостижима** — корреляция времени/объёма входа и выхода выявляет
туннель при идеальном шифровании. Личный сервер с постоянным адресом всегда
оставляет «след существования». «Практически необнаружимый против ТСПУ-2026» —
достижимо: слой 1/3/4 закрываются полностью, слой 2 — частично.

### Принципы проектирования «максимально тихого» стека

| принцип | нейтрализует | в проекте |
|---|---|---|
| Занять чужой протокольный endpoint (форж handshake реального сайта) | слой 1 | ✅ Reality |
| Ехать по массовой инфраструктуре (поток = миллиарды запросов к CF) | слои 1/3/4 | ✅ CDN |
| Туннель внутри настоящего TLS (наблюдатель видит нормальные TLS-байты; энтропийная аномалия не торчит наружу) | слой 2 (DPI-часть) | ✅ Reality/CDN; ❌ AWG (голая UDP-энтропия) |
| Зонд-защита origin (неверный SNI → ответ как настоящий сайт) | слой 3 | ✅ Reality-механика |
| On-demand туннели: нет 24/7-сессий и постоянных keepalive | слой 2 (поведение) | ❌ кандидат-WP |
| Шейпинг трафика «по-человечески» (pacing, паузы) | слой 2 | ❌ кандидат-WP (низкий приоритет: видео-через-туннель всегда будет стрим-профилем) |
| Дисперсия: ротация exit-IP, не одна пара «домашний→DC» месяцами | слой 4 | ❌ лечится вторым exit/RU-relay (roadmap) |
| DNS вне наблюдения (remote-DNS, DoH) | слои 2/4 | ✅ |

### Вывод

Стратегия «один невидимый канал» теоретически недостижима; **избыточность
живучих каналов** — достижима и реализована: противник, настроенный на
«идеальный» протокол, пропускает остальные. Резерв совершенствования —
поведенческий слой (on-demand, шейпинг, дисперсия); сигнатурный и
зондовый слои закрыты полностью.

## 4. Операционные принципы (из живых инцидентов)

1. **Никогда не доверять статусу юнита** — только сквозные пробы.
2. **Grace-period после старта** — рукопожатие не мгновенно (probe early-exit,
   повторные пробы).
3. **Деградация вместо блока** — fallback-апстрим DNS, exclude-наборы:
   жертвуя заблокированным доменом, сохраняем остальное.
4. **Мёртвый канал — не паника**: `vpn repair` (снимок+авторемонт) →
   `vpn monitor` (какая нога) → check-host (сервер жив извне?) → план Б.
5. **Миграция состояния, а не пересоздание** — state.json переносится
   (`20_vds-migrate.sh`), клиенты не перенастраиваются.
6. **Приёмка = живой e2e + Reality-gate** — любое серверное изменение не
   должно ломать существующие каналы (вычитающая интеграция).
7. **Чистый старт по умолчанию** — VPN вручную, boot-guard DNS, sysproxy
   сбрасывается при логине: любое «залипшее» состояние переживает ребут.
