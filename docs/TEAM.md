# TEAM.md — ролевая модель и процесс разработки

> Система ролей для VDS Orchestrator по образцу kino-club: чёткие артефакты,
> гейты, независимая верификация, контракт честности.
> Определения агентов — `.zcode/agents/`, контекст проекта — [../AGENTS.md](../AGENTS.md).

---

## 1. Принципы

1. **Один артефакт — один владелец.** Каждая роль пишет свой документ и не подменяет другие.
2. **Гейты, а не «по договорённости».** Нельзя начать следующий этап без выполненного гейта.
3. **Независимая верификация.** Тестировщик не доверяет отчётам кодера — проверяет сам.
4. **Контракт честности.** Честный partial уважается; фабрикация («тесты зелёные» без запуска) — табу.
5. **Малые партии.** Одна спецификация = одна ветка/PR = один набор гейтов.
6. **Трассируемость.** idea → req → spec → work package → коммит → тест → документ.
7. **Обратимость.** Деструктивные изменения — только с dry-run, бэкапом и планом отката.

## 2. Роли

| Роль | Агент | Что делает | Что НЕ делает |
|---|---|---|---|
| Владелец | `vds-owner` | Принимает идею, фиксирует ценность, приоритет, границы, бизнес-критерии | Не проектирует, не пишет код |
| Аналитик | `vds-analyst` | Переводит идею на технический язык: user stories, FR/NFR, тестируемые критерии | Не выбирает архитектуру |
| Архитектор | `vds-architect` | ТЗ/SPEC, архитектура, ADR, разбивка на work packages, распределение кодинга | Не пишет продовый код |
| Кодер | `vds-coder` | Реализует WP строго по SPEC, с pre-flight-доказательствами | Не меняет архитектуру и интерфейсы |
| Дебагер | `vds-debugger` | Воспроизводит баг, находит root cause, минимально чинит, пишет регрессионный тест | Не рефакторит соседний код |
| Тестировщик | `vds-tester` | Независимо проверяет по AC, пишет TEST-REPORT, заводит дефекты | Не правит продовый код |
| Документатор | `vds-docs` | Синхронизирует README/docs/CHANGELOG/AGENTS после изменений | Не придумывает поведение |
| Оркестратор | `vds-orchestrator` | Ведёт поток, запускает роли, держит гейты, ведёт STATUS и финальный отчёт | Не подменяет роли |

**Модели:** `vds-architect`, `vds-tester` — `glm-5.3` · `vds-debugger` — `deepseek-flash` · остальные — `glm-5.3-flash`. У всех `thoughtLevel: low`. Смена модели — только в frontmatter агента (`.zcode/agents/*.md`).

## 3. Поток и гейты

```
 IDEA ──G0──▶ REQ ──G1──▶ SPEC ──G2──▶ [WP-1..N] ──G3──▶ TEST ──G4──▶ DOCS ──G5──▶ CLOSE
  owner      analyst     architect        coders          tester       docs      orchestrator
                                ▲                              │
                                └────────── DEBUG ◀────────────┘ (при FAIL)
```

| Гейт | Условие прохода | Кто закрывает |
|---|---|---|
| **G0 Intake** | IDEA заполнена, приоритет и границы заданы, пользователь подтвердил | owner + пользователь |
| **G1 Ready** | REQ: у каждого требования есть тестируемый AC; нет открытых блокирующих вопросов | analyst |
| **G2 Spec** | SPEC: файлы, интерфейсы, тест-план, WP с DoD, риски; ADR для необратимых решений | architect |
| **G3 Build** | Для каждого WP — отчёт кодера с verbatim pre-flight; отклонений нет или раскрыты | coder → architect |
| **G4 Verify** | TEST-REPORT = PASS: все AC проверены, регрессии нет, доказательства приложены | tester |
| **G5 Docs** | DOC-REPORT: затронутые документы обновлены, ссылки целы, команды проверены | docs |
| **G6 Close** | STATUS обновлён, traceability-матрица заполнена, коммит/PR создан | orchestrator |

**Возвраты:** FAIL на G4 → `vds-debugger` → новая правка → повтор G3/G4 (макс. 2 цикла,
дальше эскалация к архитектору: возможно, дефект в SPEC). Неполный REQ на G1 →
возврат аналитику. Архитектурная проблема, обнаруженная при кодинге → стоп, возврат
архитектору, не «лечим на ходу».

## 4. Артефакты

Каталог `docs/team/`:

| Артефакт | Шаблон | Кто пишет | Где живёт |
|---|---|---|---|
| IDEA | `templates/IDEA.md` | owner | `docs/team/ideas/IDEA-YYYYMMDD-<slug>.md` |
| REQ | `templates/REQ.md` | analyst | `docs/team/requirements/REQ-YYYYMMDD-<slug>.md` |
| SPEC | `templates/SPEC.md` | architect | `docs/team/specs/SPEC-YYYYMMDD-<slug>.md` |
| ADR | `templates/ADR.md` | architect | `docs/adr/ADR-NNN-<slug>.md` |
| TEST-REPORT | `templates/TEST-REPORT.md` | tester | `docs/team/reports/TEST-<slug>.md` |
| DEBUG-REPORT | `templates/DEBUG-REPORT.md` | debugger | `docs/team/reports/DEBUG-<slug>.md` |
| DOC-REPORT | — (в отчёте агента) | docs | `docs/team/reports/DOC-<slug>.md` |
| STATUS | `templates/STATUS.md` | orchestrator | `docs/team/STATUS.md` |

**Traceability:** в SPEC — таблица «REQ → WP → файлы → тесты»; в STATUS — «IDEA → REQ →
SPEC → коммиты → TEST/DOC».

## 5. Определения

**Definition of Ready (для SPEC):**
- IDEA и REQ существуют, ссылки взаимные;
- у каждого FR есть AC в формате «Given/When/Then» или проверяемое утверждение;
- NFR зафиксированы (безопасность, идемпотентность, root, downtime, откат);
- границы «что не делаем» явные.

**Definition of Done (для WP):**
- код соответствует SPEC и конвенциям `AGENTS.md`;
- `python -m compileall -q src` — exit 0; `pytest -q` — exit 0 (или явно «тестов нет»);
- изменения в `git status --short` совпадают с заявленными;
- секреты не в логе/коде/share-link; файлы 0600;
- для деструктивного функционала — dry-run и подтверждение;
- TEST-REPORT PASS; DOC-REPORT выполнен;
- коммит в Conventional Commits.

## 6. Контракт честности (для всех ролей)

1. **Honest partial > fake complete.** Частичное выполнение с честным списком пробелов
   приветствуется. Фабрикация результатов — единственное табу.
2. **Верификация фактом.** Любое «работает / зелёное / создано» подкрепляется verbatim-
   выводом команды. «Должно работать», «по логике верно» — запрещены.
3. **Stale-state запрещён.** Pre-flight — после финальной правки, не «час назад».
4. **Отклонения раскрываются.** Любое расхождение с SPEC — отдельной строкой в отчёте.
5. **Блокер сообщается сразу.** Молчание о блокере хуже блокера.
6. **Suppress-обходы раскрываются.** `# type: ignore`, пустой `except`, отключённый тест,
   `shell=True` в новом коде, `--no-verify` — только с обоснованием в отчёте.

## 7. Лучшие практики, зашитые в процесс

- **Shift-left:** AC пишутся аналитиком до SPEC, тест-план — архитектором до кодинга.
- **Test pyramid:** unit (чистые функции) → integration (Docker) → ручная приёмка на VDS.
- **Bug → сначала падающий тест**, потом фикс (debugger обязан приложить регрессионный тест).
- **Adversarial review:** тестировщик ищет способы сломать, а не подтвердить.
- **Failure injection:** тесты на обрыв сети, занятый порт, битый JSON, повторный запуск.
- **Идемпотентность как тест-кейс:** каждая install-команда прогоняется дважды.
- **Security gates:** проверка отсутствия секретов в выводе, права 0600, UFW-политика.
- **ADR для необратимых решений** (выбор протокола, портов, схемы хранения секретов).
- **Traceability matrix** — единый источник правды о состоянии работ.
- **Small batches** — один SPEC = один PR; ревью меньше, откатывать проще.

## 8. Запуск ролей

Оркестратор запускает роли через инструмент Agent с `subagent_type`:
`vds-owner`, `vds-analyst`, `vds-architect`, `vds-coder`, `vds-debugger`,
`vds-tester`, `vds-docs`, `vds-orchestrator`.

Кодеров можно запускать параллельно (несколько копий `vds-coder`) на независимых WP;
WP, затрагивающие одни и те же файлы, выполняются последовательно.

**Типовые сценарии:**

```text
Новая фича:
  vds-orchestrator → vds-owner → vds-analyst → vds-architect
  → vds-coder (×N) → vds-tester → [vds-debugger] → vds-docs → close

Исправление бага:
  vds-orchestrator → vds-debugger → vds-tester → vds-docs → close

Только документация:
  vds-orchestrator → vds-docs → close
```

---

## 9. Куда не лезем без отдельного SPEC

Публичные интерфейсы CLI (имена команд/флагов), формат `topology.json`, схема хранения
секретов, права файлов, политика портов/UFW, systemd-юниты. Изменение любого из них —
только через REQ → SPEC → ADR.
