# ADR-016 — p2p link: несколько L4-ортогональных носителей между двумя узлами + failover

- **Статус:** 🟡 **предложен** (draft, входной гейт G2). Код не пишется до G2.
- **Связано:** ADR-015 (изоляция ноги `awg2` + манёвр портов), ADR-007 (RU-relay),
  ADR-008 (статический пул портов + REDIRECT), AGENTS §6 (граница доверия)
- **Заменяет:** — (расширяет ADR-015: тот же p2p-путь, но носителей несколько)
- **Нумерация:** ADR-016 закреплён за p2p link. Клиентский Smart Failover (D-24/Q4)
  пойдёт на **ADR-017+**.

## 1. Контекст

Сегодня нога relay↔exit — один носитель: `awg2` на UDP/51900 с внутренним
манёвром портов по пулу 51900–51911 (P24/P25, автопилот 60 с). Манёвр закрывает
класс «блок конкретного 5-tuple», но **не закрывает** два случая:

1. **Блок всего UDP-пула** до exit-узла — пул конечен (12 портов), и перебор
   портов бесполезен, если режут весь UDP к IP.
2. **Блок UDP-протокола целиком** на магистрали RU→NL.

Полевой опыт (схема владельца, работает годами без DPI-блокировок): между двумя
узлами держат **два носителя одновременно** — L4-ортогональные — и переключают
маршрут при отказе активного. Серверы те же, меняется только носитель.

Ключевое свойство схемы: границу пересекает **серверный TLS**, а не клиентский
протокол. Клиент по-прежнему ходит AWG на RU-узел (домашний IP, не цель фильтра),
а `RU-узел → NL` — это обычный HTTPS/TLS-поток.

## 2. Топология и per-carrier NAT

```
клиент ──AWG(udp/443)──> [RU-релей] ──┬── awg1   (UDP/51900…51911, 10.11.0.0/30) ──┐
                                      └── wg-ws0 (WG поверх wstunnel/TLS,           │
                                                  TCP/<ws-port>, 10.12.0.0/30) ─────┤
                                                                                    ▼
                                                                              [NL, exit]
```

**Инвариант маршрутизации (обязателен, иначе одностороннее переключение не работает):**
каждый носитель имеет **свою /30-подсеть** и **свой MASQUERADE** на выходном
интерфейсе релея:

| Носитель | Интерфейс релея | Подсеть | NAT на релее |
|---|---|---|---|
| awg (UDP) | `awg1` | `10.11.0.0/30` | MASQUERADE на `awg1` |
| wstunnel-wg (TCP/TLS) | `wg-ws0` | `10.12.0.0/30` | MASQUERADE на `wg-ws0` |

Тогда exit видит `src` из подсети **того** носителя, по которому пришёл пакет, и
возвращает ответ строго в тот же интерфейс — без динамического роутинга на exit.

**Exit-сторона для `10.12.0.0/30` обязательна** (те же три элемента, что у `awg2`
в `src/relay/exit_leg.py`):

1. выделенный WG-интерфейс `10.12.0.1/30`, слушающий **только** `127.0.0.1:<wg-ws-port>`
   (либо `input drop` на WAN для WG-порта) — на него нельзя прийти мимо wstunnel;
2. `postrouting`: `ip saddr 10.12.0.0/30 oifname "<wan>" masquerade` — иначе пакеты
   уйдут в WAN с приватным src;
3. `forward/UFW`: `route in on <exit-wg-ws> out on <wan>` allow.

Переключение на релее сводится к одной атомарной операции ядра:

```
ip route replace default dev <carrier_iface> table 100     # под FileLock
```

Без рестарта `awg0`, без переприменения nft, без правок на exit. Открытые
TCP-сессии клиентов переустановятся за 1–2 с (сменился SNAT ноги), сам
клиентский туннель `awg0` не рвётся.

## 3. Решение

**Фаза 1 (MVP).** Абстракция `p2p link` с двумя носителями и одним селектором
на RU-релее:

| Приоритет | Носитель | L4 | Роль |
|---|---|---|---|
| 1 (primary) | `awg` (существующий `awg2`/пул 51900–51911) | UDP | штатный путь, минимальный RTT; внутри — манёвр портов P25 |
| 2 (fallback) | `wstunnel-wg` (`wg-ws0` поверх wstunnel) | TCP/TLS | L4-ортогональный резерв при блоке UDP-пула/протокола |

`awg` остаётся **первичным**, потому что это kernel-space UDP без TCP-over-TCP
meltdown: WG-в-TCP при потерях на магистрали проигрывает голому UDP по задержке
и хвостам. Место wstunnel — именно резерв, а не «второй равноправный».

**Фаза 2 (опционально).** Адаптер `zerotier` в тот же интерфейс носителя — только
если ZT уже развёрнут для клиентского плеча.

## 4. Пять обязательных инвариантов (входной гейт G2)

### I-1. Изоляция порта wstunnel на exit (паттерн P24)

- Порт **не 443** (занят Reality). Кандидат — `8443/tcp` (XHTTP на asv2 снят)
  либо отдельный порт; выбор фиксируется при SPEC.
- UFW на exit: **строго** `allow from <relay-ip> to any port <ws-port> proto tcp`
  — как `51900/udp` в P24. Внешние сканеры получают **полную тишину** (ни
  утечки сертификата, ни демаскировки wstunnel, ни конфликта с SNI Reality).
- Defense-in-depth (не полагаться на порядок UFW/IPv6): тот же drop явно в nft
  (`chain input`, `priority filter - 1`, как `src/relay/exit_leg.py`):
  `ip saddr != <relay-ip> tcp dport <ws-port> drop` +
  `meta nfproto ipv6 tcp dport <ws-port> drop`.
- wstunnel-сервер запускается **только** с `--restrict-to 127.0.0.1:<wg-ws-port>`
  (запрет произвольного форвардинга).
- `ws_path` — **случайный секрет** (0600), без литеральных значений.

**TLS-сертификат: нужен настоящий LE на отдельном домене/поддомене** — и это не
для «красоты». Пассивный DPI на магистрали RU→NL видит TLS-хендшейк: в TLS 1.2
самоподписанный сертификат виден в ServerHello, в TLS 1.3 остаётся SNI, но
нерезолвящийся/поддельный SNI — сам по себе признак. Настоящий LE на реальном
домене делает поток неотличимым от обычного HTTPS. Домен не сцепляется с SNI
основного exit-канала.

### I-2. Единая иерархия автоматов — без конфликта с P25

Два независимых таймера, одновременно дёргающих `awg1` и `table 100`, **запрещены**.
Схема двухуровневая, под общим `FileLock`:

1. **Уровень 1 (внутри awg):** локальный манёвр портов пула P25 (как сейчас).
2. **Уровень 2 (селектор носителей):** переключение `table 100` на `wg-ws0`
   происходит на **первом `rollback`** манёвра P25 (отказ смены порта внутри UDP
   = признак блока пула/протокола), а **не** на `exhausted`.
3. **Возврат (`prefer_primary`):** пока трафик идёт через `wstunnel-wg`, редкий
   liveness-чек по `awg1`; возврат на `awg1` — только после **N=3** подряд
   успешных проб **и** cooldown **600 с** (анти-пинг-понг).

**Почему триггер — `rollback`, а не `exhausted` (арифметика `src/relay/maneuver.py`):**
при блоке всего пула и штатном тике 60 с — детекция `3/3` ≈180 с → попытка №1 →
`wait_liveness` 20 с → `rollback` → `COOLDOWN_S=600`; попытка №2 → ещё 600 с;
попытка №3 → `hourly_attempts >= MAX_ATTEMPTS_PER_HOUR=3` → `exhausted`
**≈22–25 минут**. Ждать этого значит потерять канал на полчаса. Поэтому:

- селектор реагирует на первый `rollback`;
- `exhausted` остаётся **терминальным**: оба носителя мертвы → уведомление
  владельцу, авто-переключений больше нет;
- итоговая задержка: `3/3` (≈180 с) + `wait_liveness` (20 с), верхняя граница
  **≤ 240 с** от блока.

**Проба активная, не пассивная:** `probe_liveness()` — это `ping -I awg1 10.11.0.1`
(`src/relay/maneuver.py`). Она работает потому, что:
- connected-маршрут `10.11.0.0/30 dev awg1` остаётся в **main**-таблице и
  переключением `table 100` не затирается;
- исходящие UDP-пакеты `awg1` идут через **output** — мимо `prerouting`
  и мимо `fwmark 0x1`.

### I-2a. Стыковка с существующей nft-таблицей и рестартом policy-юнита

- `render_nft_policy()` (`src/relay/config.py`) сейчас содержит
  `iifname "awg1" return` в `prerouting` и **не имеет** `chain forward`.
  При добавлении второго носителя обязательно:
  `iifname "wg-ws0" return` в `prerouting` и отдельная `chain forward`
  (`type filter hook forward priority filter`) с
  `tcp flags syn tcp option maxseg size set rt mtu`.
- `vds-relay-policy.service` при старте (ребут/рестарт) прописывает
  `default dev awg1 table 100` (`src/relay/init.py`). Инвариант: **активный
  носитель при старте берётся из state селектора** (селектор синхронизирует
  `table 100` при активации) — иначе после ребута трафик молча вернётся на
  мёртвый awg.

### I-3. Запрет петли маршрутизации wstunnel на релее

- Клиент wstunnel на релее подключается к `<exit-ip>:<ws-port>` через **main table
  (eth0)**, минуя `fwmark 0x1` / `table 100` — иначе туннель сам себя загонит.
- `wg-ws0` обязан иметь `Table = off` (урок `src/relay/config.py:sanitize_exit_conf`:
  иначе wg-quick перезапишет default в main и отрежет SSH).

### I-4. MTU и TCP MSS clamping

`awg0` на релее — MTU 1280 (`src/relay/init.py`). Поверх wstunnel (TLS + TCP + WS)
+ WG нужен:

- явный расчёт MTU для `wg-ws0` (минус заголовки WSS/TCP/TLS/WG от 1500);
- `tcp flags syn tcp option maxseg size set rt mtu` в forward-цепочке nft на
  релее — иначе клиентские HTTPS-фреймы упираются в PMTUD blackhole.

### I-5. Нумерация, non-goals и границы

- ADR-016 закреплён за p2p link; Smart Failover (D-24/Q4) → ADR-017+.
- **Non-goal:** схема **не закрывает** полный L3-блок IP exit-узла — оба носителя
  бьют в один IP NL. Для этого класса нужен второй exit/CDN-фронт.
- Граница доверия ADR-015/AGENTS §6 сохраняется: RU-релей **не получает**
  SSH/API/управляющих прав на exit; exit только пассивно принимает оба носителя.

## 5. Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| **IPv6-нога** (ADR-015 §7: жива, 47 мс, без новых сервисов) | Остаётся **UDP** — ложится вместе с IPv4-UDP при блоке протокола. Годится как дешёвый первый резерв, но не как L4-ортогональный |
| **TCP-Reality как носитель** | Не даёт L3-интерфейса: нужен SOCKS/tproxy-слой, `table 100` напрямую не переключить |
| **ZeroTier в MVP** | Тот же UDP/9993 (не ортогонален awg), хуже фингерпринт, тянет контроллер (Docker/ZTNET) и новую поверхность. Оставлен Фазой 2 |
| **Два равноправных носителя (без приоритета)** | TCP-over-TCP при потерях хуже UDP; переключение «куда попало» даёт флап |
| **Динамический роутинг на exit (OSPF/BGP)** | Нарушает границу доверия и добавляет сервис на exit; per-carrier /30 + NAT решает задачу дешевле |

## 6. Откат

1. Селектор: `ip route replace default dev awg1 table 100` (атомарно, FileLock).
2. Снять wstunnel-юнит и `wg-ws0` на релее; MASQUERADE `wg-ws0` удаляется юнитом.
3. На exit: `vds … wstunnel remove --apply` — снимает **и юнит wstunnel, и
   exit-интерфейс `wg-ws0` (10.12.0.1/30), и его NAT/forward-правила**, и
   UFW-правило порта. Одного снятия юнита недостаточно: интерфейс и NAT
   останутся висеть.
4. `awg2`/P25 не трогаются ни на одном шаге — они остаются рабочим путём.

## 7. Проверка (AC)

| # | Критерий |
|---|---|
| AC-1 | Внешний скан `<ws-port>` с чужих IP — **тишина** (как 51900/udp в P24) |
| AC-2 | При блоке пула 51900–51911 (runtime nft на exit): переключение на `wg-ws0` — **на первом `rollback`** P25, т.е. ≤ 60 с с момента rollback и **≤ 240 с** от блока (3/3 ≈180 с + wait_liveness 20 с); `exhausted` (~22 мин) триггером НЕ является; клиентский `awg0` не рвётся |
| AC-3 | Обратный маршрут без правок на exit: ответы приходят в тот же носитель (per-carrier /30 + MASQUERADE) |
| AC-4 | Нет петли: wstunnel-клиент релея идёт через main table; `wg-ws0` c `Table = off`; SSH жив |
| AC-5 | PMTUD: крупный HTTPS-поток (**> 1 МБ**) через `awg0 → wg-ws0` при MTU `wg-ws0` **< 1280** (например 1220–1240) идёт без зависаний и PMTUD-blackhole (MSS clamp работает). «MTU 1400+» неприменим: `awg0` уже 1280 |
| AC-6 | Возврат на `awg1` — только после 3 успешных liveness-проб и cooldown 600 с; пинг-понга нет |
| AC-7 | Один `FileLock`: P25-таймер и селектор не дёргают `table 100` одновременно |
| AC-8 | Документировано: блок IP exit обоими носителями не закрывается (non-goal) |

## 9. Последствия

- Класс «блок UDP-пула / блок UDP-протокола» закрыт на 100 % (L4-ортогональный
  резерв), без изменения клиентских конфигов.
- Появляется второй серверный сервис (wstunnel) и второй интерфейс (`wg-ws0`) —
  плюс MTU/MSS-возня и один LE-домен.
- Сложность растёт не в клиенте, а на релее: два автомата под одним локом.
- **alert-watch на exit ослепнет по ноге:** пульс релея читается с
  `ALERT_RELAY_IFACE=awg2`; когда трафик уйдёт на `wg-ws0`, `awg2` замолчит и
  сторож начнёт слать **ложные `relay_blocked`**. Обязательно в SPEC: либо
  поддержка **списка** интерфейсов ноги (пульс ok, если жив любой), либо
  переключение `ALERT_RELAY_IFACE` селектором. Пока не сделано — риск ложных
  уведомлений в момент первого же перехода на резерв.
- Фаза 2 (ZT) не блокирует MVP и добавляется в тот же интерфейс носителя.
