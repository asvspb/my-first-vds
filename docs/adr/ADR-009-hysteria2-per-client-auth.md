# ADR-009: Per-client auth Hysteria2 — HTTP-auth через локальный агент

- **Дата:** 2026-11-13
- **Статус:** proposed (ждёт цикла `W2` роадмапа; код не начат)
- **Контекст:** [GROWTH-POINTS GR-02](../GROWTH-POINTS.md), [VPN-PROTOCOLS §2.3](../VPN-PROTOCOLS.md)
- **Связанные:** ADR-002 (пути/юниты/state), ADR-004 (deploy-hook как
  перегенерируемый артефакт), ADR-008 (паттерн «именованный артефакт + oneshot»)
- **Затрагивает:** `src/hysteria2/`, `src/gateway/store.py`, `src/main.py`,
  `systemd/`, схему `state.json`

## Контекст

Сейчас Hysteria2 работает с одним `auth: {type: password, password: ...}` на
инбаунд: `src/hysteria2/clients.py` фиксирует это как ограничение модели
(«ОДИН auth-пароль на инбаунд»). Практические следствия:

1. `hysteria2 remove-client bob` удаляет запись из store, но **не отзывает
   доступ** — пароль остаётся в `config.yaml` и в ссылках остальных клиентов;
2. утечка ссылки одного клиента = компрометация всех;
3. ротация пароля возможна только «всем сразу» (и только через
   `rotate-obfs` для obfs-инстанса — для основного инбаунда команды нет).

Второй инстанс (`vds-hysteria2-obfs`, порт 51826) использует **тот же**
auth-пароль, т.е. ограничение удваивается.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **`auth.type: http` → локальный агент (выбран)** | штатный механизм hysteria2; отзыв мгновенный; пользователи в state (0600); не меняет формат share-link (`user:pass@`) | новый долгоживущий процесс на loopback; нужен токен агент↔сервер; +1 systemd-юнит |
| `auth.type: userpass` | проще всего: `password: "user:pass"`, ничего не запускать | пароли всё равно в одном файле; отзыв = правка конфига + рестарт; нет per-user метрик; hysteria2 сверяет только пару целиком |
| Перейти на инбаунд sing-box (native multi-user) | мультиюзер «из коробки», обфускация и hop тоже есть | смена ядра на живом сервере (риск для всех клиентов), другой формат конфига/юнита, переписывание install/status/remove, потеря `hysteria`-специфичных полей (masquerade/Brutal) — большой миграционный цикл |
| Оставить один пароль | нулевая работа | не закрывает архитектурный потолок; каждый отзыв = перевыпуск всем |

## Решение

1. **Auth-режим:** `auth: {type: http, http: {url: http://127.0.0.1:<port>/auth,
   insecure: false}}` — hysteria2 на каждый CONNECT делает POST
   `{addr, auth, tx}`; ответ 200 = доступ.
2. **Агент:** отдельный минимальный процесс `vds-hy2-auth` (stdlib `http.server`
   или aiohttp-free `socketserver`, без новых зависимостей),
   слушает **только loopback**, порт из `gateway/paths.py`
   (`HYSTERIA2_AUTH_PORT_DEFAULT`, первый свободный рядом с 51826).
   Аутентификация агента для hysteria2 — URL-путь с токеном
   (`/auth/<token>`), токен — секрет в `state.json` (0600), генерится install.
3. **Хранилище пользователей:** `state.protocols["hysteria2"]["users"] =
   {name: {"password": "...", "created": "..."}}`; пароль per-user
   генерируется `core.secrets.gen_password`. Схема state версионируется:
   `version` 1 → 2 с миграцией, которая заводит одного пользователя
   `default` с текущим `auth_password` (обратная совместимость ссылок).
4. **Ссылки:** `hysteria2://<user>:<password>@host:port/?...` (RFC-совместимо,
   поддерживается hysteria2, sing-box, v2rayNG). Для obfs-инстанса — тот же
   пользователь/пароль (один секрет на транспорт сохраняется), obfs-пароль
   остаётся отдельным.
5. **Команды:** `hysteria2 add-user NAME`, `remove-user NAME [--apply]`,
   `rotate-user NAME`, `rotate-password` (все существующие пользователи —
   новый пароль, ссылки перевыпускаются). Существующие `add-client` /
   `remove-client` сохраняют семантику store, но `remove-client` теперь ещё
   и отзывает пользователя в инбаунде.
6. **Юнит:** `systemd/vds-hy2-auth.service.tpl` (шаблон, `run_list`,
   `FileLock` на мутации state — как у остальных мутаторов). При падении
   агента hysteria2 отвечает 401 всем: это **fail-closed**, осознанно.

## Последствия

- Положительные: отзыв доступа в один шаг; утечка одной ссылки не ломает
  остальных; ротация per-user; появляется задел под трафик/учёт по
  пользователю (`/auth` видит имена).
- Отрицательные: +1 процесс и +1 конфиг-артефакт; при недоступности агента
  сервис фактически недоступен (fail-closed) — лечится healthcheck-таймером
  (GR-18) и `Restart=always`; ссылки меняют формат (старые пароли продолжат
  работать только через миграционного пользователя `default`).
- Обратная совместимость: state v1 читается миграцией; клиентские ссылки,
  выпущенные до миграции, продолжают работать (пароль `default`).
- Трудно изменить позже: выбор «HTTP-auth» фиксирует внешний контракт агента
  (путь/токен/JSON). Смена механизма — новый ADR.

## Миграция (план цикла W2)

1. `store.py`: `STATE_VERSION = 2`, миграция v1→v2 (пользователь `default` =
   текущий `auth_password`), тест на идемпотентность и на чтение v1.
2. `install.py`: рендер `config.yaml` с `auth.http` + токен агента; бэкап
   старого `config.yaml` (`.bak-pre-auth`); рестарт обоих инстансов.
3. `auth.py`: агент, `--check` режим (валидация state без запуска), лог без
   паролей.
4. `clients.py`: ссылки `user:pass`; команды add/remove/rotate-user.
5. `status.py`: «auth: http (N users)», проверка живости агента.
6. e2e на asv1: alice подключается, `remove-user alice` → 401, bob работает;
   obfs-инстанс — тот же сценарий; rollback на `.bak-pre-auth`.

## Как откатить

1. `vds hysteria2 auth-revert --apply` (в скоупе цикла): восстановить
   `config.yaml` из `.bak-pre-auth`, рестарт обоих инстансов; state остаётся
   v2 (агент просто не используется).
2. Полный откат кода — revert коммитов цикла; `state.json` v2 читается
   старой версией только после обратной миграции (снапшот `state.json.bak`
   делается перед миграцией).

## Открытые вопросы

- OQ-1: нужен ли per-user трафик в MVP агента (счётчик в памяти vs только auth)?
- OQ-2: оставлять ли `auth.type: password` как fallback флагом install
  (`--auth password|http`) или всегда http?
- OQ-3: токен агента — статический в state или ротация по timer (зависит от GR-18)?
