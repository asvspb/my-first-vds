# ADR-010: Обновление серверного Xray-core 25.1.1 → 26.1.23

- **Дата:** 2026-11-14
- **Статус:** accepted
- **Контекст:** [SPEC-20261114-xhttp-split](../team/specs/SPEC-20261114-xhttp-split.md);
  [TEST-20261114-xhttp-split](../team/reports/TEST-20261114-xhttp-split.md)
- **Связанные:** ADR-001 (механизм установки Xray), ADR-003 (XHTTP/Reality),
  [GROWTH-POINTS GR-06](../GROWTH-POINTS.md)

## Контекст

Xray `tun`-инбаунд (нужен для системного XHTTP-split) появился только в
**26.1.23**. Сервер asv1 был запинен на 25.1.1, и клиент 26.1.23 получал
`400 Bad Request` от XHTTP-инбаунда 25.1.1. Проверено: 26↔26 = 200; 26-клиент
через tun к 26-серверу = 200.

## Решение

Обновить серверный бинарь `/usr/local/bin/xray` до **26.1.23** (конфиг не
менять), с бэкапом `xray.bak-25.1.1` и `config.json.bak-xray25`.

## Последствия

- Положительные: XHTTP-split разблокирован; одна версия клиента/сервера;
  `xray -test` со старым конфигом — OK.
- Проверено после обновления на asv1: Reality (`phone`) 200/0.35 с через
  клиент 25.1.1; XHTTP 200/0.81 с; CDN 200/3.05 с; Hysteria2 200/0.29 с;
  tun-split в контейнере (26-клиент, 8443) — 200.
- Отрицательные: Xray 26 печатает предупреждения об устаревании VLESS без
  Flow и WS/Host-заголовков (не ломает, но следить за релизами); старые
  клиенты должны поддерживать 26-совместимый Reality (проверен 25.1.1).
- Откат: вернуть `xray.bak-25.1.1` на место и `systemctl restart vds-xray`;
  конфиг не менялся.

## Открытые вопросы

- Когда Xray уберёт VLESS без Flow/WS — потребуется миграция на Vision/XHTTP
  (отдельный цикл); сейчас только warning.
