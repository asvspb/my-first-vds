# ADR-006: CDN-транспорт VLESS за Cloudflare — DNS-топология, WS, порт 2053, Full (strict), без CF-API

- **Дата:** 2026-11-10
- **Статус:** accepted
- **Контекст SPEC:** [SPEC-20261110-cdn-transport](../team/specs/SPEC-20261110-cdn-transport.md)
- **Закрывает:** OQ-1..OQ-5 из [REQ-20261110-cdn-transport](../team/requirements/REQ-20261110-cdn-transport.md)

## Контекст

Живой asv1: Reality TCP 443 (клиент `phone`, доменная ссылка), Hysteria2 UDP 443
(клиент `mob`), XHTTP-direct vless+xhttp+tls **mode=port, публичный TCP 8443**,
path `/xhttp` (ADR-03/факт: `src/xray/config.py:27` `XHTTP_PATH = "/xhttp"`,
`src/gateway/paths.py:50` `XHTTP_INTERNAL_PORT = 8443`). Зона
`eu-cloud-xip.com` в NS регистратора (`ns1..ns4.eu-cloud-xip.com`), запись
`103-45-247-172.eu-cloud-xip.com` A → 103.45.247.172 grey-cloud (не в CF).

Главный риск REQ §1: включение CF-proxy на записях, которыми пользуются
direct-каналы, меняет DNS-ответ на IP Cloudflare → Reality и Hysteria2 по
доменным ссылкам ломаются, HTTP-01 certbot идёт через edge. Инвариант §4 REQ —
блокер приёмки.

## Решения (по OQ)

### OQ-1 — DNS-топология: отдельная proxied-запись `cdn.eu-cloud-xip.com`, апекс и `103-45-247-172` остаются grey-cloud

| Вариант | Оценка |
|---|---|
| CF-proxy на апексе / записи `103-45-247-172` | **отклонён** — прямо противоречит инвариантам §4: Reality-клиенты по доменной ссылке получат IP CF и не доедут до сервера; Hysteria2 (`sni=<домен>`) — то же; HTTP-01 уходит в edge |
| Второй домен (покупка) | **отклонён** — вне скоупа REQ §6 (покупка/оплата явно исключены) |
| **Отдельная proxied-запись `cdn.eu-cloud-xip.com` → A 103.45.247.172, orange cloud; апекс и `103-45-247-172` — grey-cloud (выбран)** | изоляция на уровне DNS-записи; отключение CDN-канала = выключение orange cloud, нулевой риск для остальных каналов; один домен, без затрат |

- **Перенос зоны в Cloudflare — ручное действие владельца** (смена NS у
  регистратора на ns1..ns3.cloudflare.com — скриптовать нельзя и незачем;
  чеклист переноса — SPEC §8). После переноса все прочие записи зоны
  обслуживает CF DNS — в чеклисте обязательный шаг «убедиться, что импортированные
  записи апекса и `103-45-247-172` в статусе DNS-only (grey)».
- Подтверждено (предложение координатора принято без переигровки).

### OQ-2 — транспорт за CF: WebSocket (v1), XHTTP packet-up — документированный future

| Критерий | WS | XHTTP (packet-up) |
|---|---|---|
| Поддержка CF free | полная, WebSocket включён по умолчанию на всех планах | packet-up работает, stream-up за CF free исторически проблемен, mode=auto деградирует на packet-up (E3 REQ) |
| Поддержка клиентов | 100% (v2rayNG, Hiddify, NekoRay, sing-box — классика) | только свежие сборки ядер; требует проверки на реальных устройствах |
| Риск приёмки | низкий — схема воспроизводится из тысяч гайдов | средний — два неопределённых звена (CF free × ядро клиента) |
| Зрелость кода Xray-конфига | `network: websocket` + `settings.path` — минимальный рендер | `network: xhttp` + mode-семантика |

**Решение: WS как единственный транспорт v1.** Владельческие клиенты свежие —
но свежесть помогает WS ничуть не хуже; XHTTP даёт риски без выигрыша (цель
цикла — egress через CF, а не новый транспорт). XHTTP packet-up за CF —
зафиксирован как future-расширение (второй CDN-инблэнд, отдельный REQ, если
WS-канал покажет ограничения). Это же — запас E3 REQ.

### OQ-3 — origin-инблэнд и порт: отдельный inbound, TCP 2053

- **Отдельный inbound обязателен:** у Xray-инблэнда один `network` в
  `streamSettings` — WS и XHTTP в одном инблэнде не совмещаются; path-роутинг
  «внутри того же 8443-inbound» между транспортом `xhttp` (path `/xhttp`) и
  `ws` невозможен. Трогать XHTTP-direct-инблэнд запрещено инвариантом §4.
- **Порт — TCP 2053.** Факт (Cloudflare docs, network ports): CF проксирует
  HTTPS на **443, 2053, 2083, 2087, 2096, 8443**. 443 занят Reality, 8443 —
  XHTTP-direct; из списка CF HTTPS-портов берём первый свободный — 2053.
- **Ключевой факт CF (определяет формат ссылки): CF соединяется с origin на
  том же порту, на который подключился клиент.** Следствие: share-link CDN
  использует порт **2053** (edge), а не 443; origin слушает 2053. Это
  **девиация от FR-4 REQ** («порт 443 CF edge, НЕ origin-порт»): в текущей
  топологии «443 → origin 443» упирается в Reality-инблэнд и сломало бы
  Reality. Девиация зафиксирована в SPEC §4.3 и отмечена аналитику/владельцу
  как правка REQ FR-4 на G5. Альтернатива «edge 443 + CF Origin Rules
  (port override → 2053)» — технически возможна на free-плане, но добавляет
  ручной CF-конфиг и зависимость; отложена как future (тот же будущий ADR,
  что и XHTTP-CDN).
- Порт фиксируется в `gateway/paths.py` (`CDN_ORIGIN_PORT_DEFAULT = 2053`,
  `CDN_WS_PATH = "/cdnws"`); проверка занятости `ss -tlnp` ДО изменений (E9).

### OQ-4 — TLS CF→origin: Full (strict) + отдельный LE-сертификат на `cdn.eu-cloud-xip.com`

- **Flexible отклонён окончательно:** CF→origin идёт открытым HTTP через
  интернет→датацентр; VLESS-пейлоад с uuid наблюдаем на этом участке (FR-3
  риск-заметка). Не принято.
- Full (strict) требует валидного сертификата на origin **имени
  `cdn.eu-cloud-xip.com`** — существующий LE-сертификат прошлого цикла выдан
  на `103-45-247-172.eu-cloud-xip.com` и для cdn-записи **невалиден**.
  Следствие: ещё один LE-выпуск по существующему certbot-механизму (ADR-004,
  HTTP-01). **Порядок обязателен:** выпуск при grey-cloud записи (HTTP-01
  напрямую), затем включение orange cloud; продление (E11) — HTTP-01 через CF
  edge, при отказе — временно grey-cloud на время продления (чеклист SPEC §8).
- Self-signed отклонён: Full (strict) его не принимает; «Full (не strict)» —
  ослабление, не предлагается.

### OQ-5 — CF-автоматизация: v1 — ручные шаги владельца в панели CF, CF-API — future

- v1 не требует API-токена (не появляется новый секрет — NFR проще); все
  CF-действия локализованы в чеклисте SPEC §8 (перенос зоны, DNS-запись,
  orange cloud, SSL/TLS режим Full strict, WebSockets On).
- Установщик `vds xray add-cdn` проверяет прекондишн DNS (E1): `dig +short
  cdn.eu-cloud-xip.com` должен вернуть IP из опубликованных диапазонов CF;
  до переноса зоны — внятный отказ до изменений.
- CF-API (создание записи/включение proxy скриптом) — будущая фаза при
  появлении токена (отдельный ADR; токен — секрет 0600, вне state.json).

## Последствия

- Положительные:Reality/Hysteria2/XHTTP-direct не затронуты ни на одном шаге;
  отключение CDN — toggle orange cloud; новые сущности — один inbound + один
  сертификат + запись state, локализованы в paths.py/cdn.py.
- Отрицательные / долг: ссылка CDN с портом 2053 (не 443) — девиация от FR-4
  (правка REQ на G5); продление LE через edge зависит от CF-настроек
  (Always Use HTTPS и пр.) — fallback «временно grey на время продления»;
  XHTTP-CDN отложен.
- Трудно изменить позже: порт 2053, path `/cdnws`, имя записи
  `cdn.eu-cloud-xip.com` — локализованы в `gateway/paths.py`; смена — новый ADR.

## Как откатить

1. Выключить orange cloud на `cdn.eu-cloud-xip.com` (панель CF, владелец) —
   CDN-канал мгновенно недоступен извне, остальной стек не затронут.
2. `vds xray remove-cdn --apply` (dry-run по умолчанию): бэкап config.json →
   вычитание CDN-инблэнда → `xray -test` → рестарт `vds-xray`; вычистка
   CDN-клиентов из state.json; LE-сертификат cdn-домена оставить (пассивный,
   продлевается сам) или `certbot delete --cert-name cdn.eu-cloud-xip.com`.
3. `vds xray remove-transport cdn` НЕ трогает Reality/XHTTP-direct части
   конфига (вычитающее удаление, паттерн ADR-003 поправки).
4. Возврат NS к `ns1..ns4.eu-cloud-xip.com` — только если владелец решит
   выйти из CF полностью (вне отката канала).

## Дополнение (2026-11-11, факт развёртывания)

Домен: **asvpersonal.ru** (личный домен владельца, reg. 2026-11-11).
`eu-cloud-xip.com` непереносим в CF — NS зоны принадлежат хостеру
(регистратор GoDaddy провайдера), смена NS на уровне реестра недоступна.
Использован **апекс** вместо `cdn`-поддомена: в зоне единственная запись,
оранжевый на апексе не задевает прямые каналы (они на старом домене).
OQ-3 (порт 2053) и архитектура §2 — без изменений. Приёмка §7.2 — PASS,
включая Reality-gate. Эксплуатационное свойство подтверждено: канал живёт
при полном блоке IP asv1 провайдером (трафик клиента → CF edge).
