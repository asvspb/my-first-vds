# ADR-007: RU-relay — входной релей на российском VDS; mobile-whitelist сценарий

- **Дата:** 2026-11-12
- **Статус:** proposed (ждёт решения владельца: покупка RU VDS ~150–300₽/мес)
- **Контекст:** [CENSORSHIP-PATTERNS](../CENSORSHIP-PATTERNS.md) §2a/§3a/§3b,
  [REQ-20261112-transport-hardening](../team/requirements/REQ-20261112-transport-hardening.md),
  [MIGRATE-VDS](../MIGRATE-VDS.md), анализ видео-источников 2026-11-11..12
  (IPv6-каскады; обзор 100 коммерческих TG-VPN — воронка 100→5)
- **Закрывает векторы:** IP-троттлинг (смена src-пути), полный блок IP exit
  (ноутбук вообще не касается asv1), **mobile whitelist** (см. §Whitelist)

## Контекст

Живой стек asv1 (2026-11-12): Reality/XHTTP/Hysteria2 (socks-профили), CDN
VLESS+WS за CF (выживание при блоке IP), AWG-split основная схема. Реализованные
векторы отказа: TSPU-троттлинг TCP (обходится UDP/CDN), полный блок IP asv1
(обходится CDN), DNS-подмена (DoH+exclude). **Не покрытый вектор**:
**mobile whitelist** — режим мобильного оператора «только разрешённые
RU-ресурсы» (Tele2 и др.; включается профилем ТСПУ по регионам/событиям; в
обзоре 100 коммерческих TG-VPN 56 из 100 выбыли именно на этом критерии).
В whitelist-режиме: иностранный dst-IP блокируется на уровне оператора —
**мёртвы все каналы, чья входная точка за рубежом** (socks-профили, CDN —
CF edge тоже не в белом списке).

Плюс накопленный болевой опыт: IP-троттлинг/asubnet-баны exit-сервера лечатся
сейчас только переездом (MIGRATE-VDS), а IPv4-подсети хостеров меняются
дорого и редко.

## Решение (предложение)

**RU-relay** — входной AmneziaWG-релей на российском VDS:

```
ноутбук/телефон ──AWG (UDP, обфускация, domestic)──> RU-relay ──> выбор ноги:
     домашний/мобильный IP          RU IP                  (a) IPv4 → asv1 (если жив)
   (whitelist: RU-IP пропускает)  (не трогается)           (b) IPv6 → asv1 (ротация за минуты)
                                                           (c) запас: TCP-Reality до relay
```

### R1. Плечо «клиент → RU-relay» — только AmneziaWG; TCP-фолбэк с RU-SNI

- Чистый WG внутри РФ недопустим: ТСПУ на транзитных стыках включает
  сигнатурные профили и внутри страны (мобильные сети особенно). AWG
  (Jc/S1/S2/H1–H4) — обязательно.
- Фолбэк-нога: **TCP-Reality до relay с RU-маской** — на domestic-плече
  RU-SNI раскрывается идеально (RU→RU TLS не подозрителен; урок
  CENSORSHIP-PATTERNS §2.7 — там RU-SNI на foreign IP был ошибкой, здесь он
  правильный). Реализация: xray inbound на relay (тот же
  `vds xray add-cdn`-паттерн), целевой dest — RU-сайт в той же подсети хостера
  relay'я.
- IPv4-адрес relay'я и порт — не в белых списках как домен; работает в
  **soft-whitelist** (см. §Whitelist). Strict-режим — отдельный раздел.

### R2. Плечо «relay → exit» — три ноги по приоритету

1. **IPv4→asv1** (если asv1 жив из РФ-DC): просто, быстро; при троттлинге
   asv1-IP для резидентов DC↔DC-плечо обычно чистое (эпирически: полный блок
   2026-11-11 не задел check-host/CF→origin ноги).
2. **IPv6→asv1** (ротация за минуты): требует dual-stack на asv1 (сейчас
   **нет v6** — проверено 2026-11-12; критерий выбора нового exit-хостера при
   миграции: **IPv6 /48+ обязательно**). Забаненный v6 → хостер выдаёт новый
   (до 64 адресов бесплатно у ряда хостеров) → правка одной AAAA/Endpoint.
   Инспирировано видео-разбором (Серверные Технологии): каскад entry→exit
   по v6 при забаненном v4.
3. **Exit-замена**: relay декоммутируется от конкретного asv1 — при
   переезде exit (MIGRATE-VDS) правится только relay-конфиг, клиенты не
   трогаются.

### R3. Интеграция со стеком

- **Ноутбук**: новая AWG-инстанция `vpn-awg-split@relay` (шаблон 14_awg-split.sh
  уже templated) + доменный split переиспользуется без изменений (маршрутизация
  зон та же, меняется только выходной iface relay-ноги). Команда:
  `vpn amneziawg tunnel on` с активной инстанцией relay; переключение
  основная/релейная схема — выбор инстанции.
- **Телефон** (главный бенефициар whitelist-обхода): профиль AmneziaVPN
  (официальное приложение) до relay + split-AllowedIPs; или v2rayNG до
  Reality-фолбэка. Ссылки — `vds amneziawg add-client phone-relay`.
- **Автодетект whitelist** (vpnm, кандидат-WP): probe расширяется проверкой
  «foreign direct fail + RU direct ok» → статус `whitelist-mode` →
  рекомендация/автопереключение на relay-профиль.

### R4. Хостинг relay

RU VDS, KVM, без ограничений UDP, Москва/Питер (RTT ~10–20 мс от
Волгограда), 150–300₽/мес. Юрисдикция РФ: relay-оператор видит метаданные
«клиент → туннель» (не содержимое — оно за AWG/xray). Приемлемо для цели
«доступ к заблокированному»; не для анонимности. 2IP/ABUSE-локации —
проверить UDP-политику при выборе.

## Whitelist-сценарий — детальный разбор

Два реализуемых режима «белых списков» у операторов:

### Режим W-soft: «RU разрешено, foreign блок» (большинство внедрений)
- Правило: dst-IP из RU-реестра/гео → пропустить; прочее → drop.
- **RU-relay работает как есть**: relay-IP российский → AWG-нога проходит.
- DNS: операторский резолвер резолвит RU; foreign — NXDOMAIN/блок. Пробу
  делаем через DoH (не зависим) либо remote-DNS relay'я (socks5h/AWG —
  DNS уходит на relay).
- Покрытие: всё, что сейчас делает основная схема, но через relay.

### Режим W-strict: «только домены из gov-списка» (жёсткий, региональные акции)
- Правило: DNS/SNI ∈ gov-список → разрешить; прочее → drop. IP-хостинг relay'я
  НЕ в списке → AWG-нога блокируется.
- Работающие паттерны (приоритет, требует полевой проверки на конкретном
  операторе):
  1. **CDN-домен в gov-списке**: если оператор резолвит/пропускает
     big-CDN на RU-попах (Яндекс-CDN и т.п.) — входная точка за таким
     фронтом (CF не в списке, RU-CDN — вероятно да).
  2. **Serverless-фронт на RU-облаке**: ingress через
     Yandex Cloud Functions / VK Cloud serverless (домены `*.yandexcloud.net`
     / RU-облака — кандидаты в списки как RU-ресурсы) → tunnel → exit.
     Спекулятивно, требует полевого теста.
  3. **v6-лазейка**: если whitelist-энфорсмент реализован только на v4
     (частый случай при спешке) и оператор даёт v6 (МТС/Мегафон) — туннель
     по v6 до relay/exit. Проверяется в полевых условиях.
  4. **eSIM зарубежная** — вне whitelist в принципе (другой оператор/страна);
     аварийный канал.
- Честный вывод: W-strict полностью не закрывается без полевого теста;
  приоритет — задокументировать матрицу проверки (§Test-plan) и провести при
  первом включении whitelist у оператора владельца.

### Test-plan (полевая матрица, на SIM с whitelist)

| проверка | метод | исход |
|---|---|---|
| raw RU-IP reachable? | ping/TCP до relay-IP | да → W-soft, relay жив |
| v6 reachable? | ping6 до relay/exit v6 | да → v6-лазейка |
| operator DNS: foreign домены? | dig @оператор api.telegram.org | NXDOMAIN → DNS-фильтр |
| gov-CDN домены (Яндекс CDN)? | curl до известного RU-CDN фронта | да → паттерн 2.1 |
| SNI-фильтр или IP-фильтр? | curl c SNI=RU-домен на relay-IP vs без SNI | различие → SNI-режим |

## Альтернативы (рассмотрены и отклонены/отложены)

| альтернатива | вердикт |
|---|---|
| Коммерческий TG-VPN с «обходом whitelist» (топ-5 обзора) | отклонено: общий оператор, трафик видит владелец бота; качество рынка — 82% нерабочих |
| CF Workers как ingress для whitelist | отклонено для W-режимов: CF не в gov-списке; остаётся в roadmap как US-blocking resilience |
| Tor bridges | аварийный люкс-канал, не рабочий транспорт (медленно) |
| v6-only путь без relay | без входной точки на RU — whitelist всё равно режет foreign dst |

## Последствия

**Положительные**: закрывается последний непокрытый вектор (mobile whitelist);
дешёвая ротация exit-ноги (v6); декоммутация клиентов от exit-IP; +5–20 мс RTT
— незаметно.

**Отрицательные/риски**: RU-хостер видит факт туннеля (метаданные); relay —
новая единица отказа (лечится вторым relay'ем в другой локации, при
необходимости); W-strict не гарантируется без полевого теста; +1 сущность к
обслуживанию (обновления, reboot-проверки).

## Шаги внедрения (при решении владельца)

1. Покупка RU VDS (dual-stack желательно, v6 — ключевой критерий).
2. `11_vds-deploy.sh`-стиль мини-деплой: bare AWG-server + (опц.) xray
   Reality-фолбэк — отдельный лёгкий скрипт `21_ru-relay-deploy.sh` (не весь
   orchestrator: relay'ю не нужны gateway/links).
3. `vds amneziawg add-client relay-laptop` на asv1 → нopa relay→asv1
   (или статические маршруты на relay: RU-direct, остальное → asv1-туннель).
4. Ноутбук: `vpn-awg-split@relay` инстанция + `vpn amneziawg add-client relay`.
5. Телефон: AmneziaVPN профиль до relay.
6. Полевая приёмка по Test-plan (при доступном whitelist-профиле оператора).
