# ADR-015: клиентское авто-переключение каналов — отдельный юнит `vpn-failover`

- **Дата:** 2026-11-18
- **Статус:** accepted (G2 APPROVED 2026-11-18; обе линзы — реализуемость и
  тест-план — без замечаний; SPEC — [SPEC-20261118-vpn-failover](../team/specs/SPEC-20261118-vpn-failover.md))
- **Контекст SPEC:** SPEC-20261118-vpn-failover (WP-FAILOVER), продолжение
  SPEC-20261116-probe-response §16 и «Фазы 4» плейбука
- **Связанные:** ADR-014 (клиентский `vpn guard`: контракт, приватность,
  read-only), ADR-012 (log-forensics: «анализатор не реагирует»),
  ADR-007 (RU-релей), ADR-011 (UFW hardening / lock-443),
  SPEC-20261116-vpn-guard, SPEC-20261116-probe-response, SPEC-20261117-alert-watch

## Контекст

ADR-014 зафиксировал жёсткий инвариант: `vpn guard` — **наблюдатель**, он не
переключает, не рестартит и в сеть не ходит (кроме явного `vpn guard sync`).
Причина — доверие: демон, который «что-то делает» по эвристике логов, при
ложном срабатывании рвёт рабочую связь и уничтожает улики.

Эксплуатация это ограничение упёрла в потолок. Два сценария:

1. **Серверный `lock-443`** (SPEC-20261116-probe-response §4): при `threat=high`
   exit-узел закрывает входящий 443/tcp на 48 ч. Прямой Reality умирает
   мгновенно, а пользователь узнаёт об этом из «интернета нет».
2. **Окно ТСПУ 2–15 минут** (ADR-014, контекст): отказ быстрый, ручная реакция
   не укладывается.

В обоих случаях правильное действие известно заранее и однотипно: уйти на
другой маршрут/протокол. Это не анализ — это **исполнение политики**. Держать
его внутри read-only демона нельзя, а заставлять человека бегать руками —
именно то, от чего уходили.

## Решение

Ввести **отдельный** клиентский агент — юнит **`vpn-failover.service`** (+
`vpn-failover.path`), который:

1. **Читает** те же артефакты, что `vpn guard` (`findings.jsonl`,
   `server-verdict.json`, `state.json`), **не пишет** их;
2. **действует** только по узкому, перечислимому набору триггеров
   (`G-01`, `G-09`, категория `expected_lockdown`) — не по любым `high`;
3. проходит **лестницу кандидатов** `relay → asv2-hy2 → asv2-awg → asv2-cdn`
   с обязательными проверками `pre_flight` / `post_flight`;
4. при исчерпании лестницы уходит в экспоненциальный backoff и **не** пытается
   «лечить» дальше;
5. **не откатывается автоматически** после снятия серверного лока.

Имя юнита — **`vpn-failover.*`, не `vpnm-failover.*`**: префикс `vpnm-` занят
профилями, и `runners.enabled_vpnm_units()` / `vpn autostart off` не должны
выключать аварийный агент (инвариант AC-F11). Это же отделяет его от
`vpn-guard.service` в `systemctl --user list-units`.

## Почему отдельный юнит, а не код внутри `vpn guard`

| Критерий | Внутри guard | Отдельный `vpn-failover` (выбрано) |
|---|---|---|
| Инвариант ADR-014 «read-only демон» | ломается | сохраняется буквально |
| Риск ложного действия | делит процесс с парсером: падение/баг меняет и наблюдаемость | изолирован; guard продолжает писать улики |
| Привилегии | демону нужен доступ к `systemctl`/`sudo` → расширение attack surface | свои, только у failover; guard остаётся без них |
| Отключение | «выключить guard» = потерять наблюдаемость | `vpn guard failover disable` не трогает guard |
| Тестируемость | AST-инвариант (AC-F1) невозможен | проверяется по импортам отдельно |

## Альтернативы

1. **Встроить в `vpn guard`** — отвергнуто: прямое нарушение ADR-014 и
   единственного инварианта, который дал демону доверие; AC-F1 стал бы
   невыполнимым.
2. **Оставить человеку, добавить только уведомления** — отвергнуто как
   достаточное: окно 2–15 мин, ночью и в дороге реакции нет; уведомление
   приходит уже после потери связи.
3. **Серверный push-команде клиенту** («переключись») — отвергнуто: сервер не
   знает локального контекста клиента (какой профиль активен, жив ли локальный
   интернет), и это превращает сервер в удалённый исполнитель на ноутбуке.
4. **Failover внутри systemd через `Restart=` / `Wants=`** — не подходит:
   профили не падают (юнит активен), умирает **канал**; systemd этого не видит.

## Последствия

**Положительные:** прямой канал перестаёт быть единой точкой отказа; человек
получает связь без участия; инвариант read-only у наблюдателя сохраняется.

**Отрицательные и как закрываются:**

- *Риск ложного переключения* (шум в логах принят за блокировку) → узкий набор
  триггеров, `local_net_check` первым шагом, `pre_flight` до переключения,
  cooldown 900 с и лимит 3 переключения/час.
- *Риск «пинг-понга»* между каналами → `candidate_cooldown` 10 мин после
  `dead_entry`/`dead_exit`, pin на выбранном профиле.
- *Риск остаться без связи из-за агрессивного `vpn down`* → при total blackout
  возврат к штатному маршруту только если не включён строгий kill-switch; иначе
  оставить как есть и уведомить.
- *Привилегии* → агент работает в user-scope; для схем, требующих root
  (`vpn start relay`), используется `sudo -n`; отсутствие sudo = `switch_error`,
  не падение и не зависание.
- *Шум уведомлений* → desktop подчиняется **отдельному opt-in флагу**
  (`notify.failover_desktop`, по умолчанию `false`), как и остальной guard
  (OQ-5 ADR-014). Решение владельца 2026-11-18: отдельный флаг, не безусловная
  отправка.
- *Секреты* → токен Telegram только в файле 0600, никогда в argv/URL-логах;
  `vpnm/guard/redact.py` получает паттерн токена бота.

**Что НЕ меняется:** `vpn guard` остаётся read-only (AC-F1);
`vpn guard sync` — по-прежнему единственная сетевая команда guard-а;
серверный `vds alert` остаётся только уведомляющим; `auto-lockdown` остаётся
opt-in.

## Совместимость и обратимость

Решение обратимо: юнит opt-in, `config.failover.enabled=false` по умолчанию,
удаление — `vpn guard failover disable` + снятие юнита. Артефакты
(`failover_state.json`, `failover_history.jsonl`, `pending_alerts.jsonl`)
изолированы и удаляются `vpn guard remove --purge`. Публичный контракт
`guard.*` не меняется — новые схемы аддитивны и версионируются
`schema_hashes()`.
